## Verdict

Both high findings of 11-18 are closed with tests,
and 18 medium ones with them;
every suite passes on four engines and in three browsers.
The main risk moved to three places where one request,
or one profile action, goes round a boundary the docs promise. An
`Expect: 100-continue` header makes the proxy skip every rule it applies
to outgoing headers (AW-118). A signed-in session alone adds an address
to an account that has no confirmed one,
and a password reset to that address takes the account (AW-119). And a
provider account with no stored address is admitted at every door while
the email rules refuse its sign-in (AW-120).
None of the three is caught by a test,
and each sits beside a fix of the last weeks: AW-84 and AW-19, AW-77,
AW-106.

## 1. Proxy, transport and WebSockets

### AW-118 `Expect: 100-continue` makes the proxy skip every header rule (high)

Everything Authwall does to the outgoing request lives in one event of
the proxy library, `proxyReq` (`src/create_app.js:310-343`):
`set_forwarded_headers` (`:312`), `strip_authwall_cookies` (`:313`),
`X-Auth-User` (`:325-328`), `AUTHWALL_SET_HEADERS` (`:329-332`) and
`AUTHWALL_UNSET_HEADERS` (`:333-335`). httpxy 0.5.6 does not emit that
event for a request that carries an `Expect` header,
`node_modules/httpxy/dist/index.mjs:317-319`:

```
proxyReq.on("socket", (_socket) => {
    if (server && !proxyReq.getHeader("expect")) server.emit("proxyReq", proxyReq, req, res, options);
});
```

With `Expect` Node has already rendered the outgoing headers,
so the library skips the hook. Node answers `100 Continue` itself and
hands the request to Express with the header still in `req.headers`,
and the request is proxied with the client's headers as sent.

Scenario: proxy or direct mode, any settings.
The actor is a signed-in user, a token holder, or nobody at all on a
public or optional-auth path (`config/settings.yaml:20-26` ships five
public paths).
The request carries `Expect: 100-continue` plus the headers to smuggle.
An upstream that trusts a header the operator pinned with
`AUTHWALL_SET_HEADERS` or dropped with `AUTHWALL_UNSET_HEADERS`,
or an `X-Forwarded-*`, takes the client's value;
and the live session cookie, which AW-19 keeps from the upstream,
reaches it.
curl and .NET clients send this header on large bodies by themselves,
and silently lose their identity.

Evidence (`scratchpad/audit/proxy/expect_http.test.js`; proxy mode,
trust proxy off, `SET_HEADERS` = `X-Role=viewer`,
`X-Proxy-Secret=operator-secret`, `UNSET_HEADERS` = `Remote-User`),
what the echo upstream got for the same signed-in POST:

| Header at the upstream | Without `Expect` | With `Expect: 100-continue` |
|---|---|---|
| `x-auth-user` | `awuser_…` | absent |
| `cookie` | absent | `authwall.sid=` the live session |
| `x-forwarded-for` | `127.0.0.1` (resolved) | `6.6.6.6` (the client's) |
| `x-forwarded-host` | `127.0.0.1:35125` | `evil.test` |
| `x-real-ip`, `forwarded`, `x-forwarded-user`, `x-original-url`, `x-rewrite-url` | absent | the client's values |
| `x-role` (pinned `viewer`) | `viewer` | `admin` |
| `remote-user` (dropped by `UNSET_HEADERS`) | absent | `admin` |
| `x-proxy-secret` (set by `SET_HEADERS`) | `operator-secret` | absent |

An anonymous `GET /favicon.ico` with `Expect` reached the upstream with
the same client values. `X-Auth-User` itself cannot be forged this way:
`clean_headers` (`src/create_app.js:302`,
`:1150-1165`) deletes it from `req.headers` before the proxy,
and the bearer token is deleted there too (`:571`).
No test in `tests/api` sends `Expect`.
The promise it breaks is `docs/config.md:469-477`. Fix:
apply the header rules to `req.headers` before `proxy.web()`,
so they do not depend on a library event,
and delete `req.headers.expect` (Node has already answered it).
Acceptance: the table's second column equals its first,
and the cases of `identity_header_strip`,
`forwarded_headers_come_from_authwall` and
`upstream_never_sees_the_session_cookie` are repeated with
`Expect: 100-continue`.

### AW-121 A signed-in WebSocket upgrade carrying `Expect` ends the process when the upstream closes or refuses the connection (medium)

### AW-122 256 unfinished requests on a public path hold every upstream socket (medium)

## What is good

To keep as it is:

- **The path judgement.** A target is decided on its canonical form and
  forwarded raw (`src/helpers/is_origin_form.js`, `canonical_path.js`,
  `target_path.js`, `is_public_path.js`), and the sidecar uses the same
  functions (`src/routes/status.js:215-226`). Encoded dots and slashes,
  double encoding, `..;`, a backslash, NUL, overlong UTF-8, `//`,
  absolute-form and the case of `/auth` all fail closed.
- **The identity strip works on the request, not on a library event.**
  `clean_headers` (`src/create_app.js:1150-1177`) and the upgrade's own
  loop (`:629-634`) delete from `req.headers`, which is why
  `X-Auth-User` could not be forged even with the hook skipped in
  AW-118. It is the pattern the other header rules need.
- **One admission answer, asked at every door.** HTTP, bearer, sidecar,
  upgrade and lease all go through
  `src/helpers/access_refusal_from_identities.js`, and
  `SessionStore.set` only updates a row it read
  (`src/helpers/SessionStore.js:80-82`).
  A revoked session or token was refused at every door tried.
- **CSRF on every state-changing route.** All 26 POST routes run
  `csrf_middleware` on a per-session token rotated at sign-in
  (`src/helpers/replace_session.js:11-16`), and a token cannot manage
  its owner's account
  (`src/helpers/middleware/auth_middleware.js:17-26`).
- **Mailed links and codes.** 32 random bytes, only the SHA-256 stored,
  spent by a conditional update inside the transaction that does the
  work (`src/helpers/consume_one_time_token.js:9`,
  `src/routes/password.js:336-346`); codes bcrypt-hashed, five guesses a
  code counted in one statement (`src/helpers/spend_attempt.js:9-12`);
  a mailed link acts only on a POST with the browser's CSRF token,
  so a scanner's GET changes nothing.
- **The provider flow.** State and PKCE S256 for all six providers,
  compared before any outbound call
  (`src/helpers/make/make_oauth_flow.js:60-66`, `:84-93`);
  no joining by address (`:314-326`); each provider's own "verified"
  flag is weighed (`src/helpers/oauth_id_token_claims.js`).
- **Configuration that refuses.** Every `${AUTHWALL_*}` of
  `config/settings.yaml` is in `config/authwall_env_vars.txt` and in
  `docs/config.md`, and the reverse;
  an unknown name stops the start (`config/make_config.js:443-454`); a
  missing root secret is made with mode 0600 and the session key derived
  from it (`:394-425`, `:184`).
- **The migrations.** All 21 ran up one by one with rows in between,
  down one by one, and up in one batch and back, on SQLite 3.54.1,
  PostgreSQL 17.12, MySQL 8.4.13 and 5.7.44, raw SQL included;
  `compileSqlOnError: false` (`knexfile.js:16`, `:37`,
