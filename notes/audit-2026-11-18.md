## Verdict

**Protect the test database first, then align authorization for existing credentials with fresh sign-in.** A routine test command can erase the configured application database. Separately, enabling an email allowlist can leave old credentials usable for a username-only account that the new policy would refuse at sign-in. Both have concrete prerequisites and consequences even with a fully passing test suite.

## Findings

<a id="aw-105"></a>

### AW-105 · API test cleanup can erase the configured application database (high)

A developer with a working application database in `.env` can lose every user, identity, session, token and audit event by running the documented test suite. This requires the configured database to be reachable with deletion privileges. The example environment itself supplies an `AUTHWALL_DB`.

`mocha.api.js:1` loads dotenv before line 6 applies the temporary SQLite fallback with `??=`. Lines 40–56 list ten live application tables and execute `await db(table).del()`. Line 77 schedules this cleanup for each concurrency test, including `tests/api/bootstrap_users.test.js:78`. The rollback used by ordinary API tests offers no protection on this branch. Playwright also inherits the ordinary database setting and starts a seeded server against it (`playwright.config.js:1`, `:91`). The destructive conclusion follows from source. All actual API runs used disposable stores.

**Fix and acceptance.** Make a unique temporary database the default even when the project’s normal dotenv file names a database. Give CI a test-only connection setting and allocate a disposable schema or database on its server. Check the target before migration, seeding or cleanup. In a regression test, put a harmless sentinel in a separate fixture named by the application setting and verify it survives both test entry points.

<a id="aw-106"></a>

### AW-106 · Existing username credentials can survive a restrictive policy change (high)

An operator who enables an allowlist can see a username-only user refused at fresh sign-in while their existing session or personal access token can still reach the upstream. This matters for installations migrating from unrestricted registration to an email policy, with a supported email-bearing sign-in method and independent email confirmation disabled (for example an OAuth flow plus usernames).

`src/helpers/username_sign_in_refusal.js` explicitly returns `no_verified_email` for an empty result. Existing-credential admission calls `account_access_refusal`, which delegates to `account_email_refusal`. The latter checks each verified address and returns `null` for an empty set (`src/helpers/account_email_refusal.js:16–25`). HTTP, sidecar, bearer and WebSocket admission share the decision (`src/create_app.js:495`, `src/routes/status.js:231`, `src/helpers/authenticate_personal_access_token.js`, `src/create_app.js:951`). The passing restart story covers an account **with** a verified address added to a denylist. It misses the empty-address transition. This source finding narrows the remaining scope of AW-80. The same cache is keyed by user ID and serialized rules, so an identity change from another replica is also invisible until cache invalidation or restart (`src/helpers/account_access_refusal.js:21–29`).

**Fix and acceptance.** Use one policy decision that can distinguish an eligible provider-backed account from an old username-only account. Preserve the separate pending-verification flow. Cover fresh login, old browser session, token, sidecar and WebSocket, then remove the restriction and check the documented restoration behavior.

<a id="aw-107"></a>

### AW-107 · Owner confirmation is spent in one request’s memory (medium)

A double submission after one approval can create two durable personal access tokens. `src/helpers/spend_confirmation.js:10–18` validates and deletes fields in a request-local session object. `src/routes/personal_access_tokens.js:52–68` independently inserts the token. `src/helpers/SessionStore.js:81` writes the full session JSON by UID. Two overlapping requests can therefore read the same unspent state. The passing one-use test in `tests/api/stories/confirmation_is_spent_once.test.js` submits the second request after the first completes.

**Fix and acceptance.** Claim a unique approval in the database with a conditional write. Commit its consumption with the authorized change. Two legitimate concurrent submissions for one approval should produce one token, one creation event and a clear outcome for each browser request.

<a id="aw-108"></a>

### AW-108 · OAuth connection approval omits the provider subject (medium)

The owner sees the provider and its returned addresses while approving a link. The callback knows the stable provider account ID. The pending approval records the provider and its emails, and the comparison key includes only the action and provider type (`src/helpers/make/make_oauth_flow.js:175–181`, `src/helpers/confirmation_key.js:8`). After approval, line 214 writes the subject returned by the **current** callback. Switching accounts at the same provider can therefore change which identity gets linked after the owner confirmed. Linking gives that identity a future sign-in method.

**Fix and acceptance.** Bind approval to the provider and its normalized subject. Show the account being approved. A changed subject should start a fresh confirmation. Retain the existing, separately authorized path for a provider that verifies the primary email.

<a id="aw-109"></a>

### AW-109 · The first removal factor can survive the ten-minute window (medium)

`src/helpers/record_confirmation.js:9–13` reuses all methods recorded for the same action and overwrites their single `confirmed_at` timestamp whenever another method succeeds. `src/helpers/is_recently_confirmed.js:11` checks only that timestamp. For a removal requiring two factors, an old first factor can consequently count alongside a current second factor. The account must still have the same pending action and supply the other factor.

**Fix and acceptance.** Track a deadline for the pending approval and timestamps for its individual factors. After the deadline, require fresh evidence for both. Exercise the expiry boundary with a controlled clock, including resumption from another tab.

<a id="aw-110"></a>

### AW-110 · Password change and revocation commit separately (medium)

A person changing their password after losing a device expects the old sessions and tokens to stop working together. Both password-change routes write the hash before calling the shared cleanup (`src/routes/password.js:394–396`, `src/routes/profile.js:148–167`). The helper regenerates a session and writes an event before deleting other sessions, invalidating links and revoking tokens in separate statements (`src/actions/complete_password_change.js:18–33`). A database failure between these steps leaves the new password in effect with some old credentials still valid. A retry with the old password then fails. Successful-path tests pass.

**Fix and acceptance.** Use the transaction in `src/routes/password.js:333` for completed resets as the model. Commit the new hash, credential invalidation and durable audit record together. Publish the replacement session and send notifications with defined post-commit behavior. Exercise failure between writes on both profile endpoints.

<a id="aw-111"></a>

### AW-111 · Seed imports accept unusable password hashes (low)

The file parser accepts the `$2y$` prefix and any two decimal cost digits (`src/helpers/parse/parse_authwall_seed_file.js:6`, `:95–97`). `src/helpers/models/users_create.js:17–23` stores the imported value verbatim. A local compatibility check using `node` and the installed bcrypt verifier on the same synthetic password and digest returned **2a true, 2b true, 2y false**. An imported password-only user can therefore be created successfully and then fail to sign in.

**Fix and acceptance.** Validate field type, supported version and supported cost at import. Reject unsupported imports with file and row location and keep the digest out of diagnostics. Cover the documented format and a rejected incompatible import.

<a id="aw-112"></a>

### AW-112 · Magic registration can leave a user row without a sign-in identity (medium)

Both the mailed-link and code branches consume the credential before looking up the identity. When creating an account they call `users_create()`, insert the identity and assign its primary address as separate operations (`src/routes/magic_link.js:112–143`, `:188–217`). The identity has a unique constraint (`db/migrations/20260314130739_user_identities.js:26`). A failed insert, including a concurrent registration for the same name through another flow, can leave a user row with no identity and a spent credential. The passing same-link concurrency test covers two uses of one token. The password registration route already wraps the user and identity writes in one transaction.

**Fix and acceptance.** Apply the same transaction boundary to both magic flows and resolve identity conflicts deliberately. Verify that a mid-registration failure leaves neither a stray user nor an ambiguous retry outcome.

<a id="aw-113"></a>

### AW-113 · Return validation and SPA navigation parse URLs differently (medium)

The relative-return branch accepts the original string after a handful of character checks (`src/helpers/is_relative_url.js:8–27`, `src/helpers/allowed_return_url.js:19–21`). `src/helpers/middleware/landing_middleware.js` preserves that string in JSON. The SPA then parses it with the browser URL parser and navigates to the resolved URL (`design/public_html/spa.html:1465–1470`). Browser URL parsing removes certain ASCII control whitespace before resolving the authority. Consequently some strings classified as relative by the server resolve outside the documented return origins. The immediate risk is a misleading post-authentication landing. No transfer of an Authwall credential is established by this finding.

**Fix and acceptance.** Reject control characters, resolve the candidate once against the canonical public origin, check the resolved protocol and host, and return the validated serialization. Preserve legitimate relative and approved subdomain returns. Require the redirect and JSON-landing paths to enforce the same origin policy.

<a id="aw-114"></a>

### AW-114 · Long passwords silently lose part of their value (low)

Sign-up, reset, password change and profile editing enforce a minimum length and pass the supplied string to bcrypt (`src/routes/password.js:160`, `:309`, `:380`, `src/routes/profile.js:82`). The installed library documents a 72-byte UTF-8 input limit in `node_modules/bcrypt/README.md:41`. Two long passwords that differ only beyond this boundary therefore authenticate identically. Visible character count can be much shorter than byte count for non-ASCII passwords.

**Fix and acceptance.** Apply an explicit byte-length policy when setting passwords, including provisioning tools, or introduce a versioned hashing scheme that consumes the full input. Preserve existing hashes on sign-in during migration. Cover the byte boundary with both ASCII and multibyte input.

### AW-115 · Development dependencies have three underlying advisories (low)

`npm audit --package-lock-only --json` reported 10 affected package entries, five high and five moderate. The underlying advisories concern picomatch, minimatch and glob. The other entries reflect dependency chains through development tools including nodemon, Mocha and c8. `npm audit --omit=dev --package-lock-only --json` reported zero. The Dockerfile installs its runtime tree with `npm ci --omit=dev` at line 13. The two packages originally named by AW-104 are clear in this scan.

**Fix and acceptance.** Refresh the development-tool chains and rerun both audits and the test suite. Check whether proposed package downgrades preserve test and watch behavior before accepting them. [picomatch advisory](https://github.com/advisories/GHSA-fc5q-39xc-vjpf) · [minimatch advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249) · [glob advisory](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4)

<a id="aw-116"></a>

### AW-116 · A verification token survives redaction inside a return URL (medium)

When an address must be confirmed from a signed-in account, `src/routes/email_verify.js:146` builds a sign-in destination whose `return` value contains the verification URL and its still-valid token. The sign-in page also constructs this destination in `design/public_html/spa.html:2244`. `src/helpers/urlxxx.js:23–28` enumerates only the outer query keys and returns the original URL when none are sensitive. `src/create_app.js:121–127` logs the incoming URL and referrer through that helper. A legitimate verification journey can therefore persist the encoded credential in request logs. Its impact depends on token lifetime, associated account state and who can read the logs. AW-100 tracks a different sink in sidecar headers.

**Fix and acceptance.** Omit nested return values from logs or safely redact the nested destination, including across the shared Sentry sanitizer. Check a normal cross-device confirmation journey with a synthetic marker. Neither the marker nor its encoded form should reach the recorded request, referrer or telemetry.

<a id="aw-117"></a>

### AW-117 · A conflicting seed can attach aliases to an unintended account (medium)

A seed may declare several email addresses. If two of them are already verified by different users, `src/helpers/bootstrap_users.js:105–110` selects the first matching row across all addresses. It does not check whether there are multiple owners. Lines 182–195 then add all still-free identities to the selected account and ignore uniqueness conflicts on occupied identities. A provisioning mistake can thus attach a new verified recovery address to one owner while leaving another address with the second owner. The operator receives an added-identities or no-changes message. This requires an inconsistent operator-supplied seed.

**Fix and acceptance.** Collect the distinct owners first and refuse the entire seed entry on disagreement, before releasing pending identities or adding aliases. Include the conflicting record location in the diagnostic. Exercise multi-owner CSV and JSON entries across database engines and verify that each account keeps its previous identifiers.

## What is good

- **User.** The browser regressions cover signing out and back in, returning to a requested page, scanner-safe mailed links, and registration availability. All three browser engines passed the same 83 cases.
- **Maintainer.** The project already has two patterns needed by the repairs: conditional token consumption and transactional registration. The API suites apply real migrations and exercise all three database families.
- **Security boundary.** Existing tests cover refused unauthenticated requests, identity-header replacement, legacy cookie handling in the built-in proxy, PAT revocation, and verification on WebSocket admission and lease checks. These passed alongside the account and mail tests.
- **Operator.** The production image builds with its declared production dependencies, starts with fresh persistent state and exposes a simple liveness endpoint. The configuration reference distinguishes liveness from database readiness.

## Recommended order of work

1. **Separate test and application data (AW-105).** Give local runs and CI the same isolation, including database-specific tests.
2. **Align admission and owner proof (AW-106–109).** Start with the restart matrix and then cover subject, age and concurrent use of confirmations. Keep existing pending-verification and recovery paths usable.
3. **Contain credentials through failure and logging (AW-110, AW-116, AW-86).** Exercise failed writes as well as successful revocation. Cover nested navigation metadata in redaction.
4. **Finish account and navigation consistency (AW-112, AW-113, AW-117, M-02).** Include cross-flow registration, confused origins, multi-owner seeds and last-usable-credential checks.
5. **Bind release to its inputs (AW-35, M-12) and resolve import and tooling issues (AW-111, AW-114, AW-115).** Use a tested commit or built image digest for publication. Run the image check in CI and keep the development and production advisory totals separate.
