# Authwall penetration test

Repository audit · 7 September 2026 · Version 1.15.0

## Executive assessment

Authwall's core controls held up under this test. The one-time-token races,
the username-only allowlist bypass, the Microsoft email-verification gap and
the surviving reset credentials that the 5 September report raised as its
highest priorities are fixed, and their regressions pass. This pass found one
new authorization defect worth treating as high priority: an inbound identity
header the proxy fails to strip, which lets a client reach the upstream with a
forged identity on the upstream frameworks that fold `_` to `-`. The remaining
open items are the session, WebSocket and operations findings the previous
report already recorded, re-confirmed here with fresh evidence.

This test reports **16 open findings: 1 High, 12 Medium, 3 Low**. Thirteen are
carried forward from earlier notes; three are new this pass (one High, two
Low). Severity reflects impact under the stated preconditions, not a claim that
every deployment is exploitable.

The existing suites passed **176 unit tests and 502 API tests**. Twelve
additional probes reproduced the behaviors below; every probe asserted the
defective behavior and passed. Application source was not changed.

## High-priority finding

### P1 · High — An underscore identity header slips past the strip and reaches the upstream

**Evidence:** [create_app.js:787](../src/create_app.js#L787) (`clean_headers`),
[create_app.js:519](../src/create_app.js#L519) (WebSocket upgrade header loop).
Reproduced on both paths.

Authwall's central guarantee is that the upstream can trust `X-Auth-User`
because Authwall strips every inbound `x-auth-*` header and sets that one
itself. Both strip loops match a literal `x-auth-` prefix:

```js
if (s.startsWith('x-auth-')) { delete req.headers[s]; }   // HTTP proxy
if (name.startsWith('x-auth-')) { delete req.headers[name]; } // WS upgrade
```

Node lowercases header names but preserves underscores, so a client header
named `X_Auth_User` arrives as `x_auth_user`, does not match the `x-auth-`
prefix, and is forwarded unchanged. Many upstream stacks fold `_` to `-` (or
the reverse) when they expose headers: PHP's CGI/FPM mapping turns both
`X-Auth-User` and `X_Auth_User` into the single `HTTP_X_AUTH_USER`, and Apache
`mod_php` and several frameworks do the same. On such an upstream the attacker's
`x_auth_user` and Authwall's own `X-Auth-User` collide into one variable with
ambiguous precedence, so a request can carry a forged identity through the
gateway.

**Reproduction.** A signed-in client sent a proxied request with
`X-Auth-User: dash-spoof` and `X_Auth_User: underscore-spoof`. The echo upstream
received `x-auth-user` set to the real account uid — the dash form was stripped
and replaced — and `x_auth_user` set verbatim to `underscore-spoof`. The
WebSocket upgrade path behaved identically.

```
UPSTREAM x-auth-user = "awuser_gkaw15ijic7lguslk5dibcll"
UPSTREAM x_auth_user = "underscore-spoof"
```

**Impact and limits.** This defeats the `X-Auth-User` trust boundary on any
upstream that treats `x_auth_user` as `X-Auth-User`. It does not affect an
upstream that reads the header name literally, and an intermediary that drops
underscore headers (nginx's default `underscores_in_headers off`) blocks it —
but Authwall is frequently the only proxy in front of the app, so no such
intermediary is guaranteed. The exposure is upstream-dependent, and no
provider-side stack was exercised here; the header leak itself is demonstrated.

**Remediation.** Strip any inbound header whose name, after mapping `_` to `-`,
begins with `x-auth-`, on both the HTTP proxy and the WebSocket upgrade path;
equivalently, normalize the name before the prefix test. Do not rely on the
operator's `unset_headers` list to cover this. Add a probe that sends
`X_Auth_User` and asserts the upstream never receives an attacker-controlled
`x_auth_*` header.

**Acceptance.** With an authenticated request or upgrade carrying `X-Auth-User`,
`X_Auth_User`, and any other `x_auth_*` / `x-auth-*` variant, the upstream sees
exactly one identity header, set by Authwall.

## Medium-priority findings

### A05 · Medium — Counting identities does not count usable credentials

**Evidence:** [make_oauth_flow.js:276](../src/helpers/make/make_oauth_flow.js#L276)
(`disconnect_post`), [email_remove.js:35](../src/routes/email_remove.js#L35).

The OAuth disconnect guard still refuses only when `identities.length <= 1`. A
pending (unverified) email with no password is counted as a credential even
though it can neither receive a magic-link login nor a reset. Disconnecting the
sole OAuth identity can leave an account reachable only through an address
nobody has proven. `email_remove` now protects the last verified address under
`AUTHWALL_CONFIRM_EMAIL_REQUIRED` and under access rules with a username, which
is an improvement, but the general "is a usable credential left" decision is
still absent from the disconnect path.

**Remediation.** Derive one "can this account still authenticate under the
enabled flows" predicate — checking verified state, password presence and
provider availability — and apply it to every disconnect/removal path and to the
UI.

### A07 · Medium — WebSocket upgrade logs bypass URL redaction

**Evidence:** [create_app.js:513](../src/create_app.js#L513),
[create_app.js:526](../src/create_app.js#L526). Reproduced.

HTTP request logging runs the URL through `urlxxx`; the WebSocket accept and
reject logs use `JSON.stringify(req.url)` directly. A rejected upgrade to
`/realtime?token=PROBE_WS_SECRET_TOKEN&user=x` wrote the raw token into the
log. Upgrade query strings can carry upstream application credentials even
though Authwall authenticates the socket by cookie or bearer header.

**Remediation.** Apply `urlxxx` to every upgrade log line and encode extracted
fields such as `requested_user`.

### A08 · Medium — WebSockets do not refresh email-verification state

**Evidence:** [create_app.js:603](../src/create_app.js#L603)
(`authenticate_ws_session` reads `custom.email_verified_at`),
[email_verification_required.js:12](../src/helpers/email_verification_required.js#L12).
Reproduced.

HTTP authorization heals a stale unverified snapshot from the live database;
the WebSocket path checks only the session's stored snapshot. A probe verified
the account's email directly in the database, then attempted an upgrade on the
same still-"unverified" session and received `401`. The HTTP path would have
admitted it. The two admission paths disagree.

**Remediation.** Share one live verification decision across HTTP, sidecar, PAT
and WebSocket admission.

### A09 · Medium — Existing WebSockets survive session revocation

**Evidence:** [create_app.js:519](../src/create_app.js#L519), no live-socket
registry. Reproduced.

Authentication happens once at the upgrade. A probe opened a socket, deleted
every session row for the user, then sent a message on the still-open socket and
received the echo. New upgrades are rejected, but an established upstream
connection continues after the credential behind it is revoked.

**Remediation.** Define the intended revocation guarantee and either close the
associated sockets on session/token/account revocation or enforce a bounded
reauthorization interval. Drain upgraded sockets on shutdown as well.

### A10 · Medium — Expired rows and logs have no retention lifecycle

**Evidence:** [SessionStore.js:28](../src/helpers/SessionStore.js#L28),
[SessionStore.js:80](../src/helpers/SessionStore.js#L80),
[make_logger_daily.js:27](../src/services/logger/make_logger_daily.js#L27).
Source-confirmed.

Expired sessions are excluded from reads but never deleted; there is no
scheduled cleanup for used/expired token rows, auth-event retention, or old
daily logs. Authenticated sessions also rewrite `expires_at`/`last_seen_at` on
every request. Anonymous sessions have a 24-hour row lifetime but their rows are
still not reclaimed on expiry.

**Remediation.** Provide bounded batch cleanup with the right expiry indexes and
a documented retention policy; throttle session touches; separate security-event
retention from disposable session/token data.

### A11 · Medium — Email change holds a transaction across mail delivery

**Evidence:** [email_change.js:103](../src/routes/email_change.js#L103)
(`email_change_confirm_get`),
[complete_email_change_confirm.js:16](../src/actions/complete_email_change_confirm.js#L16).
Source-confirmed.

The confirm handler swaps identities and calls `complete_email_change_confirm`
— which `await`s mail delivery and issues the redirect — all inside the
`db.transaction` callback. A slow or failing provider prolongs the lock or rolls
back an otherwise valid change, and the response is being written before the
transaction returns.

**Remediation.** Commit the identity change and token consumption first, then
send the notification (ideally through a transactional outbox), then redirect.

### A12 · Medium — Direct example keeps a spoofable forwarded-IP default

**Evidence:** [docs/examples/authwall-direct/docker-compose.yaml](../docs/examples/authwall-direct/docker-compose.yaml)
publishes port 3000 and sets no `AUTHWALL_TRUST_PROXY`, so the default trusts
one hop. Source-confirmed.

A directly reachable instance that trusts one proxy hop lets a client supply the
`X-Forwarded-For` value used for per-IP throttles and audit attribution. The
security documentation warns about exactly this, but the runnable direct recipe
does not set `AUTHWALL_TRUST_PROXY=false`.

**Remediation.** Set the direct recipe to trust no proxy; keep proxy recipes at
an explicit hop count and test spoofed forwarded headers.

### A13 · Medium — Expensive authenticated operations lack abuse limits

**Evidence:** [password.js:377](../src/routes/password.js#L377) and
[profile.js:136](../src/routes/profile.js#L136) (both password-change paths run
bcrypt with no dedicated failure limiter),
[profile.js:105](../src/routes/profile.js#L105) (a 5 MB upload is decoded and
resized with no route-level concurrency or pixel bound beyond Sharp's default).
Source-confirmed.

**Remediation.** Throttle password failures per account and client, bound
concurrent image processing, and set an explicit pixel limit.

### A16 · Medium — Migration tooling diverges from runtime DB selection

**Evidence:** [package.json:22](../package.json#L22) (migration scripts hard-code
`--env=sqlite`), [bin/run_knex.js:4](../bin/run_knex.js#L4). Reproduced.

The npm `migrate`/`migrate:rollback` scripts always target the SQLite Knex
config at `data/db.sqlite3`, independent of the resolved `AUTHWALL_DB`. The
alternative helper `bin/run_knex.js` requires `../db/get_database_env`, which
does not exist, so it throws before doing anything:

```
Error: Cannot find module '../db/get_database_env'
```

**Remediation.** Wire one supported migration command to the same resolved
configuration as startup, print the selected non-secret target, and ship or
document the commands that actually work.

### A17 · Medium — Coverage reporting can hide failures and measures tests

**Evidence:** [package.json:29](../package.json#L29) — the `test:coverage`
script joins the unit run, the API run and `c8 report` with `;`, so the final
exit status is the report's even if a suite failed. The `c8.exclude` list omits
`**/*.test.js`, so colocated test bodies are measured as application code.
Source-confirmed.

**Remediation.** Preserve suite exit codes, exclude test files, define the
coverage source set explicitly, and add thresholds.

### A18 · Medium — Sentry span redaction is incomplete

**Evidence:** [sentry.js:69](../src/services/sentry.js#L69)
(`sanitize_sentry_event` visits only `request` and `breadcrumbs`). Reproduced.

A synthetic transaction with a token in `spans[].description` and
`spans[].data['url.full']` passed through the sanitizer with the token intact.
Span URL fields are a live sink for the one-time credentials Authwall carries in
query parameters whenever tracing is enabled.

**Remediation.** Sanitize the SDK's actual transaction and span URL fields, or
disable tracing until fields that cannot be reliably filtered are dropped.

### A19 · Medium — Runtime image validation is missing from CI

**Evidence:** [.github/workflows/trivy.yml:24](../.github/workflows/trivy.yml#L24)
scans the checkout as a root filesystem with `exit-code: 0`; the production
image is built only during deploy and is never scanned or smoke-tested in PR CI.
Source-confirmed.

**Remediation.** Build the runtime image in PR CI, smoke-test it as its
configured user with a writable data mount, and scan that image under a
deliberate severity policy.

## Lower-priority findings

### P2 · Low — Gmail plus-addressing evades the email denylist

**Evidence:** [normalize_email.js:19](../src/helpers/normalize/normalize_email.js#L19),
[authorize_email.js:10](../src/helpers/authorize_email.js#L10). Reproduced.

`normalize_email` collapses dots in `gmail.com`/`googlemail.com` addresses but
keeps `+tags`, and `authorize_email` compares the normalized string against the
configured lists. So `b.a.d@gmail.com` normalizes to `bad@gmail.com` and a
`denied_emails=bad@gmail.com` rule catches it, but `bad+x@gmail.com` normalizes
to itself and slips past — the same Gmail mailbox reaches the app. The mirror
image hurts allowlists: with `allowed_emails=foo@gmail.com`, the owner's
`foo+tag@gmail.com` is refused.

**Impact and limits.** Denylists are inherently best-effort, and an operator can
add the `+` variants, so this is a Low. It is worth recording because the dot
handling makes the rules look address-canonical when they are not.

**Remediation.** Either document that access rules match the address as
normalized (not the mailbox), or, for the dotless-domain set, also fold
`+tag` when deciding access.

### P3 · Low — Sign-up and email-add confirm whether an account exists

**Evidence:** [password.js:170](../src/routes/password.js#L170) ("Email already
exists" / "Username already exists"),
[email_add.js:63](../src/routes/email_add.js#L63) ("Email already registered").
Source-confirmed.

Registration and email-add return distinct errors when an identifier is already
taken, so an unauthenticated caller can enumerate registered emails and
usernames. This contrasts with the password-reset and magic-link flows, which
were deliberately built not to reveal existence.

**Impact and limits.** Low: registration is open by default, and enumeration is
a common accepted trade-off. It matters more when access rules are meant to keep
the user set private.

**Remediation.** Decide whether registration should be enumeration-resistant; if
so, return a neutral outcome and confirm existence only over a verified channel.

### A06 · Low — Session serialization drops cookie policy and lifetime metadata

**Evidence:** [SessionStore.js:57](../src/helpers/SessionStore.js#L57) (the
stored `custom` excludes `cookie`), [SessionStore.js:41](../src/helpers/SessionStore.js#L41)
(`get` reconstructs only `expires` and `maxAge`). Reproduced.

With `cookie.secure=true` and `cookie.domain=.authwall.test`, the stored session
row keeps no `secure`, `sameSite`, `domain`, `path` or `originalMaxAge`; `get`
rebuilds only expiry and max-age. The store violates express-session's
serialization contract. As the 5 September report noted, no replacement cookie
stripping `Secure` on the wire was demonstrated, so the wire impact stays
bounded; existing tests pass because they inspect only initial cookie issuance.

**Remediation.** Persist and restore the full cookie metadata, with a fallback
for existing rows, and add a test that reloads a stored session and asserts the
attributes.

## A note on the `return` parameter

`is_relative_url` accepts a value containing a raw control character such as a
tab, and `redirect` would honor it — a browser strips tab/newline/return from a
URL, so `"/\t/evil.com"` collapses to the protocol-relative `//evil.com`. End to
end this is **not** exploitable: Express percent-encodes the control character
when it writes the `Location` header, so the browser receives
`/%09//evil.com`, a same-origin path it does not collapse. This is recorded as a
hardening observation, not a finding: rejecting control characters in
`is_relative_url` would remove the latent trap if a future caller emits the
value without Express's encoding.

## Reproducibility

The twelve probes were written to a scratch file, run with
`npx mocha --no-package --config mocha.api.js --grep PROBE`, and removed; the
working tree is clean and no application source was changed. Representative
commands:

```sh
npm run test:unit          # 176 passing
npm run test:api           # 502 passing
node bin/run_knex.js --help # fails: Cannot find module '../db/get_database_env'
```

MySQL and PostgreSQL were not reachable in this environment, so the atomic-token
and revocation behaviors were confirmed on SQLite only; a cross-engine
concurrency run remains the stronger check for A04 and A09.
