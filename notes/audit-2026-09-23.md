Repository: `vbarbarosh/authwall` (branch `master`, HEAD `5a434ed`, clean tree).
An authentication proxy (Express 5, Knex; SQLite/MySQL/PostgreSQL). 492 tracked
files, 653 commits on `master`, first commit 2026-03-13, last 2026-09-19.

## Verdict

The core controls still hold. Session ids rotate at every authentication
boundary, and account routes need a session plus a CSRF token. One-time links
are stored hashed and consumed with a conditional update. Inbound identity
headers are stripped on both HTTP and WebSocket, and OAuth binds `state` to the
session and uses PKCE.

The main risk is that **the email access rules are weaker than the
documentation says**. They are the reason to put Authwall in front of an
internal app, and three independent gaps weaken them:

- With `AUTHWALL_CONFIRM_EMAIL_REQUIRED=false`, an address the visitor merely
  typed counts as proof of membership (AW-01). The documentation calls
  confirmation optional.
- Emailed six-digit codes have a cap per code but no cap across codes (AW-02).
  Under a domain allowlist, any address at the domain qualifies, including
  addresses nobody reads.
- Facebook's email is trusted with no verification signal (AW-05).

The second risk is **account recovery**. A credential minted before a reset
outlives the reset (H-01), and a session row deleted by revocation can be
written back (M-01). Both were only source-confirmed on 2026-09-19. Both are
now reproduced at the database level.

The third risk is **the sidecar recipes**. This audit was the first to run
them:

- The Caddy recipe does not parse (AW-16). With that fixed, H-02 reproduces.
- The nginx recipe reflects a decoded path into a response header (AW-15) and
  lets the client choose the address that throttles key on (AW-18).
- Both recipes forward the bearer token to the upstream (AW-17).

## 1. Access rules

### AW-01 Allowlist admits an unverified, self-typed address when confirmation is off (high)

`src/routes/password.js:168-173` authorizes the address typed into the sign-up
form with `authorize_email`, then stores it with `verified_at: null`
(`password.js:196`). Sign-in by email (`password.js:73-85`) authorizes the typed
address again and never looks at `verified_at`. The only thing that holds an
unverified account back is `email_verification_required`
(`src/helpers/email_verification_required.js:14`), and that returns `false`
when `confirm_email.required` is off.

Username sign-in was fixed for exactly this in A01: it counts only *verified*
addresses (`src/helpers/username_sign_in_refusal.js:22-24`). Email sign-in was
left out. The documentation reads as if the rules stand on their own:
`docs/security.md:116-126` describes the allowlist, and then says
"Optionally, `AUTHWALL_CONFIRM_EMAIL_REQUIRED` holds users at an
email-confirmation step".

Probe P1 used `allowed_domains=['corp.test']` and `confirm_email.required=false`.
It signed up an address it does not own and requested a protected path:

```
verified_at= null status= 200 x-auth-user= awuser_fezlqs2ibvfh4yb45hu07iak
```

The precondition is an operator setting, but the documentation presents that
setting as a normal one. Refuse to start when any allow rule is set and
confirmation is not required. Better still, make the allowlist check read only
verified addresses on every flow, as the username path already does.

### AW-02 Emailed one-time codes have no aggregate guess limit (high)

Each code is capped at `max_attempts` guesses in the database
(`src/helpers/spend_attempt.js:9-13`), which is correct for one code. Nothing
caps guesses across codes:

- Email-verify codes: `POST /auth/email-verify/request`
  (`src/routes/email_verify.js:25`) has no rate limiter. Its only brake is the
  per-address cooldown at `email_verify.js:60-61`
  (`resend_cooldown_seconds: 60`, `config/settings.yaml:64`). Each new code
  brings a fresh set of `max_attempts: 5` guesses (`settings.yaml:63`).
- Magic-link codes: `POST /auth/magic-link/confirm`
  (`src/routes/magic_link.js:31`) has no limiter. Requests are limited only per
  client address (`magic_link.js:25`) and per address cooldown (`:51`).

The cooldown is per address, so the budget grows with the number of addresses.
Under `AUTHWALL_ALLOWED_DOMAINS`, any address at the domain qualifies,
including addresses no one reads, so nobody sees the mail. A correct code
produces a verified identity at an allowed domain: `email_verify.js:163-170`,
or `magic_link.js:168-178` for a new account. That admits the holder past the
allowlist.

Evidence is source-confirmed; no guessing run was performed. Remediation:

- Add a limit per account and per target domain on code verification, across
  codes.
- Stop issuing codes for an address after N failed codes.
- Offer link-only mode (`AUTHWALL_CONFIRM_EMAIL=link`,
  `AUTHWALL_MAGIC_LINK=link`) as the default when access rules are set.

### AW-05 Facebook email is trusted as verified without a signal (medium)

`src/oauth_providers/oauth_provider_facebook.js:174` returns
`verified_emails: [user_info.email].filter(Boolean)`. The other adapters gate
on a provider signal: Google `email_verified` (`oauth_provider_google.js:203`),
GitHub `verified` (`oauth_provider_github.js:248`), Discord `verified`
(`oauth_provider_discord.js:128`), X `confirmed_email`
(`oauth_provider_twitter.js:64`) and Microsoft `xms_edov`
(`oauth_provider_microsoft.js:94`). The Facebook address is used for the
access-rule decision and stored with `verified_at`
(`src/helpers/make/make_oauth_flow.js:207-218`).

The 2026-09-05 audit set this aside as "a separate item"
(`notes/audit-2026-09-05.md:395`), but no later register carried it. Whether
Facebook ever returns an unconfirmed address was not established here. Either
way, the code takes it on trust. Treat the Facebook address as pending, as the
Microsoft fallback does, until Authwall's own confirmation verifies it. Or
document that Facebook must not be enabled together with access rules.

### AW-08 `denied_domains` misses a trailing-dot domain (low)

`src/helpers/authorize_email.js:19` compares the domain as an exact string.
`normalize_email` (`src/helpers/normalize/normalize_email.js:7`) accepts a
trailing dot, which is the fully qualified form of the same domain. Probe P5,
with `denied_domains=['evil.test']`:

```
evil.test -> Email domain is not allowed | evil.test. -> null
```

Allowlists fail closed, so only deny rules are affected. Deliverability through
the three providers was not tested. Strip one trailing dot, and convert IDN
domains to one form (punycode), in `normalize_email`.

## 2. Recovery, sessions and account changes

### H-01 Pending email-change link survives password reset and change (high)

Unchanged: `src/routes/password.js:326-336` deletes reset tokens and sessions
and revokes PATs, but leaves `email_change_tokens` alone.
`src/actions/complete_password_change.js:27-30` does the same for the profile
path. The confirm route needs only the token (`src/routes/email_change.js:103-155`).

Probe P2 created a pending change and then applied the same deletions the reset
transaction makes:

```
pending change tokens before= 1 after recovery-style cleanup= 1
```

Remediation is as in the 2026-09-19 audit: delete unused email-change tokens
(and email-verify tokens) inside the reset and password-change transactions.

### M-01 A late session save re-creates a revoked session row (medium)

`src/helpers/SessionStore.js:58-61` upserts with `onConflict('uid').merge(...)`.
Probe P3 wrote a session, deleted the row as revocation does, then called
`set` again:

```
row after delete+set: true
```

`error_handler` (`src/create_app.js:353-362`) saves the session on every failed
request. So the client that holds the session can itself trigger a late save;
it does not depend on server timing alone. The HTTP race itself was not run.
Make `set` insert only for a new session. For an existing one, use an update
that fails closed when the row is gone.

### AW-04 Credential-changing actions need no re-authentication (medium)

A session and a CSRF token are enough for every one of these:

- Requesting an email change. The link goes to the new address, and the old
  address is only told afterwards: `src/routes/email_change.js:34-100`,
  `src/actions/complete_email_change_confirm.js:16-27`.
- Setting a first password on an OAuth-only account: `src/routes/password.js:363-365`,
  `src/routes/profile.js:131-133`. The SPA does not show that a password now
  exists (M-13).
- Creating a PAT: `src/routes/personal_access_tokens.js:201-255`. PATs survive a
  profile password change (M-05).
- Removing the account after typing `DELETE`: `src/routes/account.js:197`.

A session obtained briefly, from an unattended device or a leaked cookie,
becomes a durable credential or a changed recovery address. OWASP ASVS 3.7.1
expects recent re-authentication before such changes. Require the current
password or a fresh OAuth or magic-link proof within a short window. For email
change, require confirmation from the old address as well.

### AW-06 Unverified email identities never expire and block the address owner (low)

Sign-up stores any typed address as a pending identity (`password.js:188-197`).
Nothing removes pending identities; M-10 covers tokens and sessions, not
identities. While the pending row exists, the real owner is turned away:

- Sign-up with that address: "Email already exists" (`password.js:169-171`).
- Magic-link sign-in: "registered but not yet verified" (`magic_link.js:200-202`).
- Adding the address to another account: "Email already registered"
  (`email_add.js:212-221`).

This is source-confirmed; the refusals themselves have regression stories.
Expire pending identities once the verification window has passed. Let a
successful magic link or OAuth proof of the address displace a pending row
that belongs to another account.

### AW-11 Magic-link GET signs in whoever opens it (low)

`GET /auth/magic-link/confirm?token=` (`src/routes/magic_link.js:73-122`) consumes the
token and replaces the visitor's session on the first request. A mail scanner
that prefetches links uses up the token, and the owner then sees "Invalid or
expired". A link handed to another person signs that person into the sender's
account (login CSRF). The email-verify and email-change GET routes behave the
same way (`email_verify.js:79-117`, `email_change.js:103-155`). Render a
confirmation page on GET and do the work on a POST carrying the session's CSRF
token.

## 3. Proxy and sidecar

### H-02 Sidecar trusts `X-Original-URI` ahead of `X-Forwarded-Uri` (high)

Unchanged: `src/routes/status.js:227`,
`docs/examples/authwall-sidecar-caddy/Caddyfile`. The Caddy recipe first had to
be made to parse (AW-16). After that, an anonymous request to a protected path
reached the upstream through Caddy 2.11.4. The nginx recipe overwrites the
header and was not affected. Details are in the 2026-09-19 audit and in
section 6.

### AW-03 Public-path canonicalization accepts `..;` and double-encoded dot segments (medium)

`src/helpers/canonical_path.js:302-308` rejects dot segments, backslashes and
double-encoded *separators* (`%2f`, `%5c`). It does not treat a `..;` segment as
a dot segment, and it does not reject double-encoded dots. Its own comment
(`canonical_path.js:1-8`) names Tomcat as an upstream it defends against, and
Tomcat and Jetty drop `;` path parameters before they resolve `..`. Probe P4:

```
["/lib/..;/admin","/lib/..;/admin"]
["/lib/%2e%2e;/admin","/lib/..;/admin"]
["/lib/%252e%252e/admin","/lib/%2e%2e/admin"]
["/lib/../admin",null]
["/lib/%2e%2e/admin",null]
```

A non-null result means "canonical", so a `/lib/*` public rule admits the path
with no identity header (`src/create_app.js:275`, `:398`). The sidecar makes
the same decision (`status.js:187`). Impact depends on the upstream; it was not
tested against Tomcat. Strip `;` parameters from every segment before the
normalize check, or reject any path containing `;` under a public or
optional-auth prefix. Reject `%25` followed by a hex pair, as `%2f` already is.

## 4. Abuse controls and enumeration

### AW-07 Throttles key on the full client address only (low)

`src/helpers/middleware/rate_limit_middleware.js:20` and
`make_failure_counter.js` key on `req.ip`. Consequences:

- One IPv6 host holds a /64 and can rotate addresses at no cost.
- The counters live in memory, so they reset on restart and are per process.
- No sign-in limit is keyed to the account being attacked
  (`password.js:38`).

Group IPv6 by /64 and add a per-account failure counter for sign-in. Document
that multi-instance deployments need a shared store.

### AW-10 Password-reset request timing reveals a verified address (low)

`src/routes/password.js:251-266` waits for `send_email` (a provider API call)
only when the address exists and is verified. Otherwise it returns at once
(`:270-282`), despite the comment "Never reveal whether email exists" at
`:268`. A provider error also surfaces only on the first path. This was not
timed against a real provider. Send the mail after the response, or through an
outbox, so both paths take the same time. L-02 already covers sign-up.

## 5. Email

### AW-09 Display names are not quoted per RFC 5322 in the recipient string (low)

`src/helpers/format/format_email_address.js:138-149` escapes `"` but not `\`.
It quotes the name only when it contains one of `" , < >`, not the other
RFC 5322 specials. The display name is user-controlled, up to 100 characters
(`src/routes/profile.js:88-93`), or comes from an OAuth provider. The result is
used as the `to` of password-reset, email-change and notification mail
(`src/helpers/send_email.js:25`):

- Mailjet (`make_mailer_mailjet.js:49`) and SES (`make_mailer_ses.js:131-180`)
  parse the string themselves and extract only the last angle-bracket address.
- Resend receives the raw string (`make_mailer_resend.js:11-16`), and its
  parsing was not tested.

Pass the address and the name as separate fields to every provider, instead of
building a header string. Or escape backslashes and quote every name that is
not a plain atom.

## 6. SPA and deployment recipes

The shipped sidecar recipes were run in containers: nginx 1.31.6 and
Caddy 2.11.4. Only hostnames and ports were changed, apart from the Caddy parse
fix in AW-16. They ran against a scratch copy of Authwall and a local echo
upstream. `spa.html` was read in full, and the server's `return` validation was
driven with 16 inputs.

### AW-15 nginx sidecar recipe writes the decoded path into a redirect header (medium)

`docs/examples/authwall-sidecar-nginx/nginx.conf:75` has
`return 302 /auth/sign-in?return=$uri;`, and `:80` does the same for
email-verify. `$uri` is the *decoded* path, so encoded line breaks in a
requested path turn into real line breaks in the 302. When this was run, a
signed-out request added a response header of the requester's choosing,
including a `Set-Cookie`. Caddy did not reproduce it. Use `$request_uri` and
percent-encode it, or pass the path through a `map` that allows only a safe
character set.

### AW-16 The Caddy sidecar recipe does not start (medium)

`docs/examples/authwall-sidecar-caddy/Caddyfile:25` and `:33` use
`redir /auth/sign-in?return=...`. Caddy reads a first argument that starts with
`/` as a path matcher, and `caddy adapt` fails with
"wrong argument count ... after 'redir'" on 2.6, 2.9 and 2.11.4. So the
recipe, and the security notes in its README (`:72-77`), have never been run.
The fix is `redir * /auth/...`. With that fix, H-02 was reproduced: an
anonymous request to a protected path, with the original-path header naming
`/favicon.ico`, reached the upstream. The nginx recipe overwrites the header
(`nginx.conf:65`) and was not affected.

### AW-17 Sidecar recipes forward the bearer token to the upstream (medium)

In proxy mode, Authwall deletes `Authorization` after it validates a PAT
(`src/create_app.js:472`). In sidecar mode, that delete only affects
Authwall's own copy of the auth subrequest. A valid PAT reached the echo
upstream unchanged, next to `X-Auth-User`, in both recipes. That contradicts
`docs/security.md:18-21` ("strips the bearer credential"). Clear the header in
the recipes (Caddy `request_header -Authorization`, nginx
`proxy_set_header Authorization ""` on the protected location), or document
the behaviour.

### AW-18 nginx sidecar auth check forwards the client's `X-Forwarded-For` (medium)

The `location = /_auth` block (`nginx.conf:59-69`) does not set
`X-Forwarded-For`, and `trust proxy` defaults to 1
(`src/helpers/parse/parse_trust_proxy.js:9`). So the client picks the address
that Authwall keys the bearer failure limiter on and records as `last_used_ip`.

- Twenty-two bad PATs with one fixed forwarded address tripped the limiter on
  requests 21 and 22.
- The same 22 with a different address each time never tripped it.
- A valid PAT recorded the address the client supplied.

Caddy overwrote the header. Add `proxy_set_header X-Forwarded-For $remote_addr;`
to `/_auth`. This is the sidecar form of M-08.

### AW-19 Protected apps share the Authwall origin and receive its session cookie (medium)

`/auth/*` is served on the protected app's own origin in every mode. The SPA
reads its CSRF token from same-origin `GET /auth/status`
(`design/public_html/spa.html:1193-1197`, `src/routes/status.js:95`, `:131`).
Script running in any app page can therefore act on the Authwall account:
change the email (see H-01), create PATs, revoke sessions. `HttpOnly` and the
`/auth` CSP do not apply to app pages.

Separately, `connect.sid` is forwarded to the upstream. The echo upstream
replayed it to `/auth/status` and received `authenticated: true` with a valid
`csrf_token`. July audits reported the cookie forwarding (07-10 L4, 07-27 L7),
but it dropped out of the September registers. `AUTHWALL_UNSET_HEADERS` does
not apply in sidecar mode. Remove Authwall's cookie from forwarded requests by
default, and require re-authentication for account changes (AW-04). Document a
separate auth origin as the stronger deployment.

### AW-20 Direct mode forwards client `X-Forwarded-*` and `X-Real-IP` unchanged (low)

`src/create_app.js:256` sets `xfwd` only in proxy mode. In direct mode, the
upstream received client-supplied `x-forwarded-for`, `x-real-ip` and
`x-forwarded-host` exactly as sent. Apps that build links or IP rules from
them get forged values. Remove these headers in direct mode, or set them from
`req.ip` and `config.public_url`.

### AW-21 A new PAT secret stays in the page after navigation (low)

`spa.html:1173` clears `#pat-token` and `#pat-curl` only when the view is
opened through `showView`. The Back/Forward handler (`:1179-1184`) calls
`renderView` only. Going back to the tokens view after leaving it shows the
full secret again, despite the "will not be shown again" text at `:911`. Clear
both elements on every view change.

### SPA: what held and what is noted

- **What held.**
  - Every server value that reaches `innerHTML` goes through `escape_html`.
  - Error text uses `textContent`.
  - The page loads no external script, style or font.
  - Nothing is kept in `localStorage`, `sessionStorage` or `document.cookie`.
  - Every state-changing POST carries the CSRF token.
  - `/auth` pages cannot be framed.
- **Redirect table.** The 16-input table found no input that leaves the site.
  `//`, backslash, `%2f`, `javascript:` and user-info forms are rejected;
  subdomains are accepted by design.
- **CSP.** `script-src 'unsafe-inline'` and `img-src https:`

## What is good

- Session ids and CSRF tokens rotate on sign-in, sign-up and password change
  (`src/helpers/replace_session.js`). CSRF comparison is constant-time and
  rejects non-strings (`src/helpers/crypto_equal.js`).
- One-time tokens are 256-bit (`random_hex(32)`), stored as SHA-256 hashes, and
  consumed by conditional update. Guess counters are updated by the database.
- Password sign-in runs bcrypt against a dummy hash for unknown users.
- Inbound `x-auth-*` and `x_auth_*` headers are stripped on HTTP and WebSocket,
  and bearer tokens are removed before forwarding.
- Public-path matching rejects `..`, encoded separators, backslashes, NUL and
  duplicate slashes (AW-03 is the gap in that list).
- OAuth: state is bound to the session, PKCE S256 is used, identities are keyed
  by provider subject, and Microsoft email trust is gated on `xms_edov`.
- Emails are plain text, and `normalize_email` refuses markup, quotes and
  separators.
- The runtime image runs as a non-root user and copies an explicit file list.
  No live secret appears in the tree or in history.
- The API suite is broad (517 cases), quick (about 11 s) and isolated per
  process.
