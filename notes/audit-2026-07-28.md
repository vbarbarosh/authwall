# Authwall project audit

Date: 2026-07-28
Scope: repository at `/app`, version `1.14.0`, commit `dcda42f` (branch `master`)
Method: full source read + empirical reproduction against the project's own test harness, plus
independent re-verification of every finding carried over from `audit-2026-07-27.md`

## TLDR

The thirteen commits since yesterday's audit did real work: five of the six High findings from
`audit-2026-07-27.md` are fixed (H6, the provider-email policy call, was not attempted), the
production dependency tree is clean, and the sidecar authorization bypass is closed with a test that
pins proxy/sidecar parity. That progress is genuine and it holds up under re-verification.

What this audit found is that the same *classes* of defect are still open one layer down. Tokens no
longer reach the logs through `req.url` — they reach them through the `Referer` header instead.
Email verification is enforced everywhere it should be, but from a stale snapshot rather than the
database. Configuration is validated by name and then silently clamped by value.

The one thing that must be fixed today is a regression: the redaction helper added yesterday throws
on request targets Express accepts, including from inside the error handler's own catch block. One
unauthenticated request now kills the process.

Verdict: **materially safer than yesterday in every respect except availability, where it is
strictly worse.** One Critical and five High findings, all new, all reproduced.

- 🚨 **`GET //[` crashes the whole proxy** — unauthenticated, one request, no account needed, and
  every app behind Authwall goes down with it. Introduced by yesterday's log-redaction fix.
  *(Reproduced)*
- 🔴 `AUTHWALL_COOKIE_SECURE=` (empty, as `.env.example` writes nine other vars) **turns off** the
  `Secure` cookie flag on an HTTPS deployment. *(Reproduced)*
- 🔴 Password-reset tokens still land in the logs — via the `Referer` header, a sink yesterday's
  redaction fix does not cover. *(Reproduced)*
- 🔴 Email verification is read from a sign-in snapshot: verify on your phone and your desktop
  session is locked out permanently; delete your verified email and every live session keeps
  access. *(Both directions reproduced)*
- 🔴 `AUTHWALL_BCRYPT_ROUNDS=1` silently yields cost **4**, not a startup error — while
  `docs/config.md` promises "Authwall refuses to start." *(Reproduced)*
- 🔴 **GitHub sign-in fails for every user whose primary email is private** — the shape assertion on
  `/user/emails` accepts only `null` and `"public"`, and GitHub sends `"private"`. *(Reproduced)*
- 🟠 Sidecar mode ignores `public_paths` and `optional_auth_paths` entirely, and the new 403 is a
  dead end in both shipped example configs. *(Reproduced)*
- 🟠 A malformed `AUTHWALL_SEED` writes the seed **password in cleartext** to the log. *(Reproduced)*
- 🟠 Every proxied request costs a session `UPDATE` — a database write per asset, on a default
  backend running without WAL. *(Reproduced)*
- 🟠 No CSP and no `X-Frame-Options` anywhere in the repo; every `/auth/*` page is framable.
- 🟠 Rate limiting — a documented security control — has **zero** integration coverage.

## Critical severity

### N31. One malformed unauthenticated request crashes the entire proxy

**Description.** `urlxxx()` — the redaction helper introduced yesterday to fix H3 — parses the URL
with `urlparts()`, which is `new URL(url, 'fake://fake/')`. That throws on request targets Node and
Express accept perfectly well: `//[`, `//]`, `//a:b/`, `//[::1/x`.

There are three call sites and none is guarded (`src/create_app.js:67`, `:305-306`, `:311`). The
third is the decisive one — it is inside the `catch` block of `error_handler`, the last-resort handler
that exists specifically so logging cannot take the process down:

```js
catch (error2) {
    als.logger.write(`[error_handler] ⚠️ … url=${urlxxx(req.url)} …`);   // ← throws again, from the catch
}
```

`error_handler` is `async`, so the throw becomes an unhandled rejection, which Node terminates on by
default.

**Impact.** Any unauthenticated client that can open a TCP connection can kill Authwall with one
request — no session, no account, no valid route required. Because Authwall is the trust boundary,
every application behind it goes down with it. Under `restart: unless-stopped` the attacker simply
repeats, and a restart loop is indistinguishable from an outage. The previous audit rated a *logger
filesystem error* crashing the proxy as High (H4); this is the same outcome reachable remotely and on
demand.

This is a regression: commit `5825161` lifted the redaction predicate out of `sentry.js` but left
behind the `try/catch` that the original `sanitize_url` had around its `new URL()` call.

**Severity:** Critical — unauthenticated, remotely triggered, total loss of availability for the
proxy and everything it fronts.

**Location:** `src/helpers/urlxxx.js:23`; call sites `src/create_app.js:67`, `:305-306`, `:311`;
`@vbarbarosh/node-helpers/src/urlparts.js:5`.

**Verification (reproduced)** against a real `create_app()` instance:

```
$ printf 'GET //[ HTTP/1.1\r\nHost: a\r\n\r\n' | nc <host> <port>

TypeError: Invalid URL
    at new URL (node:internal/url:819:25)
    at urlparts (/app/node_modules/@vbarbarosh/node-helpers/src/urlparts.js:5:11)
    at urlxxx (/app/src/helpers/urlxxx.js:23:49)
    at error_handler (/app/src/create_app.js:311:96)      ← the catch block
    …
  code: 'ERR_INVALID_URL', input: '//[', base: 'fake://fake/'

node exit code: 1
```

Confirmed separately that a plain Node HTTP server accepts that request target and reports
`req.url === "//["`, so nothing upstream of Express filters it. With `urlxxx` stubbed to the identity
function — pre-fix behaviour — the same request returns `302` and the process survives.

**Expected:** an unparseable request target is logged as-is (or as a placeholder) and the request is
answered.
**Actual:** the process exits.

**Remediation.** Make `urlxxx` total — it is a log-sanitizing helper, and such a helper must never
throw:

```js
function urlxxx(url)
{
    if (typeof url !== 'string' || !url) {
        return url;
    }
    try {
        // …existing body…
    }
    catch (error) {
        return '[Unparseable URL]';
    }
}
```

Returning a placeholder rather than the raw string matters: the fallback must not become a way to get
an unredacted URL into the log by making it unparseable. Add unit tests for `//[`, `//]`, `//a:b/`,
and an empty target. Separately, `error_handler`'s catch block should not call anything that can
throw, and it is worth wrapping the whole handler so that no future logging change can repeat this.

## High severity

### N1. `AUTHWALL_COOKIE_SECURE=` (empty) disables the Secure flag on an HTTPS deployment

**Description.** `cookie.secure` defaults to `public_url.startsWith('https://')`
(`config/make_config.js:168`), but `src/helpers/resolve_yaml_vars.js:15` treats a variable as unset
only when the key is *absent*. An environment variable set to the empty string resolves to `''` and
overrides the computed default.

**Impact.** The session cookie ships without `Secure`, so any plaintext request to the host — a
hardcoded `http://` link, an HSTS-less first visit, an attacker forcing a downgrade — discloses a
live session id. Two related protections switch off with it: the forced `x-forwarded-proto: https`
shim (`src/create_app.js:85-90`) and `express_session`'s `proxy` option (`:99`). Nothing warns.

The trigger is not exotic. `.env.example` writes nine other variables as bare `NAME=`, so an operator
copying that style to "leave the default" gets the opposite of the default. `docs/deployment.md:156`
and `docs/config.md:556` both promise the HTTPS-derived value.

**Severity:** High — silent loss of transport protection on the session credential.

**Location:** `config/make_config.js:168`; `src/helpers/resolve_yaml_vars.js:15`.

**Verification (reproduced).** With `AUTHWALL_PUBLIC_URL=https://app.example.com`:

```
baseline (https)                -> cookie.secure=true
AUTHWALL_COOKIE_SECURE=""       -> cookie.secure=false
```

**Expected:** an empty value means "unset", leaving the HTTPS-derived default in place — or a
startup error.
**Actual:** the flag is disabled with no diagnostic.

**Remediation.** In `resolve_yaml_vars`, treat `''` as unset when the whole value is a single
`${VAR}` placeholder. That fixes this class everywhere at once rather than only for this variable.
Then add a startup check that refuses to run with `public_url` on `https://` and `cookie.secure`
false, since that combination is never intentional.

### N2. Password-reset tokens still reach the logs — through the `Referer` header

**Description.** Yesterday's H3 fix routes `req.url` through `urlxxx()` at all three URL sinks, and
that part works. But `[req_begin]` also logs a set of request headers verbatim
(`src/create_app.js:66-67`), and `LOGGED_HEADERS` includes `referer` (`:42`).

Three of the four token-bearing URLs are GET routes that redirect, so they never become a document.
`/auth/password-reset/confirm` is the exception: it has only a POST route, so the GET falls through
to the `config.pages` handler (`src/create_app.js:194-214`) and **renders the SPA**. The user sits on
that page with the token in the address bar, and every same-origin request the SPA makes from it —
starting with `GET /auth/status` — carries the full URL as `Referer` under the default referrer
policy.

**Impact.** A password-reset token in a log file is a complete account takeover for whoever can read
it, which is exactly the threat model H3 was written to close. The fix reduced the exposure from
"every token type" to "the one token type that grants password control", and the remaining path is
on the normal, non-error flow rather than an edge case.

**Severity:** High — credential disclosure to a lower-trust store.

**Location:** `src/create_app.js:42` (`LOGGED_HEADERS`), `:66-67` (the write);
`config/make_config.js:102` (the page that renders with the token).

**Verification (reproduced).**

```
GET reset page          : 200 text/html          ← renders as a document
log lines with the token: 1
  [req_begin] GET "/auth/status" ... {"referer":"http://127.0.0.1:40261/auth/password-reset/confirm?token=de…
```

**Expected:** no sink writes a live credential to disk.
**Actual:** the reset token is logged verbatim on the request immediately following the click.

**Remediation.** Two changes, both small, and do both:

1. Run the header through the same helper before serializing: `headers.referer = urlxxx(headers.referer)`.
   Apply it to any header added to `LOGGED_HEADERS` in future — the allow-list is the right shape,
   it just needs the value filtered too.
2. Send `Referrer-Policy: same-origin` (or `no-referrer`) on `/auth/*` responses, so the token does
   not leave the browser on outbound requests either. The current absence means a third-party
   resource loaded from that page would receive the token as well.

Consider also having the reset page strip the token from the address bar via `history.replaceState`
after reading it, which removes it from browser history and from any screenshot or screen-share.

### N3. Email verification is a sign-in snapshot, not live state

**Description.** `email_verification_required()` reads `req.session.email_verified_at`
(`src/helpers/email_verification_required.js:5`). That field is written in exactly one place —
`replace_session()` at sign-in (`src/helpers/replace_session.js:16-20`) — and refreshed in exactly
one other, when the *same* session confirms the email (`src/actions/complete_email_verify_confirm.js:15`).

Every session-authenticated gate consumes that snapshot: the proxy (`src/create_app.js:375`), the
sidecar (`src/routes/status.js:191`), `auth_middleware` (`:23`), and the WebSocket upgrade
(`src/create_app.js:581`). The PAT path is the odd one out — it queries `user_identities` live
(`src/helpers/authenticate_personal_access_token.js:33-41`).

The snapshot goes stale in both directions.

**Impact, direction 1 — lockout.** Sign up on a desktop, open the confirmation email on a phone.
The identity is verified in the database, but the desktop session's snapshot still says `null`, so
that browser is redirected to the verification page on every request — permanently. The page cannot
help: "resend" calls `email_verify_request_post`, which looks for an *unverified* identity, finds
none, and returns `No unverified email found`. The user is in a closed loop with no in-app exit; the
only escape is to sign out and sign in again, which nothing tells them to do. Desktop-signup /
phone-email is one of the most common paths in the product.

**Impact, direction 2 — fail-open.** `POST /auth/email/remove` deletes the verified email identity
(permitted whenever the user holds any second identity) and never touches live sessions. The account
now has no verified email, yet every live session keeps full access through both the proxy and the
sidecar — while a PAT belonging to the same user is correctly refused, because that path checks the
database. Two authentication methods for one account disagree about whether it is authorized.

**Severity:** High — a lockout with no user-visible recovery on a mainstream flow, plus a stale-state
authorization gap in the control `AUTHWALL_CONFIRM_EMAIL_REQUIRED` exists to enforce.

**Location:** `src/helpers/email_verification_required.js:5`; `src/helpers/replace_session.js:16-20`;
`src/actions/complete_email_verify_confirm.js:15`; `src/routes/email_remove.js:45`.

**Verification (reproduced).** Direction 1 — verify from a second client:

```
desktop before verify   : 302 /auth/email-verify?return=%2Fprotected%2Fpage
db verified_at          : SET
desktop session         : email_verified_at=null
desktop after verify    : 302 /auth/email-verify?return=%2Fprotected%2Fpage
desktop sidecar         : 403
desktop /auth/status err: "Email verification required"
resend attempt error    : "No unverified email found"
```

Direction 2 — remove the verified email with `confirm_email.required = true`:

```
proxy before email removal : 200
email identities remaining : 0
proxy after email removal  : 200
sidecar after removal      : 200      ← plus X-Auth-User
```

**Expected:** the gate reflects the account's current verification state.
**Actual:** it reflects the state at the moment of sign-in, and drifts both ways.

**Why the suite misses it.** `tests/api/stories/email_verify_cross_session.test.js` covers precisely
this scenario and asserts the *safe* half — that Alice's session is unchanged when she opens Bob's
link. It never checks what happened to Bob's own session, which is where the defect is.

**Remediation.** Resolve verification from the database on the gate path rather than caching it in
the session, matching what the PAT path already does. If a per-request query is unacceptable, keep
the snapshot but give it a short TTL and re-read on miss. Whichever route you take, the four gates
should call one function — see the cross-cutting note below.

As an immediate mitigation, independent of the redesign: have `email_verify_request_post` detect
"the identity is already verified but this session does not know it", refresh the session, and
redirect onward instead of erroring. That converts a permanent lockout into a self-healing click.
Add the missing assertion to the cross-session test.

### N4. Integer config options are silently clamped — `AUTHWALL_BCRYPT_ROUNDS=1` becomes cost 4

**Description.** `docs/config.md:150` states: *"If either value is out of range, Authwall refuses to
start."* It does not. Integer options go through `safe_int`, which clamps
(`Math.max(min, Math.min(max, tmp||0))`) and never throws.

**Impact.** bcrypt at cost 4 is roughly 256× cheaper to attack than the documented default of 12,
and it is applied to every password hash and every magic-link code hash written from then on. An
operator who sets `AUTHWALL_BCRYPT_ROUNDS=1` on a slow box — or who writes `AUTHWALL_BCRYPT_ROUNDS=`
as an empty placeholder — gets the weakest possible cost with no warning, while the documentation
tells them such a value is impossible. `AUTHWALL_PASSWORD_MIN=` likewise silently yields a 4-character
minimum against a documented 8.

The inconsistency is sharpest inside one file: `make_config.js:415-426` hard-fails on an unrecognized
`AUTHWALL_*` **name**, so the same config layer is strict about spelling and silent about values.

**Severity:** High — a documented cryptographic control degrades silently to its weakest setting.

**Location:** `config/make_config.js:162` (bcrypt_rounds), `:177` (min_password_length), `:123-126`
(confirm_email integers); clamping in `@vbarbarosh/type-helpers/src/safe_int.js:25`.

**Verification (reproduced).**

```
AUTHWALL_BCRYPT_ROUNDS=1     -> bcrypt_rounds=4
AUTHWALL_BCRYPT_ROUNDS=""    -> bcrypt_rounds=4
AUTHWALL_BCRYPT_ROUNDS=abc   -> bcrypt_rounds=12    ← non-numeric falls back, out-of-range clamps
AUTHWALL_PASSWORD_MIN=""     -> min_password_length=4
```

**Expected:** an out-of-range value is a startup error, as documented.
**Actual:** it is clamped to the boundary; a non-numeric value falls back to the default. Two
different silent behaviours for two kinds of bad input.

**Remediation.** Make out-of-range and non-numeric values throw at config load, and fold the boolean
(prior M3) and enum (N13) cases into the same rule so one convention covers every option. The
existing unknown-name check is the model to follow. Note that `mocha.api.js:23` pins
`AUTHWALL_BCRYPT_ROUNDS='4'`, so the suite cannot surface this — the test for it has to sit at the
config layer.

### N27. GitHub sign-in fails for every user whose primary email is private

**Description.** `oauth_provider_github.fetch_user_info` validates the live `/user/emails` response
against a fixed shape:

```js
visibility: assert_shape.enum(null, 'public'),
```

GitHub returns `visibility: "private"` for the primary address whenever the account has "Keep my
email addresses private" enabled — a setting GitHub turns on for accounts created through the normal
signup flow, and one that a large share of users have. `assert_shape` throws an `AssertionError`,
which is not a `UserFriendlyError`, so `error_handler` replaces it with `An error occurred [req_…]`.

**Impact.** GitHub sign-in is unavailable — not degraded, unavailable — for those users, on both
sign-up and sign-in, with an opaque error and a real exception raised into Sentry on every attempt.
This is the second consecutive audit to find GitHub sign-in broken by a fixture that encodes a
payload GitHub does not send; yesterday's H2 was the numeric `sub`.

There is a second, wider failure in the same call: `assert_shape` requires **exact key equality**, so
the day GitHub adds a field to `/user/emails` — an additive, non-breaking change by their own API
contract — every GitHub sign-in starts failing. A validator that hard-fails on unknown keys is a
liability when it is pointed at someone else's evolving API.

**Severity:** High — a headline sign-in flow is broken for a large user population, and is one
upstream field addition away from breaking for everyone.

**Location:** `src/oauth_providers/oauth_provider_github.js:59-64`; `src/helpers/assert/assert_shape.js:52`
(exact-key check).

**Verification (reproduced)** against the real module:

```
visibility="public"  -> OK
visibility=null      -> OK
visibility="private" -> THROWS: Value "private" not in enum [null,"public"]   (AssertionError)
```

**Why the suite misses it.** Every fixture avoids the value: `tests/mock_github.js:25,31,37` and
`tests/api/stories/github_no_email.test.js:31` all send `'public'` or `null`. The mock was written
from the code, not from the API.

**Expected:** every documented value of `visibility` is accepted.
**Actual:** the documented and most common value throws.

**Remediation.** Accept `'private'` (the full documented set is `null`, `'public'`, `'private'`), and
make the shape check tolerant of unknown keys — validate the fields you consume and ignore the rest.
Then decide deliberately whether a shape mismatch on a provider response should be fatal at all: a
`UserFriendlyError` with a clear message is better than a generic one, and degrading gracefully is
better than either. Add fixtures covering `private`, plus one with an extra unknown field.

## Medium severity

### N5. Sidecar mode ignores `public_paths` and `optional_auth_paths`

**Description.** `sidecar_get` (`src/routes/status.js:170-198`) resolves the caller's identity and
never looks at which path was requested. It cannot: the requested path arrives in a header
(`X-Original-URI` from the nginx example, `X-Forwarded-Uri` from Caddy's `forward_auth`) and the
handler reads neither.

**Impact.** Both features silently do nothing in sidecar mode. A configured public path returns 401
to anonymous users, so the reverse proxy sends them to sign-in for content meant to be open — a
health endpoint, a marketing page, a webhook receiver. `docs/config.md:391-392` documents both
features without qualification, and `docs/security.md` does not mention sidecar mode at all. The
failure is closed rather than open, which is the right direction, but the behaviour contradicts the
documentation and differs from the proxy path for the same configuration.

**Severity:** Medium — a documented feature is inoperative in a first-class topology.

**Location:** `src/routes/status.js:170-198`; `docs/examples/authwall-sidecar-nginx/nginx.conf`
(sends `X-Original-URI`); `docs/examples/authwall-sidecar-caddy/Caddyfile`.

**Verification (reproduced).** With `config.public_paths = ['/pub/*']` and no session:

```
anonymous GET /pub/thing   (proxy)  : 200
anonymous GET /auth/sidecar         : 401
```

**Expected:** the sidecar answers for the path the proxy is asking about.
**Actual:** it answers a path-independent question.

**Remediation.** Read the original path from `X-Original-URI` / `X-Forwarded-Uri` (documenting which
headers must be forwarded), and apply `is_public_path` / `is_optional_auth_path` before the identity
check. Ship the required `proxy_set_header` lines in the nginx example — Caddy sends
`X-Forwarded-Uri` by default. Until that lands, say plainly in `docs/config.md` that both settings
are proxy-mode only.

### N6. The new sidecar 403 is a dead end in both shipped example configs

**Description.** Yesterday's H1 fix makes `/auth/sidecar` return **403** for a signed-in user whose
email is unverified. Neither example config handles that status.
`docs/examples/authwall-sidecar-nginx/nginx.conf` maps only `error_page 401 = @authwall_signin`;
`docs/examples/authwall-sidecar-caddy/Caddyfile` matches only `@unauthorized status 401`. nginx's
`auth_request` passes a 403 straight through to the client, and Caddy's `forward_auth` copies the
unhandled response.

**Impact.** In the exact deployment the fix was written for, the user gets a bare `403 Forbidden`
with an empty body and no link to the verification page. In proxy mode the same user is redirected
to `/auth/email-verify`. The security hole is closed and replaced with an unexplained wall — and
because the response body is empty, there is nothing on screen to search for.

**Severity:** Medium — correct enforcement, unusable presentation, in the documented topology.

**Location:** `docs/examples/authwall-sidecar-nginx/nginx.conf` (the `error_page` line);
`docs/examples/authwall-sidecar-caddy/Caddyfile` (the `@unauthorized` matcher).

**Verification.** Read both configs against `src/routes/status.js:191-194` and the documented
`auth_request` / `forward_auth` semantics for non-2xx auth responses.

**Expected:** an unverified user is sent to the verification page in every topology.
**Actual:** proxy mode redirects; both sidecar examples show a bare 403.

**Remediation.** Add a 403 branch to both examples pointing at `config.pages.email_verify_request`:
`error_page 403 = @authwall_verify;` for nginx and a second `handle_response` matcher for Caddy.
This is the kind of gap that a fix landing without its examples always leaves — worth adding a line
to `docs/deployment.md` noting that the sidecar endpoint answers 401 *and* 403, and what each means.

### N7. A malformed `AUTHWALL_SEED` writes the seed password to the log in cleartext

**Description.** `bootstrap_users` rejects a seed entry with no usable username and no valid email,
and logs the rejected entry in full:

```js

```

`user_seed.password` is the plaintext password (`src/helpers/parse/parse_authwall_seed.js:30-37`).

**Impact.** Seed users are administrative accounts, and the log is a lower-trust store (prior H3 is

**Severity:** Medium — administrative credential written to disk; needs a misconfiguration, but the
misconfiguration is quiet and the log line is the only evidence of it.

**Location:** `src/helpers/bootstrap_users.js:25`; `src/helpers/parse/parse_authwall_seed.js:19-37`.

**Verification (reproduced).**

**Actual:** the password is printed verbatim.

**Remediation.** Log the identifying fields only — `username`, `display_name`, the email list — and

### N8. Every proxied request costs a session write

**Description.** `express-session` calls `store.touch()` whenever a request carries a valid session
cookie and nothing about the session changed (`shouldTouch` → `cookieId === req.sessionID &&
!shouldSave(req)`), and `SessionStore.touch` issues an `UPDATE`
(`src/helpers/SessionStore.js:75-87`). The session middleware is mounted globally
(`src/create_app.js:92`), so this applies to proxied upstream traffic, not just `/auth/*`.

**Impact.** Every request a signed-in browser makes through Authwall — each script, stylesheet,
image, XHR — costs one indexed `SELECT` plus one `UPDATE` on `sessions`. On the default backend the
aggravating factors compound: SQLite runs in `journal_mode=delete` (no WAL is configured anywhere),
and knex holds a single connection, so each of those writes takes an exclusive database lock. A page
with 40 subresources takes 40 write locks. Reads from elsewhere — `bin/activity-summary` while the
server runs — serialize behind them.

The `SELECT` is fine: `sessions.uid` is unique-indexed (`db/migrations/20260313201917_sessions.js:26`).
The write is the cost, and it buys only a `last_seen_at` refresh.

**Severity:** Medium — throughput ceiling on the hot path of a component every request passes through.

**Location:** `src/helpers/SessionStore.js:75-87`; `src/create_app.js:92`; `knexfile.js:11-28`
(no `pool`, no pragma).

**Verification (reproduced).** Queries for one proxied request by a signed-in client:

```
queries for ONE proxied request: 2
  select * from `sessions` where `uid` = ? and `expires_at` > ? limit ?
  update `sessions` set `expires_at` = ?, `last_seen_at` = ? where `uid` = ?
```

**Expected:** a read on the hot path; writes only when something changed.
**Actual:** a write per request.

**Remediation.** Throttle the touch the way the PAT path already throttles its own — skip the
`UPDATE` when `last_seen_at` is within a few minutes (`authenticate_personal_access_token.js:53-58`
is the pattern, and it is right there in the codebase). Enable WAL and set a `busy_timeout` in the
SQLite branch of `knexfile.js` regardless; both are one-line `afterCreate` pragmas and help every
concurrent-access path.

### N15. Recipient injection: a trailing comma bypasses the email denylist and fans out on SES

**Description.** Nothing validates email syntax at runtime. `normalize_email` only trims and
lowercases, and the routes reject only falsy values (prior M12 predicted this; here is the exploit).
Two consequences compose:

- `authorize_email` derives the domain with `email_normalized.split('@')[1]`
  (`src/helpers/authorize_email.js:6`), so `evil@denied.com,` yields the domain `"denied.com,"`,
  which matches no denylist entry.
- `make_mailer_ses.js:51-93` explicitly splits the recipient string on commas.

**Impact.** Access rules are evaluated against a string that the mailer later interprets as a list.
A denied address passes the check and is still delivered to. A value like
`victim@example.com, attacker@evil.com` produces two SES recipients from one request. The magic-link
route reaches this **unauthenticated** (`src/routes/magic_link.js:36-67` forwards `req.body.email`
straight through). Mailjet fails closed; Resend's behaviour is unverified.

This is not account takeover — the magic-link token is keyed to the whole normalized string, so the
extra recipient cannot sign in as anyone. It is an access-policy bypass and an outbound-mail abuse
primitive using the deployment's own SPF/DKIM.

**Severity:** Medium — bypasses a configured access control and enables mail abuse.

**Location:** `src/helpers/normalize/normalize_email.js`; `src/helpers/authorize_email.js:6`;
`src/services/mailer/make_mailer_ses.js:51-93`; entry point `src/routes/magic_link.js:36-67`.

**Verification (reproduced).**

```

domain seen by authorize_email      = "denied.com,"
denylist ["denied.com"] includes it? false
SES ToAddresses                     = ["evil@denied.com"]      ← delivered
"victim@example.com, attacker@evil.com" -> ["victim@example.com","attacker@evil.com"]
```

**Expected:** an address containing a comma is rejected as malformed.
**Actual:** it passes the access rules and expands into multiple recipients.

**Remediation.** Fix prior M12 — have `normalize_email` return `null` unless the value is a single
well-formed address (exactly one `@`, no commas, no whitespace, non-empty on both sides), reusing the
shape check `make_config` already applies to `normalize_access_email` so config-time and runtime
validation agree. Then, defensively, reject any recipient containing a comma at the mailer boundary.

and then exits **1**. Under `restart: unless-stopped` (as `docker-compose.yaml:5` sets) that reads as
a crash rather than a clean stop. Ten seconds is also Docker's default stop grace period, so SIGKILL
and the timer race — and when SIGKILL wins, the `await using` disposers in `src/index.js:44-46` never
run, so the database pool and the log stream are not flushed.

**Severity:** Medium — every deploy of a WebSocket-enabled instance looks like a failure and may lose
buffered log output. Default-off, so it affects only deployments that opted in.

**Location:** `src/helpers/express/express_run.js:26-36`; `src/index.js:44-46`.

**Verification (reproduced).** A minimal server holding one upgraded socket, with the same shutdown
logic:

```
[SIGTERM] calling server.close()
[timeout] process.exit(1)
[exit] code=1
```

The same script with an idle keep-alive connection instead exits 0 immediately — modern Node closes
idle HTTP connections, so WebSockets are the specific trigger.

**Expected:** SIGTERM closes connections and exits 0.
**Actual:** ten-second hang, exit 1, disposers skipped.

**Remediation.** Track upgraded sockets and destroy them on shutdown (or call
`server.closeAllConnections()` after a short drain), and exit 0 on the timeout path — a forced
shutdown after a grace period is the expected outcome, not an error.

### N28. Discord and Twitter pre-stringify the subject, defeating the new `oauth_sub` guard

**Description.** Yesterday's H2 fix added `oauth_sub()` (`make_oauth_flow.js:243-255`), which rejects
a subject that is missing or empty. Two providers stringify before it is reached:

```js
// oauth_provider_discord.js:57
sub: String(user_info.id),
// oauth_provider_twitter.js:61 — note tmp = user_info.data || {}
sub: String(tmp.id),
```

`String(undefined)` is `'undefined'` — a non-empty string, so the guard passes it through.

**Impact.** Any response without an id yields the identity value `'undefined'` for that provider. The
first such user creates it; the second **signs in as the first**. The X path makes this concrete:
`oauth_provider_twitter.js:58` reads `user_info.data || {}`, and X returns `{errors: [...]}` with no
`data` on several ordinary failures (suspended account, revoked scope, rate limit), so a non-fatal
API error becomes a shared identity rather than a rejection.

**Severity:** Medium — cross-account sign-in, reachable through a provider error path rather than
attacker action, and only on providers using this shape.

**Location:** `src/oauth_providers/oauth_provider_discord.js:57`;
`src/oauth_providers/oauth_provider_twitter.js:61`, `:58`.

**Verification.** `oauth_sub(String(undefined))` returns `'undefined'` — the guard's own type check
(`typeof value !== 'string' && typeof value !== 'number'`) is bypassed because the value arrives
already converted.

**Why the suite misses it.** No mock omits the id, so both rejection branches
(`make_oauth_flow.js:246`, `:251`) have zero coverage — the H2 remediation has no test of its own.

**Remediation.** Remove `String()` from both providers and let `oauth_sub` see the raw value; that is
what centralizing the normalization was for. Have the twitter provider fail loudly when `data` is
absent rather than defaulting to `{}`. Add fixtures with a missing id for both, and a provider-error
fixture for X.

**Severity:** Medium — no defect today, but the safety net has holes exactly where it matters most.

**Location:** `src/create_app.js:367-370`, `:520-546`, `:570-571`, `:582-583`;

### N30. Test-harness helpers hide failures

**Description.** Several helpers in `tests/setup_servers.js` silently absorb the failures they should
surface:

- `sign_in()` (`:377-393`) never checks that the sign-in worked. It waits for an email only when the
  fixture has one; for the ~105 username-only call sites, a failed sign-in returns `{user_id}` and
  the test proceeds believing it is authenticated.
- `ws_roundtrip` (`:98-138`) resolves rather than rejects on timeout, returning
  `{opened: false, status: null}` — indistinguishable from a deliberate rejection for any test that
  asserts only `opened === false`. `websockets.spec.js:17` has the same weakness: it asserts close
  code `1006`, which browsers emit for any abnormal closure including "server never started".
- `request()` (`:230-305`) converts every method to GET on any 3xx including 307/308, follows
  redirects without a bound, and stores cookies by name while ignoring `Max-Age=0`, `Expires`,
  `Path`, and `Domain` — so a server-cleared cookie is retained as an empty value rather than
  dropped, which is exactly what a sign-out test needs to observe.
- `spin()` (`:27-28`) derives `config.cookie.domain` and `config.cookie.secure` from substrings of
  the **test's title**, so renaming a test silently changes what it exercises — and the cookie tests
  then assert the value the title produced.

**Impact.** A green suite is weaker evidence than it appears, and the weakness concentrates in
authentication and session-lifecycle tests. `sign_in()` in particular means a whole class of
regression — anything that breaks username sign-in — could pass every test that depends on it.

**Severity:** Medium — testing infrastructure that can mask the defects it exists to catch.

**Location:** `tests/setup_servers.js:27-28`, `:98-138`, `:230-305`, `:377-393`;
`tests/playwright/websockets.spec.js:17`.

**Remediation.** Have `sign_in()` assert `authenticated === true` from `/auth/status` before
returning — a one-line change that immediately strengthens 105 tests. Make `ws_roundtrip` distinguish
timeout from rejection. Take cookie attributes into account in the client, or use a real cookie jar.
Pass cookie settings as explicit test parameters rather than parsing titles.

### N32. Sentry transaction events bypass redaction entirely

**Description.** `init_sentry` registers only `beforeSend` (`src/services/sentry.js:22`). There is no
`beforeSendTransaction` and no `beforeBreadcrumb`, while tracing is a supported, documented option
(`:29`, `config/make_config.js:136`, `AUTHWALL_SENTRY_TRACES_SAMPLE_RATE`).

**Impact.** With tracing enabled, transaction events carry the full URL in `request.url`,
`request.query_string`, and `contexts.trace.data` (`url.full`, `http.url`, `http.target`,
`http.query`) — none of which passes through `sanitize_sentry_event`. Magic-link tokens, email-verify
tokens, and OAuth codes therefore reach Sentry in cleartext on ordinary successful requests, not only
on errors. `docs/security.md:132-138` tells the operator that query parameters which look like secrets
"are replaced with `[Filtered]`", without qualifying that this applies to error events only. Error
events themselves are clean — the M10 fix works.

**Severity:** Medium — credential disclosure to a third-party processor, gated on tracing being
enabled.

**Location:** `src/services/sentry.js:22`, `:28-30`.

**Remediation.** Register `beforeSendTransaction` with the same sanitizer, extend it to the
`contexts.trace.data` URL fields, and add `beforeBreadcrumb` (still outstanding from M10). Then make
`docs/security.md` say which event types the guarantee covers.

## Low severity and hardening gaps

- **L1. Pre-fix logs were never rotated, and two sinks still bypass redaction.** `data/logs/` holds
  **142 distinct token values** and the Google OAuth `code=` entries quoted in yesterday's audit; the
  code is fixed but the instruction to treat existing logs as compromised was not carried out.
  Separately, `[ws_upgrade]` and `[ws_upgrade_reject]` (`src/create_app.js:491`, `:504`) log `req.url`
  raw while the three HTTP sinks use `urlxxx`. Delete or archive the old logs; route the WS lines
  through the same helper.
- **L2. Eight orphaned files (~650 KB) remain in `data/temp-uploads/`.** The leak is fixed; the debris
  from before the fix was never swept, and nothing sweeps that directory at startup.
- **L3. The "last auth method" guards count identities that cannot authenticate.**
  `make_oauth_flow.js:275` and `email_remove.js:34` both test `identities.length <= 1` without
  considering whether a remaining identity is usable — an unverified email counts, and
  `password_hash` is not consulted. An OAuth user who adds an unverified email can disconnect the
  provider and be left with no usable credential, recoverable only through a password-reset email.
  Count usable methods instead.
- **L4. `display_name` has no length limit.** `src/routes/profile.js:88` stores whatever fits in the
  100 kB JSON body limit, and it is rendered in the SPA and in every outbound email. See N18.
- **L5. A magic-link token is consumed before the access rules are checked.**
  `src/routes/magic_link.js:88-92` marks the row used and then calls `authorize_email`, so a

- **L6. The logger drops the failure-adjacent lines, never re-arms, and ignores backpressure.**
  Lines written between `createWriteStream()` and the async `'error'` event go into the doomed

- **L27. The redaction predicate covers Authwall's own parameters, not the upstream app's.**

## Cross-cutting observations

Three of this audit's findings are instances of one pattern each, and the pattern is the more useful
thing to fix.

**Configuration validates names strictly and values not at all.** `make_config.js:415-426` refuses to
start on an unknown `AUTHWALL_*` name — the right instinct, and unusual to find. But an out-of-range
integer clamps (N4), an unrecognized enum falls back (N13), an unrecognized boolean enables (prior
M3), and an empty string overrides a computed default (N1, and again in `.env.example`'s SES region).
The result is that the config layer is strictest about the mistake operators are least likely to make
and silent about the ones that change security behaviour. `docs/config.md:1-11` describes the strict
behaviour as a design principle, so the documentation is currently a description of the intent rather
than the code. One rule — *invalid input is a startup error* — resolves four findings and makes the
docs true.

**Yesterday's fixes were correct and half-shipped.** Nine of thirteen commits fixed the defect named
in the finding and stopped at the code, leaving the rest of the finding's blast radius untouched: the
redaction fix covered `req.url` and not the `Referer` header, Sentry transactions, or the WS log
lines — and it introduced N31 by dropping the `try/catch` the code it replaced had. The sidecar fix
landed without the example configs that consume its new status code. The initial-password fix landed
without the UI that exposes it. The dependency fix landed without the Trivy half. The log-redaction
fix landed without rotating the logs it declared compromised.

The pattern is worth naming because it is cheap to correct: a finding is closed when the *impact*
is gone, not when the line is changed. For this codebase that usually means asking three questions
before calling a fix done — is there another sink or caller with the same problem, does anything
shipped (examples, SPA, docs) need to change with it, and does the fix itself introduce a new failure
mode? N31 is what the third question catches.

**Authorization state is read from four places, and one of them is a snapshot.** Yesterday's H1 was
the proxy and the sidecar disagreeing; the fix made them agree by sharing a helper. N3 is the same
shape one level deeper: the shared helper reads a session field that only sign-in writes, while the
PAT path reads the database. The extraction of a single `authorize_request(req)` that yesterday's
audit recommended is still the right move, and N3 raises its priority — it should own the freshness
question too, not just the rule.

**The suite validates the code against itself.** Yesterday's audit named this for OAuth mocks and
fixed the two instances it found. The pattern survived the fix. N27 is the same defect one field
over: the GitHub fixture sends `visibility: 'public'` because the code accepts `'public'`, so a
shape assertion that rejects GitHub's most common value passes every test. N28 is the H2 remediation
itself going untested, so two providers still route around it.

It also has three forms that are not about mocks at all. `email_verify_cross_session.test.js` covers
N3's exact scenario and asserts only the half that passes. Rate limiting (N14) is disabled
process-wide in the API suite, so a documented control's wiring is unverified while its unit tests
stay green. And `sign_in()` (N30) never checks that it signed anyone in, which weakens roughly a
hundred tests at once.

Coverage cannot see any of this — the lines execute, and the assertions are about the wrong thing.
Two habits would catch most of it: when a test's name promises a behaviour, check that the body
asserts *that* behaviour; and when code validates someone else's API, the fixture has to come from
that API rather than from the code under test.

### Larger refactoring — worth scheduling, not worth rushing

- **One authorization decision, one source of truth.** Yesterday's audit recommended extracting
  `authorize_request(req)` for the proxy, sidecar, PAT, and WebSocket paths. N3 and N5 both argue for
  it and extend the requirement: the extracted function should own *freshness* and *path scope*, not
  just the rule. Every drift finding in the last two audits — H1, N3, N5 — lives in the gap between
  those four call sites.
- **A validation layer with one convention.** N1, N4, N13, N22, prior M3, and prior M12 are all "input
  reached storage or configuration without being checked". Config-time and request-time validation
  currently share nothing, which is why `make_config` has a real email regex that no route uses.
- **Real provider fixtures.** Carried over from yesterday and still the highest-leverage testing
  change available: capture one redacted live response per provider and rebuild the mocks from it.
