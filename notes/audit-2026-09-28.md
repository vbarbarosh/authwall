## Verdict

The controls that held on 2026-09-23 still hold:

- session ids and CSRF tokens rotate at authentication boundaries;
- one-time tokens are 256-bit, stored hashed, and consumed atomically (except
  email change, AW-71);
- inbound identity headers are stripped on both HTTP and WebSocket;
- the random helpers are unbiased.

This pass found **three new high findings**, and each breaks a different
guarantee:

- **AW-22**: the public-path check reads the path Express parsed, which ends
  at a `#`, while the upstream receives the raw path. With the default public
  paths, `GET /favicon.ico#/../admin.txt` reached a protected file anonymously
  through BusyBox httpd.
- **AW-23**: on MySQL, `magic_links.email_normalized` has an accent- and
  case-insensitive collation. A code mailed to `alice@acmé.test` signs the
  sender in as `alice@acme.test`. It was reproduced on MySQL 8.4.
- **AW-24**: an OAuth identity linked from a borrowed session survives a
  password reset. The "connected" email tells the owner to reset the password,
  which is exactly the step that does not remove the link.

The pattern from 2026-09-23 continues: **recovery does not revoke everything a
borrowed session can plant**. H-01 (email-change links), M-05 (PATs), AW-24
(OAuth links) and AW-27 (other email-change links) are four forms of it. One
shared "revoke everything pending" step, used by every recovery path, closes
all four.

**Access rules** have three more gaps:

- A sign-in through OAuth or email and password checks only the address
  presented, not the account's own addresses (AW-28).
- A verification link completes the account that asked for it, not the
  account of the person who clicked (AW-25).
- Link-only magic-link mode still accepts codes (AW-26), which undercuts one
  of the AW-02 remediations.

## 1. Proxy and path decisions

### AW-22 A `#` in the request line makes a public path an anonymous route to any file (high)

`src/create_app.js:275` and `:398` decide "public" and "sign-in required" with
`is_public_path(req.path)`. `req.path` comes from `parseurl`, which falls back
to `url.parse`, and `url.parse` treats `#` as the start of a fragment:

```
> url.parse('/favicon.ico#/../admin.txt').pathname
'/favicon.ico'
```

The proxy forwards the raw `req.url` and splits it only at `?`
(`node_modules/httpxy/dist/index.mjs:83-88`). So Authwall judges one path and
the upstream receives another. An upstream that keeps `#` in the path and
then resolves `..` serves the file named after it. With the default public
paths in front of BusyBox httpd:

```
"/admin.txt"                  -> 302 Redirecting to /auth/sign-in
"/favicon.ico#/../admin.txt"  -> HTTP/1.1 200 OK | SECRET-ADMIN
"/robots.txt#/../admin.txt"   -> HTTP/1.1 200 OK | SECRET-ADMIN
```

The echo upstream received `{"url":"/lib/x#/../../admin","x_auth_user":null}`.
Node, PHP `-S`, nginx and Apache cut at `#` and are not affected. Go's
`http.FileServer` used as a bare handler should be affected, but that was
judged from its source and not run. This is not AW-03: AW-03 is about `..;`
and `%25`-encoded dots.

A backslash before a `#` is rewritten to `/` by `url.parse` as well. Dot
segments are still caught, so that variant was not exploitable.

Fix: answer 400 to any request target that contains `#` or is not in origin
form, before any auth decision. Better still, make every public and
optional-auth decision on the raw `req.url` split at `?`, the same string the
upstream receives. Check the sidecar's `X-Forwarded-Uri` path
(`src/routes/status.js`) the same way.

### AW-20 Client `X-Forwarded-*` and `X-Real-IP` reach the upstream in both modes (raised to medium)

The 2026-09-23 text implies that `xfwd` (`create_app.js:256`) fixes proxy
mode. It does not. httpxy's `xfwd` only fills these headers when they are
missing; it never overwrites them or appends to them
(`node_modules/httpxy/dist/index.mjs:266-269` for HTTP, `:425-426` for
WebSocket). `X-Real-IP` is never touched. Probe with
`AUTHWALL_UPSTREAM_MODE=proxy` on a public path:

```
upstream saw {"x-forwarded-for":"6.6.6.6","x-forwarded-host":"evil.test","x-forwarded-proto":"https","x-real-ip":"6.6.6.6"}
```

`docs/config.md:440-443` says Authwall "sends X-Forwarded-For,
X-Forwarded-Host, X-Forwarded-Proto" to the routing proxy behind it. That
proxy trusts Authwall as its only hop, so the client chooses the IP and host
it sees. Fix: in `proxyReq` and `proxyReqWs`, delete every inbound
`X-Forwarded-*` and `X-Real-IP` header, then set them from `req.ip`,
`req.protocol` and `Host`.

## 2. Access rules

### AW-23 On MySQL, a magic-link code for a collation-equal address signs in as the victim (high)

`db/migrations/20260314182720_magic_links.js:9` declares `email_normalized`
without `utf8mb4_bin`. `user_identities.value_normalized` has it
(`20260314130739_user_identities.js:14`), and so do `sessions` and `users`.
`knexfile.js:32-98` claims that MySQL tables are created with
`COLLATE utf8mb4_unicode_ci`. In fact knex emits only
`default character set utf8mb4`, so the tables take the server default,
`utf8mb4_0900_ai_ci` on 8.4, which ignores case and accents.

The confirm route looks up the code row by the *submitted* address
(`src/routes/magic_link.js:140-145`). It then resolves the identity by the
submitted address as well (`:162`).

Scenario:

1. The victim is `alice@acme.test`. The attacker owns the IDN domain
   `acmé.test`, which `normalize_email` accepts.
2. The attacker requests a magic link for `alice@acmé.test` and receives the
   code.
3. The attacker posts `{email: alice@acme.test, code}` to the confirm route.
   The row lookup matches the attacker's row, and the identity lookup returns
   the victim.

On MySQL 8.4.11:

```
PM1 code mailed to: alice@acmé.test code: 110610
PM1 authenticated: true error: null is victim: true
magic_links.email_normalized collation: utf8mb4_0900_ai_ci; user_identities.value_normalized: utf8mb4_bin
```

Limits:

- An allowlist blocks step 2, because `acmé.test` is not allowed. Open and
  deny-only deployments are exposed.
- The mail provider must deliver to a Unicode domain; only the fake mailer was
  used.
- SQLite and PostgreSQL are not affected.

Every `token_hash` column except the PATs' has the same `ai_ci` collation, so
base64url hashes compare case-insensitively on MySQL. That is a defence-in-depth
gap only.

Fix:

- In the confirm route, require `magic_link.email_normalized ===
  email_normalized` in JavaScript, and take the identity from the stored row.
- Add a migration that sets `utf8mb4_bin` on `magic_links.email_normalized` and
  on every `token_hash` and `code_hash` column.
- Correct the knexfile comment.

### AW-25 A verification link completes whichever account requested it (medium)

`GET /auth/email-verify/confirm` (`src/routes/email_verify.js:79-117`) is
anonymous. It verifies the pending row of `record.user_id`, whatever session
opens it. The pending row comes from sign-up (`password.js:184-221`) or from
email add (`email_add.js:80-102`). `docs/security.md:127` says the user must
"prove control of their address".

Scenario, with `allowed_domains=corp.test` and confirmation required:

1. The attacker signs up `victim@corp.test` with a password of the attacker's
   choosing.
2. The victim clicks the "Welcome, confirm your email" mail.
3. The attacker signs in with that password and is proxied.
4. Later, the victim's own magic link or password reset signs the victim into
   the attacker's account.

```
attacker before click: status 302 location /auth/email-verify?...
victim click: 302 /auth/email-verify/success
attacker after click: upstream url= /private/data x-auth-user= awuser_s66n...
```

The 2026-09-02 audit mentioned this chain inside S2, but no later register
carried it. AW-11 covers prefetch and login CSRF only. Fix: complete
verification only in a session signed in to that account, or on a POST
confirmation page. Otherwise, treat a verification from another browser as an
ownership transfer: revoke sessions and require a new password.

### AW-26 Magic-link codes are accepted in link-only mode (medium)

`src/routes/magic_link.js:55` and `:62` generate and hash a code in every
mode. The POST confirm route (`:125-160`) never checks the mode. Compare
`email_verify.js:122-124` and `create_email_verify_token.js:12`, which do.
`AUTHWALL_FLOWS=magic_link` resolves to `mode: link`.

```
template= magic_link_without_code body has code= false | stored code_hash present= true | mode= link authenticated via code= true
```

So a code that no user ever receives can still be guessed. AW-02 recommends
link-only mode as a mitigation, and for magic links that mitigation does not
work. Fix: in link mode, store no `code_hash` and reject POST confirm. In code
mode, reject GET.

### AW-28 Sign-in checks the presented address, not the account's addresses (medium)

`src/helpers/make/make_oauth_flow.js:83-85` authorizes only the provider's
current `verified_emails`. It then signs the existing account in
(`:187-189`, `:225-226`) with no further check. Email and password sign-in
(`password.js:84`) authorizes only the typed address. Compare
`username_sign_in_refusal.js:22-29`, which checks every verified address
stored on the account.

Scenario: the account holds `bad@corp.test` and GitHub id 777, and the
operator denies `bad@corp.test` (the `fired@myapp.test` example in
`docs/config.md:700-702`). The user changes the address at GitHub, and
sign-in through GitHub still succeeds:

```
PC2 same user: true authenticated: true error: null identities: [["oauth_github","777",true],["email","bad@corp.test",true]]
PC2 upstream x-auth-user: awuser_h24qrlft6wv7kr54v316yd02
```

Fix: after resolving the user, apply the account-wide refusal to every
sign-in method: OAuth, email and password, and magic link.

### AW-46 `denied_domains` does not cover subdomains (low)

`src/helpers/authorize_email.js:19` compares the domain as an exact string.
`docs/config.md:622` says the setting blocks "whole domains".

```
x@evil.test -> Email domain is not allowed
x@mail.evil.test -> allowed
```

Deny when `domain === d || domain.endsWith('.' + d)`, or document exact
matching. This is a different gap from AW-08 (the trailing dot).

### AW-47 Domain access-rule entries are never validated (low)

`config/make_config.js:122-123` calls `src/helpers/parse_domains.js:7-12`,
which splits the environment form on `,` only and does not trim the array
form. Denied emails, by contrast, are validated (`make_config.js:571-583`).

```
DENIED_DOMAINS "@evil.test"            -> bob@evil.test: ALLOWED
DENIED_DOMAINS "*.evil.test"           -> bob@evil.test: ALLOWED
DENIED_DOMAINS "evil.test;other.test"  -> bob@evil.test: ALLOWED bob@other.test: ALLOWED
DENIED_EMAILS  "@evil.test"            -> AUTHWALL_DENIED_EMAILS contains invalid email
```

Validate every entry as a hostname and refuse to start otherwise. Trim both
forms.

### AW-50 A GitHub user with one extra address outside the allowlist is refused (low)

`authorize_oauth_verified_emails.js:16-19` passes to
`email_access_rules_refusal.js:11-21`, which requires *every* address to
pass. GitHub is the only adapter that returns several addresses
(`oauth_provider_github.js:70`). With `allowed_domains=[corp.test]` and GitHub
addresses `me@corp.test` and `me@personal.test`:

```
PC1 {"authenticated":false,"error":"Email domain is not allowed"}
last event: change_me_email_not_authorized failure identity=null
```

The event type is a placeholder (`create_app.js:384`) and carries no address.
Fix: apply deny rules to every address, apply allow rules to the stored
address, and drop the addresses that do not pass. Give the event a real type.

## 3. Recovery and account changes

### AW-24 An OAuth identity linked from a borrowed session survives password reset (high)

Connect inserts an identity with a session alone
(`src/helpers/make/make_oauth_flow.js:122-132`). The reset transaction
(`src/routes/password.js:326-336`) deletes reset tokens and sessions and
revokes PATs, but leaves `user_identities` alone. Every `*-connected.txt` mail
says: "If you did not connect a Google account, reset your password
immediately" (`design/emails/google-connected.txt:10-11`).

The unique key is `(type, value_normalized)`
(`20260314130739_user_identities.js:26`). So a user can hold two identities of
the same provider, and "Disconnect" removes the first one it finds
(`make_oauth_flow.js:263`, `:287`).

```
PC4 after reset: authenticated true as owner: true
PS oauth_google rows on owner: ["owner-google","attacker-google"]
PS after one "Disconnect Google": ["attacker-google"]
```

This is the same break as H-01, but it never expires. AW-04's list of actions
that need no re-authentication left out OAuth connect. Fix:

- Allow at most one identity per provider per user, and disconnect by
  identity uid.
- Require recent re-authentication for connect (AW-04).
- Point the connected mails at "Disconnect" in the profile.
- Remove, or ask the owner to review, OAuth identities linked since the last
  password-verified sign-in when the password is reset.

### AW-27 Confirming one email change leaves the account's other change links live (medium)

`src/routes/email_change.js:128-154` marks only the confirmed token used.
Other unused `email_change_tokens` of the user stay live. Email remove
(`email_remove.js:68-73`) does not delete them either.

```
emails after owner change= [ 'owner-new@authwall.test' ] | unused change tokens left= 1 |
attacker link later: 302 /auth/email-change/success | emails after attacker link= [ 'attacker@evil.test' ]
```

The trigger is the owner's own change, which H-01's remediation does not
cover. Fix: delete every other unused change token in the confirm
transaction and on email remove, through the same shared revoke step as
H-01 and M-05.

### AW-71 Email-change links are not consumed with a conditional update (low)

`email_change.js:129` updates `where({id})`, with no `used_at IS NULL`
condition. Only the unique index on identities stops a double spend. The same
link opened twice at once:

```

```

The loser gets a generic error. The 2026-09-23 verdict says that every
one-time link is consumed with a conditional update. Use
`consume_one_time_token` here.

### AW-37 A stale verification link crashes or reports false success (low)

Removing or changing an address does not delete its `email_verify_tokens`
(`email_remove.js:68-73`, `email_change.js:128-150`). Opening the old link
consumes it, updates no row, and passes `undefined` on

```
required=false: emails after remove= 0 | click: 302 /auth/email-verify/success | email_verified events= [ null ]
required=true:  status.error= An error occurred [...]
                TypeError: Cannot read properties of undefined (reading 'user_id') at complete_email_verif...
```

Delete the address's tokens when the address goes. In confirm, treat zero
updated rows as "Invalid or expired".

### AW-39 A failed profile request still replaces the public avatar (low)

`src/routes/profile.js:101-113` writes the avatar with sharp before the
password checks at `:117-140`. A request rejected with "Current password is
incorrect" has already replaced `data/uploads/<slug>/avatar.webp`, which is
served anonymously (`create_app.js:109`). Source-confirmed only. Validate
first, render to a temporary file, and rename it into place after the
database commit.

### AW-40 Account removal notifies nobody (low)

`src/routes/account.js:18-58` sends no mail. Password change, email change,
new sign-in and provider connect all notify the owner. Removal needs only a
session, CSRF and typing `DELETE` (AW-04). Read the verified address before
the transaction, and send an "account removed" notice after the commit.

### AW-51 Connecting a provider does not verify the matching pending address (low)

`make_oauth_flow.js:145-157` inserts the address with
`onConflict(['type','value_normalized']).ignore()`, so an existing pending row
of the same user stays unverified:

```

```

On conflict, when the row belongs to this user and `verified_at` is null, set
`verified_at`.

### AW-62 Double submit, and a count-then-delete race in the last-method guards (low)

In the SPA, session revoke (`spa.html:2064-2070`), PAT revoke
(`:2055-2061`), disconnect (`:1977-1982`) and resend verification
(`:2102-2108`) never disable their control. One double click sent
`["/auth/sessions/revoke","/auth/sessions/revoke"]`.

On the server, the disconnect and email-remove guards count first and delete
afterwards, without a lock (`make_oauth_flow.js:276` then `:287`;
`email_remove.js:35` then `:69`). Two concurrent removals of different
identities can both pass and leave no sign-in method. This part is
source-confirmed only. Fix: disable the control while its request is pending,
and do the count and the delete in one transaction or as a conditional delete.

## 4. Sessions and WebSockets

### AW-29 Sessions never reach a hard expiry (medium)

`src/helpers/SessionStore.js:41-44` rebuilds the cookie without
`originalMaxAge`; that is the root cause of L-01. express-session's `touch`
then resets `expires` to `undefined`. `row_expires_at` (`:93-101`) falls back
to now + `max_age_days`, and `touch` (`:80-90`) applies it on every request.
WebSocket admission does the same (`create_app.js:607-610`).

```
PB4 expires_at set to now+1h; after one request it is now+ 30.00 days
```

The browser keeps the `Expires` it got at sign-in, so the real user is signed
out at day 30, while any other holder of the cookie is not (see AW-19). Fix:
store an absolute deadline, created_at plus the maximum age, and enforce it
in `get()`. Keep a separate idle timeout, and persist `originalMaxAge`.

### AW-30 A reset during a WebSocket upgrade can crash the process (medium)

After an upgrade, Node removes its own error listener from the socket.
`handle_ws_upgrade` (`src/create_app.js:493-533`) then awaits a database
lookup (`:511`) with no `socket.on('error')`. A client reset during that wait
emits an unhandled `error`, and the process exits.

```
isolated Node 24.20: upgrade received; error listeners on socket = 0 ... Error: read ECONNRESET ... exit code 1
Authwall, 30 ms delay injected on queries: Uncaught Error: read ECONNRESET at TCP.onStreamRead
```

It needs `AUTHWALL_WEBSOCKETS=true` (default false,
`config/make_config.js:155`) and a database with network latency. On SQLite,
200 attempts survived. Fix: attach an error handler as the first statement of
`handle_ws_upgrade`, and skip `reject()` when the socket is already destroyed.

### AW-42 Every cookieless `/auth` request writes a session row (low)

`create_app.js:141-150` sets `ip`, `ua` and `csrf_token` on every `/auth`
request, so express-session saves a new row even for `/auth/does-not-exist`:

```
PB1 rows before= 0 after 100 cookieless requests= 100 anonymous= 100
```

Create an anonymous session only where a CSRF token is issued, and prune the
rows (M-10).

### AW-44 Stack traces reach clients when `NODE_ENV` is not `production` (low)

`express.json` runs before the session middleware (`create_app.js:113`). For a
GET to the sign-in path, `error_handler` calls `next(error)` (`:371-373`),
and Express's default handler renders the stack:

```
GET /auth/sign-in, Content-Type: application/json, body {bad
status= 400 body= <pre>SyntaxError: Expected property name ... at parse (/app/node_modules/body-pars...
```

The Docker image sets `NODE_ENV=production` (`Dockerfile:29`), but
`npm start` and `node .` do not. Add a last error handler that answers with
the status text and never the stack.

## 5. Abuse controls

### AW-36 Anyone can burn another person's magic-link code (low)

POST confirm (`magic_link.js:31`) has no limiter. It spends an attempt on the
latest link of *any* address (`:140-151`). With mode `code`, five wrong
guesses from another session:

```
victim with correct code: authenticated= false error= Invalid or expired code
```

This is fixed together with AW-02: throttle confirm per address and per IP.

### AW-43 Throttle maps have no size limit (low)

`rate_limit_middleware.js:10-47` counts every request, and
`make_failure_counter.js:13-50` counts failures. Expired entries are removed
only by a timer that runs once per window, so an entry can live up to twice
the window.

```
1000000 distinct keys -> heap +196 MiB (205 B/key)
```

There is one such map per limiter, seven in all, and the keys are cheap to
vary with IPv6 or a spoofed `X-Forwarded-For` (M-08). Cap each map, expire
entries when they are read, and key IPv6 by /64 (AW-07).

### AW-41 Non-string body fields reach bcrypt and string methods and return 500 (low)

The JSON body parser accepts numbers and objects:

- `username.includes` throws for a numeric username (`password.js:66`).
- A numeric password passes the length check, because `undefined < 8` is
  false (`password.js:154`, `:373`; `profile.js:81`). bcrypt then throws.

```
sign-up numeric password -> error= An error occurred [...]
sign-in numeric username -> error= An error occurred [...]
```

Reject any field that is not a string at route entry, with a
`UserFriendlyError`.

## 6. Configuration and OAuth input

### AW-38 `AUTHWALL_CONFIRM_EMAIL=off` changes only the status payload (low)

`src/helpers/parse/parse_magic_link_setting.js:16-20` sets `enabled=false`
(`:33-37` for an unknown value), but `confirm_email.required` stays true
(`make_config.js:505-510`). Only `status.js:66` and `:144` read `enabled`. Sign-up still mails a link and a
code (`password.js:219`, `complete_sign_up.js:28-41`), and the verify routes
stay mounted (`create_app.js:205-209`). `docs/config.md:716-721` says "off"
disables confirmation, and so does any value outside the list.

```
make_config: CONFIRM_EMAIL=off -> required true enabled false; =lnik -> same
PCE sign-up -> 302 /auth/email-verify/sent; emails sent: ['welcome_and_confirm_email']; protected -> 302 /auth/email-verify?return=%2Fapp%2Fpage
```

Two readers found this independently. When the mode is off, set
`required=false` and mount no verify routes, or refuse to start on the
contradiction. Reject unknown values.

### AW-48 `AUTHWALL_PUBLIC_URL` is not validated (low)

`make_config.js:47` takes the raw value. `:175` derives `cookie.secure` from
it. Links are built as `public_url + '/auth/...'`
(`complete_magic_link_request.js:20`).

```
PUBLIC_URL "https://auth.example.com/" -> reset link https://auth.example.com//auth/password-reset
GET //auth/password-reset/confirm?token=abc -> 302 /auth/sign-in?return=%2F%2Fauth%2Fpassword-reset%2Fconfirm%3Ftoken%3Dabc
```

`urlxxx` redacts only a top-level `token` key, so the token lands in the log.
When the variable is unset, links point at `http://127.0.0.1:3000` and
`cookie.secure` is false, with no warning. Parse the value with `URL`, require
a scheme and a host, strip a trailing slash, and warn when it is unset in
production.

### AW-49 `.env.example` ships an empty `AUTHWALL_SES_REGION` (low)

`.env.example:43-44` has `AUTHWALL_SES_REGION=`. The default in
`make_config.js:242` applies only to an undefined value, so the region
becomes `""`, and `make_mailer_ses.js:10` builds
`https://email..amazonaws.com`. First reported on 2026-07-28
(`audit-2026-07-28.md:650`), then dropped. Treat `''` as unset.

### AW-52 Provider display names bypass the profile's sanitizing (low)

`make_oauth_flow.js:193-195` passes the provider's name to
`users_create.js:16` unchanged. The profile route strips control characters
and caps the name at 100 characters (`profile.js:89-90`).

```
SQLite and MySQL: stored "Security Team\r\n\r\nYour account is locked. Call +1 555 0100."
MySQL, 300 chars: authenticated false, error "An error occurred [req_…]"
```

The name reaches mail bodies and the recipient string (AW-09). Run provider
names through the same normalizer.

## 7. SPA

### AW-31 The sign-in form keeps a dead CSRF token after an SPA sign-out (medium)

`#si-csrf` is filled once, at boot (`spa.html:2226-2227`).
`sync_sign_in_form` (`:1151-1154`) rewrites only the form action. Sign-out
(`:2155-2160`, `:1291-1296`) and account removal (`:1965-1974`) show the
sign-in view without a reload. In both browsers:

```
si-csrf in form after SPA sign-out: ptSfpnoN, session csrf now: Qjpgr3u0, same: false
second sign-in without reload: err 'Invalid CSRF Token'
```

Set `#si-csrf` from every `/auth/status` response.

### AW-32 Subdomain returns are blocked by the SPA's own CSP; landings are fetched twice (medium)

`src/helpers/redirect.js:12-13` and `:44-47` accept a subdomain `return`. The
`/auth` CSP has `connect-src 'self'` and `form-action 'self'`
(`create_app.js:765-766`). The SPA posts with `fetch(..., {redirect:'follow'})`
(`spa.html:1255-1260`, `:1277-1282`).

- Chromium blocks the form sign-in: "Sending form data to … violates …
  form-action 'self'". The page stays on sign-in while `/auth/status` says
  `authenticated: true`.
- SPA sign-up fails with "Failed to fetch" in both browsers. The button stays
  on "Please wait…".
- With a same-origin return, the fetch follows the redirect into the app, and
  then `window.location` loads the page again:
  `["fetch GET /probe-double-…","document GET /probe-double-…"]`.

Fix: use `redirect:'manual'`, or have the server answer fetches with JSON
`{next}`, then call `location.assign`. Either allow subdomains in
`form-action`, or drop subdomain returns from `redirect.js` and
`docs/security.md:132-137`.

### AW-33 Email change is implemented and documented but unreachable in the SPA (medium)

`POST /auth/email-change/request` exists (`email_change.js:29`) and is
documented (`docs/glossary.md:21`, `:39`; `docs/emails.md:60-61`). The SPA
never posts to it. It has only the "sent" and "success" views (`spa.html:1072`,
`:1089`, `:1131-1132`), and it offers "Add email" only when the account has no
address (`:1614`). This is the same shape as M-13. Add a change-email form
behind AW-04's re-authentication, or remove the claim from the docs.

### AW-56 Back after sign-out shows the previous user's data (low)

`popstate` calls only `renderView` (`spa.html:1179-1184`), and nothing clears
the rendered user data on sign-out:

```
{"path":"/auth/profile","active":"profile","uid":"foo","sessions":"Chrome on Linux 127.0.0.1 · just now This device"}
```

AW-21 is the PAT-secret case of the same cause. Clear the user-data containers
on sign-out, and re-fetch the status on every `popstate` into a protected view.

### AW-59 A proxy 413 on avatar upload is shown as "Profile saved." (low)

`http_post_*` never reads `res.ok` (`spa.html:1267-1273`). The nginx recipes
leave `client_max_body_size` at nginx's 1 MiB default, while Authwall accepts
5 MiB (`profile.js:24-25`). With a routed 413 and a 2 MB file:

```
{"ok":"flex","okText":"Profile saved.","err":"none"}
```

The file input is never reset (`:1904-1921`), so the next save uploads the
file again. This widens M-14 (section 10). Check `res.ok`, clear the input
after every attempt, and set `client_max_body_size 6m` on `/auth/`.

### AW-60 SPA accessibility gaps beyond L-07 (low)

- The avatar file input is `display:none` inside a `<label>` (`spa.html:760`),
  so it cannot be reached by Tab. Evidence: "avatar file input reachable by
  Tab: false".
- `#pat-expires` has an inline `outline:none` and no focus rule (`:953`).
- `--text-subtle #9aa1ae` (`:34`) has a contrast of 2.60:1 on white. It is
  used for section titles, the user's email and "Not connected". The PAT
  expiry warning is 2.97:1.

Make the upload control focusable, add a focus ring, and raise both colours
to 4.5:1.

### AW-61 In-SPA navigation drops the query string (low)

`pushState(path)` drops `location.search` (`spa.html:1167-1168`), and
`navigate_after` keeps only the pathname (`:1293-1295`). Two consequences,
both source-confirmed:

- A reload of the code page says "Session expired. Please request a new magic
  link." (`:1892`), because `?email=` is gone and `_magic_email` lived only in
  memory (`:1870`).
- `:1894` forwards `location.search`, which by then no longer holds
  `?return`.

Carry the search through flow views, or keep the values in `history.state`.

### AW-63 The SPA ignores the server's minimum password length (low)

`status.js:58` sends `flows.password.min_password_length`, and the SPA never
reads it. `password_strength()` (`spa.html:1337-1342`) calls 10 characters
"strong", so with `AUTHWALL_PASSWORD_MIN=12` the meter says strong and the
server refuses. Set `minlength`, a hint and the meter from the status.

### AW-69 The demo navigation bar is on by default on localhost and on `?demo=1` (low)

Re-registered from 2026-09-02 S33. `spa.html:1136` and `:2200` enable an
18-button debug bar on `localhost` and `127.0.0.1`, and on any host with
`?demo=1`. On localhost, the profile's tab order starts with the 18 demo
buttons. Enable it only through an explicit development setting.

## 8. Deployment, CI, docs site and tooling

### AW-35 The production workflow deploys the branch tip, not the tested commit (medium)

Every job in `.github/workflows/production.yml` checks out `ref: production`
(`:11-13`, `:42-44`, `:94-96`, `:167-169`, `:197-199`), and there is no
`concurrency:` key. The deploy job runs `bin/deploy` (`:206`), which builds
HEAD and pushes four tags (`bin/deploy:30-39`). If commit B lands before
commit A's deploy job starts, A's run ships B untested. Source-confirmed.
Check out `${{ github.sha }}`, add a `concurrency` group, and deploy the
digest that was built and tested (M-12).

### AW-34 The docs site cannot be operated by keyboard (medium)

`.docs/static/docs.js:257-267` moves focus to the search box on any keydown
outside an input, including Enter and Space on links and buttons. In both
browsers, on the built docs:

- Enter on the theme toggle only focuses the search box.
- Enter on a sidebar link does not navigate.
- Enter on a Copy button does nothing.

That fails WCAG 2.1.1. `tests/playwright/docs-search-scroll.spec.js:35` checks
only that Space reaches the search box. Skip interactive targets, or use a
dedicated `/` key.

### AW-57 Multi-domain recipes cannot carry browser WebSockets (low)

The WebSocket `Origin` must equal the public URL's origin
(`create_app.js:715-738`), but the proxy recipes serve several hosts under
one public URL (`docs/examples/authwall-proxy-*/docker-compose.yaml:12`):

```
http://localhost:3377 -> OPEN; http://app.localhost:3377 -> HTTP 401 (origin_mismatch)
```

The nginx recipes also send `Connection ""` without forwarding `Upgrade`
(proxy-nginx `nginx.conf:31-32`, sidecar-nginx `:54-55`). That half is
source-confirmed. Accept a configured list of origins, and forward the
upgrade in both nginx recipes.

### AW-58 Recipes send `X-Forwarded-Proto: http` behind TLS termination (low)

The nginx recipes set `X-Forwarded-Proto $scheme` on port 80 (proxy-nginx
`nginx.conf:29`, sidecar-nginx `:52`). The Caddy recipes set no
`trusted_proxies`. The READMEs, however, tell users to terminate TLS in front
(proxy-nginx README `:71-73`, sidecar-nginx README `:85`). Source-confirmed.
Pass the load balancer's value through, or document the setting per recipe.

### AW-53 The runtime user can write its own code, config and templates (low)

`USER node` (`Dockerfile:22`) combined with `COPY --chown=node:node`
(`:32-43`) makes the application tree writable by the process. Copy as root,
make only `/app/data` owned by `node`, and document `read_only: true`.

### AW-54 Unused optional native packages are installed in production (low)

`@vbarbarosh/node-helpers` declares `ssh2` and `redis` as optional
dependencies. `ssh2` pulls in `cpu-features`, which has an install script.
`npm ci --omit=dev` (`Dockerfile:13`) installs both, although Authwall uses
none of the `sftp_*` helpers. Drop them with an `overrides` entry, not with
`--omit=optional`, because sharp needs its optional binaries.

### AW-55 `bin/` bash scripts abort when the path contains a space (low)

``script=`realpath $0` `` and `cd $scriptdir/..` are unquoted in every bash
script (e.g. `bin/deploy:7-11`, `bin/release:20-31`):

```
realpath: space/bin/test: No such file or directory
```

No injection was found. Quote the variables.

### AW-45 `bin/log-summary` files requests under a client-chosen IP (low)

`render_log_summary.js:315-321` prefers the leftmost `X-Forwarded-For`, then
`X-Real-IP`, and only then the socket address. The leftmost entry is always
written by the client. The throttles and auth events use `req.ip`. Log
`req.ip` in `req_begin`, and summarize by that value only.

### AW-64 Docs search corrupts snippets and mishandles `$`, `^`, `!` (low)

`docs.js:582-607` escapes the text first and marks hits inside the escaped
HTML, so a term like `lt` splits the `&lt;` entity. `filter1_from_spec_fuzzy.js:44-55`
strips `^`, `$` and `!` anywhere in a term, while `.docs/search-spec.md:46-48`
defines them only at the edges. For example, `$remote_addr` finds 0 of 2
sections. There is no XSS path. Mark hit ranges in the raw text and escape
each piece.

### AW-65 `docs.js` fails with blocked storage; floating CDN Mermaid in `loose` mode (low)

`localStorage` is used without `try/catch` (`docs.js:9`, `:40`, first reached
at `:31`). With storage blocked, the result is "The operation is insecure.",
0 of 44 copy buttons and no search. `:117` imports
`cdn.jsdelivr.net/npm/mermaid@11` with no exact version, and `:125` sets
`securityLevel: 'loose'`. Wrap the storage calls, pin or vendor Mermaid, and
use `strict`.

### AW-66 Browser tests skip every state-changing flow; `design.yaml` is stale (low)

The browser suite covers sign-in, the sign-out landing, page rendering and

- sign-up submit, password reset, and magic-code confirm;
- profile save, avatar and password change;
- email add and provider disconnect;

## What is good

- The random helpers (`random_base62`, `random_slug`, `random_code`) use
  rejection sampling or `randomInt`, with no modulo bias. cuid2 uses
  `crypto.getRandomValues`.
- `spend_attempt` and `consume_one_time_token` are atomic. CSRF comparison is
  constant-time. `resolve_yaml_vars` uses `Object.hasOwn`, so it is not open
  to prototype pollution.
- Log fields from users are JSON-quoted, and the HTTP parser refuses raw CR/LF
  in headers, so log injection was not found.
- `docs/config.md`, `config/settings.yaml`, `config/authwall_env_vars.txt` and
  `src/` name exactly the same set of `AUTHWALL_*` variables.
- The built docs have no broken relative links or anchors. The documented
  expiries and the rate-limit table match the code.
- The OAuth callback binds `state` to the session and uses PKCE.
  Microsoft email trust is gated on `xms_edov`.
- The runtime image runs as a non-root user and copies an explicit file list.
  No live secret appears in the tree or in history.
- The API suite (517 cases) made every probe in this audit cheap to write.
