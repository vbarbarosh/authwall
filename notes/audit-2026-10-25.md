## Verdict

The stage 1 work of the 09-28 plan did what it set out to do. Every high
finding of that register is closed, and closed in the code and its tests,
not only in the changelog:

- the request target is judged raw, before any auth decision, and a `#` in
  it is a 400 (AW-22); `..;` and double-encoded dots are refused (AW-03);
- a magic-link code works only for the address it was mailed to and only in
  the browser that asked (AW-23, AW-36's code half), the codes have an hour
  budget per address (AW-02), and a link-only mode issues none (AW-26);
- a reset or a password change kills pending links and tokens (H-01, M-05,
  AW-27), one account per provider per user is enforced by the schema and a
  connect from a borrowed session waits for the owner (AW-24);
- the sidecar protects when its two path headers disagree (H-02), the
  recipes stop the bearer and encode the redirect (AW-15 to AW-18), Authwall
  sets `X-Forwarded-*` itself (AW-20), and an open WebSocket ends with its
  credential (M-04).

Of the 94 findings of 09-28, 25 are fixed, 6 partly, 2 changed in premise
and 61 stand as written, re-cited to today's lines. The 69 that stay open
are the ones the plan had not reached yet: 19 medium, 50 low.

The code written for those fixes is where this pass found its new
findings, 29 of them, four high. Three of the four are the same theme the
09-28 verdict named, **what a borrowed session can still do**, and one is
the same theme from the other side, **what a GET of a mailed link does**:

- **AW-77**: removing the primary address needs neither the "confirm it is
  you" step nor the primary's approval. A borrowed browser removes the
  owner's address, adds its own, confirms it, and asks for a reset: the
  account is gone with no mail to the owner. It needs confirmation not
  required, the documented setting for username and OAuth deployments.
- **AW-78**: the approval link mailed to the current primary approves on a
  bare GET. A mail scanner that prefetches links spends it, and the
  attacker's address gets its confirmation link.
- **AW-79**: the same GET on a confirmation link, opened by a scanner before
  the owner, is "elsewhere" for the handover rule of AW-25's fix: the
  password is nulled, the sessions end, and the scanner is handed a reset
  token. Every sign-up behind such a scanner ends this way.
- **AW-76**: an upstream that drops the connection after its headers went
  out ends the Authwall process: the 502 handler writes to a response that
  was already sent, and nothing catches the throw. Both modes.

The six new medium findings are gaps next to fixes: access rules that apply
at sign-in only (AW-80), a ten-minute "confirmed" window that covers every
action of the session (AW-81), the squat that AW-25's fix leaves to an
account with another way in (AW-82), the header spellings and vendor
headers that the forwarded-header strip does not reach (AW-83, AW-84), and
the proxy recipes built like the direct one but not fixed with it (AW-85).

AW-75, which the 10-23 commit names and no note lists, is entered here from
that commit: auth-event inserts that carried unbounded request strings into
sized columns, so that on MySQL and PostgreSQL a long user agent made a
sign-in or a password change complete without its event and without the
containment steps after it. Fixed by `28722ba`; its siblings in the
sessions and token tables are AW-91. AW-72 to AW-74 are not in the tree,
the history or the working notes; they are reserved for the register the
author worked from.

## 1. Proxy, transport and WebSockets

### AW-76 An upstream that resets mid-response ends the Authwall process (high)

httpxy emits `error` when the upstream connection breaks after the response
headers went out. The handler at `src/create_app.js:336-345` answers every
error the same way:

```
proxy.on('error', function (error, req, res) {
    als.logger.write(`[proxy_error] ⚠️ ${error.message} url=${urlxxx(req.url)} originalUrl=${urlxxx(req.originalUrl)}`);
    // res is a `Socket` for WS upgrade errors and a `ServerResponse` for HTTP errors.
    if (typeof res.status === 'function') {
        res.status(502).send('Upstream service unavailable');
```

With the headers already sent, `res.send` throws `ERR_HTTP_HEADERS_SENT`
inside an EventEmitter callback. Nothing catches it: `src/index.js` installs
no `uncaughtException` handler, and `cli()` only reports a rejected `main`.
The `.catch` of `proxy.web` (`create_app.js:367-370`) emits the same event
and then calls `next(error)` on a response that is gone. httpxy's own path
is `node_modules/httpxy/dist/index.mjs:387-390`: `proxyRes.on("error", …
server.emit("error", err, req, res, currentUrl))`.

Scenario: a client asks for anything the upstream streams, a download, an
event stream, a long JSON, and the upstream drops the connection after the
headers: a restart during a deploy, its own timeout, or an endpoint an
attacker can make abort mid-body. The gate in front of every app exits, and
every user is cut off until the supervisor restarts it. Both modes. Probe
`crash.probe.js`, proxy and direct:

```
[log] [proxy_error] ⚠️ aborted url=/stream originalUrl=/stream
[probe] UNCAUGHT EXCEPTION (process would die): ERR_HTTP_HEADERS_SENT Cannot set headers after they are sent to the client
```

No test in `tests/api` covers a 502 after the headers (`grep -rn
"502\|headersSent" tests/api` finds nothing). The handler is older than the
httpxy wiring (`c4ddeee`), which made it reachable this way. Fix: return
after `res.destroy()` when `res.headersSent || res.destroyed`; in the
`.catch`, do not call `next` once the headers are sent; a test with an
upstream that writes one chunk and destroys its socket, asserting
`/auth/health` still answers.

### AW-83 Underscore spellings `X_Forwarded_*` and `X_Real_IP` reach the upstream (medium)

`set_forwarded_headers` (`src/create_app.js:716-736`) strips two spellings
only:

```
if (name.startsWith('x-forwarded-') || name === 'x-real-ip') {
    proxy_req.removeHeader(name);
}
```

The identity strip in the same file folds `_` to `-`
(`create_app.js:1009-1019`, `is_inbound_identity_header`) for the reason the
comment there gives: PHP CGI, FPM and Apache `mod_php` read
`X_Forwarded_For` and `X-Forwarded-For` into the same
`HTTP_X_FORWARDED_FOR`. The forwarded-header strip does not fold. Probe
`forwarded.probe.test.js`, proxy mode, default trust: the upstream received
`"x_forwarded_for":"7.7.7.7","x_forwarded_host":"evil7.test","x_forwarded_proto":"https","x_real_ip":"7.7.7.7"`
next to Authwall's own `"x-forwarded-for":"6.6.6.6"`; direct mode and both
WebSocket runs the same. In direct mode the upstream then has only the
forged value; in proxy mode it has two candidates for one CGI variable, and
the header order decides. Fix: strip on `name.replace(/_/g, '-')`, as the
identity strip does; the underscore names go into
`tests/api/stories/forwarded_headers_come_from_authwall.test.js`.

### AW-84 `Forwarded`, `X-Original-URL`, `X-Rewrite-URL` and vendor client-IP headers pass to the upstream (medium)

The same strip list is the only one. Probe `forwarded.probe.test.js`, proxy
mode (direct and WebSocket identical), the upstream received:

```
"forwarded":"for=8.8.8.8;proto=https;host=evil8.test","x-original-url":"/admin/secret","x-rewrite-url":"/admin/secret","x-original-host":"evil9.test","x-host":"evil9.test","x-client-ip":"9.9.9.9","true-client-ip":"9.9.9.9","x-cluster-client-ip":"9.9.9.9","x-http-method-override":"DELETE","via":"1.1 evil"
```

Authwall judged the path and resolved the client address; these headers let
common upstreams re-decide both. `X-Original-URL` and `X-Rewrite-URL` make
IIS and ASP.NET URL Rewrite route to that path instead of the request line:
an anonymous `GET /favicon.ico` with `X-Original-URL: /admin` is judged
public and served as `/admin`, the AW-22 class through a header. RFC 7239
`Forwarded` is read by Spring's `ForwardedHeaderFilter`, Symfony and Go
frameworks; `X-Client-IP`, `True-Client-IP`, `CF-Connecting-IP` and
`X-Cluster-Client-IP` by Rails's `remote_ip`, Laravel's and Symfony's
trusted-header presets and Cloudflare-aware apps, each trusting Authwall as
its only hop. `X-Forwarded-Prefix` was correctly absent. Shown against the
echo upstream only; no IIS was run. Fix: one fixed list in
`set_forwarded_headers`, both modes, HTTP and WebSocket: `forwarded`,
`x-original-url`, `x-rewrite-url`, `x-original-host`, `x-host`,
`x-client-ip`, `true-client-ip`, `cf-connecting-ip`, `x-cluster-client-ip`,
`x-proxyuser-ip`; say in `docs/security.md` whether `X-HTTP-Method-Override`
is left to the upstream.

### AW-85 The proxy recipes and the root compose file publish Authwall under the one-hop default (medium)

`75446d0` fixed the direct recipe:
`docs/examples/authwall-direct/docker-compose.yaml:11-12` `# No proxy in
front, so a client's X-Forwarded-For is not trusted.` /
`AUTHWALL_TRUST_PROXY: none`. The two proxy recipes were built the same way
and were not fixed: `docs/examples/authwall-proxy-nginx/docker-compose.yaml:8-17`
and `docs/examples/authwall-proxy-caddy/docker-compose.yaml:8-17` publish
Authwall on `3000:3000` as "the entrypoint and the only published service"
(`:3`) with no `AUTHWALL_TRUST_PROXY`; the root `docker-compose.yaml:3-14`
likewise. The default is one hop
(`src/helpers/parse/parse_trust_proxy.js:10-12`), so a client's
`X-Forwarded-For: 1.2.3.4` becomes `req.ip`: the per-IP throttles, the
"last used from" line and the `auth_events` IP are the attacker's choice.
Since `75446d0` the consequence is larger: Authwall now sets
`X-Forwarded-For`, `-Host` and `-Proto` from the resolved request, so the
client's values arrive at the router and the apps as Authwall's own. Probe
P2c (default trust, proxy mode): `upstream saw
{"x-forwarded-for":"6.6.6.6","x-forwarded-proto":"https","x-forwarded-host":"evil.test","x-forwarded-port":"443"}`.
Source-confirmed for the recipes; the compose files were not started. This
is M-08's class in the two examples M-08 did not name. Fix:
`AUTHWALL_TRUST_PROXY: none` with the same comment in both proxy recipes
and the root compose file; `hops/1` only where the README's TLS terminator
is in front, said per recipe (AW-58).

### AW-95 The sidecar judges a comma-joined duplicate path header as one path (low)

`src/routes/status.js:235` reads `req.headers['x-original-uri']` and

### AW-96 An anonymous WebSocket upgrade to a public path is refused (low)

### AW-98 The lease check does not dedupe credentials and runs after every `/auth` response (low)

### AW-99 SIGTERM with open WebSockets never drains; exit 1 after ten seconds (low)

### AW-100 In sidecar mode the original URL, with its query string, reaches Sentry unredacted (low)

### AW-79 A confirmation link fetched by a mail scanner hands a password-only account to the scanner (high)

### AW-75 Auth-event inserts carry unbounded request strings into sized columns (medium, fixed)

Registered from commit `28722ba` ("auth events: cut ip, user agent and
identity to the column sizes (AW-75)"); no note in the tree describes it.
Before the commit, `insert_auth_event` wrote `req.headers['user-agent']`,

ignores the size; MySQL in strict mode and PostgreSQL reject the insert.

`complete_password_change.js:20-33` (hash written, then no

medium.

The fix: `src/helpers/insert_auth_event.js:21-24` `identity_value:
auth_event_text(params.ident?.value, 255)`, `ip` to 64, `ua` to 512, cut by
code point (`:32-35`, `Array.from(value).slice(0, length)`), which matches
MySQL's utf8mb4 and PostgreSQL's character semantics; `4e90504` moved the
last direct insert (`account.js`) onto the helper. `grep -rn auth_events
src` finds no other writer. Covered by
`tests/api/auth_events/failures.test.js` "bounds attacker-controlled fields
to the database column sizes". `custom` is TEXT and unbounded
(`src/routes/personal_access_tokens.js:94` puts a raw uid into it; a 100 kB body is
over MySQL TEXT's 64 kB): a self-inflicted 500 at worst. MySQL and
PostgreSQL behaviour is source-reasoned, no server here.

## What is good

- The request-target gate (`src/create_app.js:119-126`) runs before the
  session and before the proxy; the WebSocket upgrade and the sidecar judge
  the same string with the same function. 36 raw and encoded shapes,
  `%2F`, `..;`, `%252e`, `%c0%ae`, NFD, the fullwidth solidus among them,
  were tried; the upstream received exactly the target it was judged on.
- The OAuth `state` carries the intent and is bound to the session that
  started the flow; the callback deletes it before the token exchange, so
  it cannot be replayed across sessions, after a sign-out, or twice. The
  classic login-CSRF link of an attacker's provider into the victim's
  account is stopped.
- A magic-link code is bound to the session that asked for it, not to a
  fingerprint; the per-address budget is counted in the database, so it
  holds across processes and restarts. The confirm step counts its
  failures in `auth_events`, the same way.
- One primary address per user and one account per provider per user are
  unique indexes, not application checks; the migrations fail cleanly on
  existing duplicates and `down` restores the previous shape (run on
  SQLite; MySQL and PostgreSQL read).
- The email-change ordering is sound in itself: the confirmation token is
  minted only at approval, the approval expires in 30 minutes and is single
  use, and `revoke_pending_tokens` reaches the approval row too.
- `set_forwarded_headers` sets For, Host, Proto and Port identically on
  HTTP and on a WebSocket upgrade, for every trust-proxy setting tried;
  the trust-proxy parser refuses `hops/0`, negatives, floats, the old
  booleans and mixed lists.
- The handover guard reads the identities, not the session: a verified
  provider or a second verified address stops it.
- `express_run` rejects on a failed listen and runs `ready` once; the
  WebSocket lease's timer never throws out of its callback; `cli()` exits
  1 on a rejected `main`.
- The new SPA views build their markup from fixed maps and take their
  redirect target from the server's status, never from a query parameter.
- `insert_auth_event` cuts by code point to the column sizes, and every
  writer of `auth_events` goes through it.
- The API suite, 610 cases, with a harness that spins the app per test,
  made the readers' 200 probe cases cheap to write.
