# Authwall penetration audit

Repository audit · 19 September 2026 · Authwall 1.15.0

## Executive assessment

Authwall has a solid base: session identifiers rotate at authentication boundaries, state-changing browser routes use session-bound CSRF tokens, one-time credentials are stored as hashes and consumed conditionally, password reset revokes sessions and personal access tokens, proxy identity headers are normalized and stripped, public-path matching rejects ambiguous paths, OAuth uses state and PKCE, and the application has unusually broad API coverage.

Two authorization/recovery defects remain serious enough to fix before treating the current release as hardened:

1. A pending email-change link survives password recovery. An attacker who briefly controls a session can request a change to an address they own, wait for the owner to recover the account, then use the old change link to replace the recovered address and reset the password again.
2. In sidecar mode, Authwall trusts `X-Original-URI` ahead of `X-Forwarded-Uri`. The shipped Caddy recipe supplies the latter but does not delete a client-supplied former header. With any public or optional-auth path configured, an anonymous client can describe a public path to the auth check while requesting a protected path from the upstream.

This audit records **23 open findings: 2 High, 14 Medium, and 7 Low**. Several medium and low items are operational or defense-in-depth gaps rather than direct account takeover. No Critical issue was found. Severity assumes the documented deployment patterns and the preconditions stated in each finding.

The application suites passed **179 unit tests and 517 API tests**. The browser result is recorded in the validation section. `npm audit` returned no High or Critical advisory and one Moderate transitive advisory. The two new High findings are source-confirmed and have direct, finite exploit sequences; the Caddy integration itself was not executed because Caddy is unavailable in this environment.

## High-priority findings

### H-01 · Pending email change can reverse password recovery

**Evidence:** [`password.js`](../src/routes/password.js#L326), [`email_change.js`](../src/routes/email_change.js#L102), [`complete_password_change.js`](../src/actions/complete_password_change.js#L12).

Password-reset confirmation changes the password, deletes unused reset tokens, deletes all sessions, and revokes PATs. It does **not** delete unused `email_change_tokens`. The ordinary authenticated password-change path also leaves those tokens alive. Email-change confirmation is an unauthenticated bearer-link route: possession of the link is sufficient, and it replaces the account's email with the token's already-approved address.

Exploit sequence:

1. The attacker briefly obtains a browser session, for example from a stolen cookie or unattended device.
2. The attacker requests an email change to `attacker@example` and retains the link delivered there.
3. The owner notices compromise and completes password recovery. Authwall revokes sessions and PATs, apparently settling recovery.
4. Before the 30-minute email-change link expires, the attacker opens it. Authwall replaces the owner's verified email with the attacker's address.
5. The attacker requests a password reset to the new address and takes the account again.

The owner receives a notification at the old address only after the change is committed. That notification does not prevent the takeover. The link's short lifetime limits the window but does not break the chain. This is High because it defeats the recovery boundary Authwall explicitly tries to establish.

**Remediation.** Inside the same transaction that completes either a password reset or a profile password change, delete all unused email-change tokens for the user. Consider invalidating email-verification and magic-link credentials tied to superseded identity state as part of one centralized `revoke_pending_credentials(user_id, reason)` operation. For especially sensitive deployments, require recent password/OAuth reauthentication before creating an email-change token.

**Acceptance tests.** Create a pending email-change link, complete password reset, and assert the link fails without altering the identity. Repeat for profile password change. Also assert recovery invalidates two concurrent change links and behaves consistently on SQLite, MySQL and PostgreSQL.

### H-02 · Sidecar authorization trusts a client-spoofable path header

**Evidence:** [`status.js`](../src/routes/status.js#L181), [`Caddyfile`](../docs/examples/authwall-sidecar-caddy/Caddyfile#L16), [`nginx.conf`](../docs/examples/authwall-sidecar-nginx/nginx.conf#L58).

`sidecar_original_path` selects `X-Original-URI` before `X-Forwarded-Uri`. Caddy `forward_auth` clones the incoming request, rewrites the auth request URI, and sets `X-Forwarded-Uri` to the real original URI. The shipped Caddy block does not remove or overwrite `X-Original-URI`. A client can therefore send:

```http
GET /private/admin HTTP/1.1
X-Original-URI: /favicon.ico
```

If `/favicon.ico` is a configured public path, Authwall evaluates that client header, returns `200` to Caddy without an identity, and Caddy continues the original protected request to the upstream. An optional-auth prefix works similarly. The nginx example is safer because it explicitly overwrites `X-Original-URI` in an internal location, but custom proxy configurations remain exposed unless they do the same.

Canonical-path checking does not help: the attacker supplies a perfectly canonical public path. The defect is the provenance of the path, not its syntax.

**Remediation.** Define one trusted header per supported integration and ensure the front proxy overwrites it. For the Caddy route, either consume only `X-Forwarded-Uri` or set a dedicated secret/internal header and remove all client copies. A safer contract is to reject requests containing both headers unless their canonical paths match. Restrict `/auth/sidecar` at the network/proxy layer so clients cannot call it directly.

**Acceptance tests.** Run the shipped Caddy example and request a private resource with spoofed `X-Original-URI`, `X-Forwarded-Uri`, mixed casing, duplicates and absolute-URI forms. Every protected request must be denied anonymously regardless of supplied client headers. Test public and optional paths separately.

## Medium-priority findings

### M-01 · Revoked sessions can be recreated by an in-flight save

**Evidence:** [`SessionStore.js`](../src/helpers/SessionStore.js#L52), [`sessions.js`](../src/routes/sessions.js#L26), [`password.js`](../src/routes/password.js#L326).

The store's `set` method is an upsert: `insert(...).onConflict('uid').merge(...)`. Revocation deletes a row. If a request loaded that session before deletion and later saves modified session state, `set` inserts the same authenticated session UID again. Routes that explicitly save session state include OAuth initiation, error handling, email-verification healing, and other account flows. The race also applies to the delete-all performed by recovery.

This requires request timing and a state-changing late save, so it is Medium rather than High, but it contradicts the documented immediate-revocation guarantee.

**Remediation.** Distinguish first creation from updates. An already-issued session must update an existing row and fail closed if the row was deleted. A per-user/session revocation generation checked on every save is more robust across process and database races. Add a deterministic test that pauses a request after load, revokes its session, releases the save, and confirms the row remains absent.

### M-02 · Last-identity check does not prove a usable credential remains

**Evidence:** [`make_oauth_flow.js`](../src/helpers/make/make_oauth_flow.js#L258), [`email_remove.js`](../src/routes/email_remove.js#L16).

OAuth disconnect refuses only when `identities.length <= 1`. A pending email without a password counts as an identity even though it cannot receive a magic-link sign-in or password reset. Disconnecting the only OAuth provider can strand the account. The email-removal route has more nuanced checks, but the decisions are not centralized and can disagree.

**Remediation.** Implement one predicate that determines whether at least one credential will remain usable under enabled flows, verification rules and access rules. Use it for every disconnect/removal action and expose its result to the SPA.

### M-03 · WebSocket admission does not refresh verification state

**Evidence:** [`create_app.js`](../src/create_app.js#L577), [`email_verification_required.js`](../src/helpers/email_verification_required.js#L1).

HTTP authorization heals an unverified session snapshot from the live identity table. WebSocket session admission checks only `custom.email_verified_at`. A user who verifies from another session can use HTTP immediately but receives `401` on the stale session's socket until they sign in again.

**Remediation.** Share the live verification decision across HTTP, sidecar, PAT and WebSocket admission, then update the session snapshot after a positive lookup.

### M-04 · Existing WebSockets outlive credential revocation

**Evidence:** [`create_app.js`](../src/create_app.js#L510).

Authentication occurs only during upgrade. Authwall keeps no user/session/token-to-socket registry and performs no later authorization check. Deleting a session, revoking a PAT, resetting a password or removing an account blocks new upgrades but leaves established proxied sockets usable until an endpoint closes them.

**Remediation.** Define the promised revocation latency. Register live sockets by credential and close them on session/PAT/account revocation, or impose a short reauthorization lease. Drain sockets during shutdown. Test traffic after each revocation event.

### M-05 · Profile password changes leave other durable credentials active

**Evidence:** [`complete_password_change.js`](../src/actions/complete_password_change.js#L12), [`personal_access_tokens.js`](../src/routes/personal_access_tokens.js#L28).

A profile password change rotates the current session, deletes other browser sessions, and invalidates reset links. It leaves PATs and pending email-change links active. Password reset does revoke PATs, so the two password-change paths offer materially different compromise containment without telling the user.

**Remediation.** Choose and document one credential-revocation policy. A secure default is to revoke PATs and pending identity-change credentials on every password change, with an explicit user choice only if preserving PATs is a product requirement. Record counts and reasons in auth events.

### M-06 · Email confirmation performs network I/O inside a transaction

**Evidence:** [`email_change.js`](../src/routes/email_change.js#L128), [`complete_email_change_confirm.js`](../src/actions/complete_email_change_confirm.js#L12).

The confirmation transaction deletes and inserts identities, then awaits delivery of the old-address notification and issues a redirect before the transaction returns. A slow provider holds database locks; a provider error rolls back a valid confirmation; the response can begin before commit succeeds.

**Remediation.** Commit token consumption and the identity swap first. Insert an outbox row in the same transaction, deliver asynchronously or after commit, and send the redirect only after the transaction resolves.

### M-07 · Expensive authenticated operations lack dedicated abuse controls

**Evidence:** [`password.js`](../src/routes/password.js#L341), [`profile.js`](../src/routes/profile.js#L101).

Both password-change paths perform bcrypt comparisons/hashes without a failure limiter. Avatar uploads accept up to 5 MB and invoke Sharp with no route concurrency limiter or application-selected pixel bound. Authentication reduces exposure but does not protect a shared service from a compromised or malicious account.

**Remediation.** Rate-limit current-password failures by user and client, cap concurrent image jobs, set an explicit Sharp pixel policy, and monitor saturation. Test limits without running destructive load against production.

### M-08 · Direct example accepts spoofed forwarded client addresses

**Evidence:** [`parse_trust_proxy.js`](../src/helpers/parse/parse_trust_proxy.js#L1), [`docker-compose.yaml`](../docs/examples/authwall-direct/docker-compose.yaml#L1).

The default trusts one proxy hop. The direct example publishes Authwall itself and does not set `AUTHWALL_TRUST_PROXY=false`, so a direct client controls the forwarded address used for per-IP throttles and audit attribution.

**Remediation.** Set `AUTHWALL_TRUST_PROXY=false` in the direct recipe. Proxy recipes should declare the exact hop count or trusted CIDRs and overwrite forwarded headers. Add a spoofed-header smoke test for each recipe.

### M-09 · Sentry spans are outside the sanitizer

**Evidence:** [`sentry.js`](../src/services/sentry.js#L69).

The sanitizer handles request URLs, selected request headers and breadcrumbs. It does not traverse `event.spans[].description` or span URL fields such as `data['url.full']`. One-time credentials carried in query parameters can therefore survive in transaction telemetry when tracing is enabled.

**Remediation.** Sanitize the actual Sentry transaction/span schema used by the installed SDK or drop URL-bearing span fields. Capture and inspect a representative serialized transaction before enabling tracing in production.

### M-10 · Sensitive records and logs have no retention lifecycle

**Evidence:** [`SessionStore.js`](../src/helpers/SessionStore.js#L25), [`make_logger_daily.js`](../src/services/logger/make_logger_daily.js#L27), database migrations in [`db/migrations`](../db/migrations/README.md).

Expired sessions and used/expired one-time rows are excluded from authentication but not purged. Auth events and daily logs have no configured retention. Sessions are touched frequently. This grows storage and preserves IP addresses, email identifiers and user agents longer than necessary.

**Remediation.** Add bounded cleanup jobs and supporting expiry indexes, define separate retention periods for security events and disposable credentials, rotate/delete logs, and throttle session touches.

### M-11 · Migration tooling does not select the runtime database

**Evidence:** [`package.json`](../package.json#L19), [`run_knex.js`](../bin/run_knex.js#L1), [`make_config.js`](../config/make_config.js#L470).

The npm migration scripts hard-code `--env=sqlite`, which points at `data/db.sqlite3` regardless of `AUTHWALL_DB`. The alternate helper immediately requires a missing `db/get_database_env` module and fails even for `--help`. The runtime image does not copy `bin/`.

**Remediation.** Provide one supported migration command using the same resolved configuration as startup, print a redacted target, package it where documentation says it exists, and test custom SQLite, MySQL and PostgreSQL targets.

### M-12 · CI does not validate the final container image

**Evidence:** [`master.yml`](../.github/workflows/master.yml), [`production.yml`](../.github/workflows/production.yml), [`trivy.yml`](../.github/workflows/trivy.yml#L21), [`Dockerfile`](../Dockerfile#L1).

CI tests source inside a Playwright image. Trivy scans the checkout as a root filesystem and cannot fail the workflow. The production image is built during deployment, after review-time gates. OS packages, copied runtime contents, ownership and startup behavior are therefore not validated as one artifact.

**Remediation.** Build the exact runtime image in pull-request CI, start it as the configured non-root user with a writable data mount, run a health/auth smoke test, and scan the image under an explicit severity and exception policy. Deploy the already-tested digest.

### M-13 · OAuth-only users cannot set a first password in the SPA

**Evidence:** [`spa.html`](../design/public_html/spa.html#L1934), [`password.js`](../src/routes/password.js#L359), [`set_first_password.test.js`](../tests/api/stories/set_first_password.test.js).

The server intentionally lets a verified user with no password set the first password without `current_password`. The SPA always requires and submits a current password, and status does not expose `has_password`. The backend capability is inaccessible through the normal UI.

**Remediation.** Expose a narrowly scoped capability such as `can_set_first_password`, render the correct form, and add an end-to-end OAuth-to-first-password test.

### M-14 · Network failures leave SPA actions unresolved

**Evidence:** [`spa.html`](../design/public_html/spa.html#L1267), [`spa.html`](../design/public_html/spa.html#L1901).

Sensitive action handlers set loading state, await fetch and status parsing, and clear the state only on the success path. A rejected request, invalid JSON, or failed status refresh skips cleanup and gives the user no reliable indication whether a password, token, session or identity action committed.

**Remediation.** Route actions through a common `try/catch/finally` wrapper, validate HTTP status before parsing, display a retry-safe outcome, and test offline, timeout and 5xx cases.

## Lower-priority findings

### L-01 · Reloaded sessions lose cookie attributes

**Evidence:** [`SessionStore.js`](../src/helpers/SessionStore.js#L35).

The stored JSON excludes `cookie`, and `get` reconstructs only `expires` and `maxAge`. Attributes such as `secure`, `sameSite`, `domain`, `path`, `httpOnly` and `originalMaxAge` do not round-trip through the store. No replacement cookie with weakened wire attributes was demonstrated in this pass, so this remains Low.

Persist and restore the full safe cookie policy, with migration defaults for existing rows, and assert the attributes after a session reload that causes `Set-Cookie`.

### L-02 · Identifier existence is exposed

**Evidence:** [`password.js`](../src/routes/password.js#L140), [`email_add.js`](../src/routes/email_add.js#L43).

Sign-up distinguishes existing emails/usernames, and email-add distinguishes an address registered to another account. This allows account enumeration. It is a common product tradeoff, but it matters when access rules are meant to keep membership private.

Use neutral responses where privacy is required and retain the specific reason only in audit events.

### L-03 · Coverage reporting can return success after a failed suite

**Evidence:** [`package.json`](../package.json#L29).

The coverage script separates test runs and report generation with semicolons, so its final status can be successful even if a suite failed. Colocated `*.test.js` files are not excluded by the current patterns.

Preserve failure codes with `&&` or a script that aggregates them, explicitly select production sources, exclude all tests, and enforce deliberate thresholds.

### L-04 · Patched dependency advisory is present but appears unreachable

**Evidence:** [`package-lock.json`](../package-lock.json), installed tree `@vbarbarosh/node-helpers -> csv-parse@7.0.1`.

`npm audit` reports GHSA-8cw4-87c7-c6xx / CVE-2026-85063, fixed in `csv-parse` 7.0.2. The vulnerable behavior requires parsing attacker-controlled CSV with `columns: true` and duplicate prototype-related columns. Authwall does not import the dependency's CSV helper; only an unused helper module in `@vbarbarosh/node-helpers` imports it. No application-reachable path was found.

Update the transitive package anyway, preferably by updating the direct helper dependency or its lock resolution, then rerun the production audit.

### L-05 · Documentation states stronger guarantees than the code provides

**Evidence:** [`security.md`](../docs/security.md), [`cli.md`](../docs/cli.md), [`deployment.md`](../docs/deployment.md).

The security page describes immediate session revocation without qualifying established WebSockets or the late-save race. Sidecar safety depends on trusted original-path headers but that provenance requirement is not prominent. CLI documentation describes commands absent from the runtime image. Runnable direct deployment guidance does not override the forwarded-IP trust default.

Update guarantees to state the boundary and latency precisely, then test documentation examples as release artifacts.

### L-06 · Builds and workflows are not fully reproducible

**Evidence:** [`Dockerfile`](../Dockerfile#L7), [`master.yml`](../.github/workflows/master.yml), [`package.json`](../package.json#L45).

The Docker base is a moving `node:24-alpine` tag, setup uses `lts/*`, GitHub Actions use mutable major tags, and `proxy-addr` is imported directly while installed only transitively. These are supply-chain and maintenance risks; no compromised dependency or workflow was found.

Pin reviewed digests/commits where practical, align test/runtime Node versions, declare direct imports, add explicit least-privilege workflow permissions, and automate controlled updates.

### L-07 · Keyboard and semantic support is incomplete

**Evidence:** [`spa.html`](../design/public_html/spa.html).

Several navigation/actions use click handlers or non-semantic elements without equivalent keyboard behavior and focus management. This can block recovery or session-revocation actions for keyboard and assistive-technology users.

Use links, buttons and forms with labelled status/error regions; test every account-security flow by keyboard.

## Controls that held

The following controls were rechecked and should be preserved with regression tests:

- Inbound `x-auth-*` and `x_auth_*` variants are stripped for HTTP and WebSocket proxying before Authwall sets its own identity header.
- Public and optional path rules operate on canonical paths and reject dot segments, encoded separators, backslashes, duplicate slashes and invalid encoding.
- Browser account-management routes require an authenticated browser session and CSRF token; PATs cannot administer the Authwall account.
- Session IDs and CSRF tokens rotate after sign-in, sign-up and password change.
- Password sign-in performs a dummy bcrypt comparison for unknown users.
- Password reset is sent only to verified identities, conditionally consumes one token, deletes sibling reset links, deletes sessions and revokes PATs.
- Magic-link and email-verification attempts use database-side bounded counters and conditional one-time consumption.
- OAuth flows bind state to the session and use PKCE; OAuth identities use stable provider subjects rather than email matching.
- Google, GitHub, Discord, X and Microsoft adapters distinguish provider-verified addresses with provider-specific signals. Live providers were not exercised.
- Bearer credentials are hashed at rest, checked for revocation/expiry, stripped before proxying and subject to email-verification policy.
- WebSocket browser sessions require a signed cookie and exact-origin match; bearer credentials are removed before upgrade forwarding.
- URL logging redacts token/code/state/secret/password-like query keys, and sensitive request headers are removed from Sentry request events.
- Avatar input is converted to WebP, uses a size limit, and temp files are cleaned after downstream failure.
- The runtime container uses a non-root user and explicitly copies runtime files instead of the whole build context.

## Suggested regression matrix

At minimum, add these cases before closing the two High findings:

| State transition | Concurrent/old credential | Expected result |
| --- | --- | --- |
| Password reset completes | Pending email-change link | Link rejected; email unchanged |
| Profile password change completes | Pending email-change link and PAT | Policy applied consistently and recorded |
| Session revoked | Request loaded before deletion then attempts save | Row remains deleted |
| PAT/session/account revoked | Already-open WebSocket | Connection closes within documented latency |
| Caddy private request | Spoofed `X-Original-URI` naming public path | Auth check rejects anonymous request |
| Caddy private request | Spoofed `X-Forwarded-Uri`, duplicates, mixed case | Trusted proxy value wins; request rejected |
| Email verified in another session | Existing session opens WebSocket | Same result as HTTP authorization |
| OAuth disconnect | Pending email/no password is the only other identity | Disconnect refused |

Run the state/race cases on SQLite, MySQL 5.7/8 and PostgreSQL because affected-row counts, transaction isolation and conflict behavior differ.

## Browser-suite result

`npm run test:e2e` scheduled 96 cases. All 64 Firefox and WebKit cases passed. All 32 Chromium cases failed before test execution with:

```text
browserType.launch: Executable doesn't exist at
/home/ubuntu/.cache/ms-playwright/chromium_headless_shell-1234/
chrome-headless-shell-linux64/chrome-headless-shell
```

This is an environment/browser-installation failure, not an application assertion failure. It also confirms the reproducibility concern in L-06: the local dependency tree and cached browser set are not sufficient to run the repository's default three-browser command after the Playwright update. CI's pinned Playwright container is expected to supply those executables, but that CI run was not independently observed in this audit.
