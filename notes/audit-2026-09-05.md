# Authwall project audit

Repository audit · 5 September 2026 · Version 1.15.0

## Executive assessment

Authwall has a strong functional baseline and substantial recent security improvements, but its remaining authorization and account-recovery defects warrant remediation before treating it as a hardened gateway for restricted applications.

This review identifies **23 findings: 3 High, 16 Medium, and 4 Low; no Critical finding was established**. Severity reflects the impact under the stated preconditions, not a claim that every deployment is exploitable. The highest priorities are email allowlists bypassed by username-only accounts, Microsoft email claims treated as verified authorization evidence, and password-reset credentials that survive recovery or an email change.

The existing suites passed **169 unit tests, 451 API tests, and 54 browser tests** across three browsers, with a temporary Chromium launch adjustment. Nine additional targeted probes reproduced defects that those suites do not catch. The production container built, loaded its native modules, served its health endpoint, and exited cleanly on SIGTERM.

This is an audit and remediation report. Application source was not changed.

## Architecture and positive controls

The main HTTP path is: request logging → static/health handling → session loading → optional PAT authentication → account routes → identity-header stripping and authorization → upstream proxy. Sidecar requests return an authorization decision to nginx/Caddy. WebSocket upgrades use a separate authentication path.

| Area | Controls observed |
| --- | --- |
| Identity boundary | Incoming `x-auth-*` headers are stripped on the built-in HTTP and WebSocket proxy paths; authenticated identity is set by Authwall. Public-path matching uses a canonicalization helper. |
| Browser sessions | Random signed session identifiers, server-side storage, regeneration at sign-in, random per-session CSRF tokens, and browser-only account-management endpoints. |
| Passwords and tokens | bcrypt password/code hashing; high-entropy tokens stored as hashes; sequential token-reuse checks; PAT revocation on password reset. |
| Email identity | Magic links refuse pending email identities; reset mail requires a verified address; many security notifications use verified recipients. |
| OAuth | Session-bound random state, PKCE plumbing, subject validation, explicit account connection, and prevention of implicit merging solely by matching email. |
| Input and rendering | Email/username validation, profile name limit, escaped identity/session/PAT rendering, avatar transcoding and temporary-file cleanup. |
| Response and telemetry | Auth-page security headers, `no-store` on status, HTTP query/Referer redaction, Sentry request/breadcrumb filtering, owner-only daily log files and logging failure fallback. |
| Packaging and CI | Lockfile, explicit runtime COPY list, deny-by-default Docker context, non-root image, production dependency audit, and SQLite/MySQL/PostgreSQL CI jobs. |

These controls are meaningful improvements over issues described in earlier notes. They do not resolve the cross-flow inconsistencies below.

## High-priority findings

### A01 · High — Username accounts bypass email allowlists

**Evidence:** [password.js:151](../src/routes/password.js#L151), [password.js:60](../src/routes/password.js#L60), [make_config.js:330](../config/make_config.js#L330).

Email access rules run only when the request supplies an email identity. Username registration and sign-in do not consult those rules. With username flow enabled and email verification disabled, an anonymous caller can register a username without an email and reach a protected upstream even when `allowed_emails` contains only a different address.

**Reproduction:** Set an allowlist containing `allowed@example.test`; submit username-only sign-up for `unlisted`. The probe obtained `authenticated: true` and a proxied response carrying an Authwall-generated `X-Auth-User`.

**Impact and limits:** This defeats the documented use of email allowlists to restrict registration in that configuration. Required email verification blocks the specific username-only path tested. Open registration without access rules is an intentional feature, not itself a finding.

**Remediation:** Define one account-authorization policy across enabled credential types. Either disallow username-only access when email rules exist, require a verified allowed email, or explicitly support a separate username allowlist. Reject contradictory configurations early.

**Acceptance:** Test every sign-up/sign-in flow against an email/domain allowlist, both with verification enabled and disabled.

### A02 · High — Microsoft email is treated as proof of mailbox control

**Evidence:** [oauth_provider_microsoft.js:61](../src/oauth_providers/oauth_provider_microsoft.js#L61), [authorize_oauth_verified_emails.js:17](../src/helpers/authorize_oauth_verified_emails.js#L17), [make_oauth_flow.js:182](../src/helpers/make/make_oauth_flow.js#L182).

The Microsoft adapter puts `user_info.email` into `verified_emails` solely because it is present. The common OAuth flow then uses it for email/domain authorization and can persist it with `verified_at`. The authority is the Microsoft `common` endpoint, rather than an explicitly restricted organization.

Microsoft documents that the email claim is mutable and must not be used for authorization; its UserInfo endpoint returns that email claim when available. See [Microsoft claim reference](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference) and [UserInfo documentation](https://learn.microsoft.com/en-us/entra/identity-platform/userinfo).

**Impact and limits:** Where a provider account can present an email not backed by the mailbox-control guarantee Authwall assumes, it may satisfy a restricted email policy and create a locally “verified” identity. The code path is confirmed; this audit did not create a real Microsoft tenant or execute a provider-side impersonation attack. This is not a claim that every Microsoft user can arbitrarily choose every email.

**Remediation:** Treat provider email as a suggested address until independently verified, or restrict tenants and authorize immutable provider identity/tenant identifiers with an explicit trust policy. Review Facebook's similar assumption separately; no blanket claim about Facebook verification was established here.

**Acceptance:** Provider responses lacking an explicit trusted verification basis must not satisfy email allowlists or produce locally verified email identities.

### A03 · High — Old reset credentials remain valid after recovery

**Evidence:** [password.js:284](../src/routes/password.js#L284), [complete_password_reset_confirm.js:14](../src/actions/complete_password_reset_confirm.js#L14), [email_change.js:127](../src/routes/email_change.js#L127).

Reset completion marks only the submitted token used. Other unused reset tokens for the account survive. Changing the account email also leaves old-address reset tokens valid because reset tokens refer to `user_id`, not the current email identity or credential version.

**Reproduction:** Two separately issued reset tokens both changed the password in sequence. In a second probe, a reset token issued to `before@example.test` still reset the account after the email changed to `after@example.test`.

**Impact and limits:** An attacker who already possesses another unexpired reset token can regain control after recovery or an email change. Reset tokens expire after ten minutes, which bounds this window; a token must first be obtained.

**Remediation:** Invalidate all outstanding recovery credentials after a successful reset and after relevant identity changes. Apply password update, reset-token invalidation and credential revocation in one transaction; issue notifications after commit.

**Acceptance:** Reusing the same token, a sibling token, or an old-address token must fail after recovery. Legitimate sign-in with the new password must still work.

## Medium-priority findings

### A04 · Medium — Concurrent requests can consume one token twice

**Evidence:** [password.js:284](../src/routes/password.js#L284), [magic_link.js:148](../src/routes/magic_link.js#L148), [email_verify.js:169](../src/routes/email_verify.js#L169).

Reset validation reads the row before bcrypt and before the transaction. The later update matches only its ID, without a `used_at IS NULL` condition or affected-row check. Two concurrent requests using the same token produced **two `password_reset_completed` events** in SQLite. This was not limited to a hypothetical MySQL race. Magic-link and email-verification paths also separate validation and consumption; attempt counters use read/modify/write.

Make consumption a conditional database operation inside the same transaction as its effect, and check that exactly one row changed. Increment bounded counters atomically. Add genuinely concurrent tests on all three backends. Only the reset race was executed here; other token families require dedicated race tests.

### A05 · Medium — Counting identities does not count usable credentials

**Evidence:** [make_oauth_flow.js:275](../src/helpers/make/make_oauth_flow.js#L275), [email_remove.js:34](../src/routes/email_remove.js#L34).

The disconnect guard checks the number of identity rows. A pending email is counted even when it cannot receive a magic-link login or reset, and an email may have no usable password. A probe constructed an OAuth account with a pending email and no password; disconnect removed the only OAuth identity and left only the unverified email.

Determine whether a remaining credential can actually authenticate under the enabled flows. Check verified state, password presence, provider availability and verification requirements. Apply that shared decision to disconnect/removal operations and the UI. Test recovery without relying on a still-active browser session.

### A06 · Medium — Session serialization drops cookie policy and lifetime metadata

**Evidence:** [SessionStore.js:41](../src/helpers/SessionStore.js#L41), [SessionStore.js:57](../src/helpers/SessionStore.js#L57), installed `express-session/session/store.js:86`.

The store removes the cookie from stored custom data and reconstructs only `expires` and `maxAge`. The original `secure`, `sameSite`, `domain`, `path`, and `originalMaxAge` do not round-trip. This was reproduced with Secure/domain configuration.

**Important limit:** The tested follow-up response emitted no replacement cookie; this audit did **not** demonstrate Secure being stripped from a browser cookie on the wire. The installed session library resets `originalMaxAge` from the omitted field, affecting subsequent cookie lifetime handling. The store violates the library's serialization contract even though existing tests pass because they inspect only initial cookie issuance.

Persist/restore the complete cookie metadata, with a migration/fallback for existing rows. Test several requests, mutation, expiry, domain/path scoping and cookie attributes after reloading the stored session. [Express session documentation](https://expressjs.com/en/resources/middleware/session/) describes these independent cookie settings.

### A07 · Medium — WebSocket URL logging bypasses redaction

**Evidence:** [create_app.js:513](../src/create_app.js#L513), [create_app.js:526](../src/create_app.js#L526).

HTTP request logging uses `urlxxx`; WebSocket accept/reject logs use `JSON.stringify(req.url)`. A rejected upgrade to `/realtime?token=AUDIT_SYNTHETIC_TOKEN` preserved that marker in the logs. Query strings can contain upstream application credentials even though Authwall itself authenticates WebSockets using cookies or a bearer header.

Use the same URL redactor on every upgrade log, and safely encode extracted fields such as `requested_user`. Test accepted and rejected upgrades with token/code/state queries. No real token was exposed by the audit.

### A08 · Medium — WebSockets do not refresh email-verification state

**Evidence:** [create_app.js:603](../src/create_app.js#L603), [email_verification_required.js:12](../src/helpers/email_verification_required.js#L12).

HTTP authorization heals an unverified session snapshot from the live database. WebSocket authorization checks only the snapshot. A verified account with a stale session received 401 on upgrade; after an ordinary protected HTTP request, the same session received 101.

Use a shared live verification decision for HTTP, sidecar, PAT and WebSocket admission. Add a story that verifies email in another session and immediately reconnects a WebSocket.

### A09 · Medium — Existing WebSockets survive session revocation

**Evidence:** [create_app.js:511](../src/create_app.js#L511), [express_run.js:26](../src/helpers/express/express_run.js#L26).

Authentication occurs at upgrade and no connection registry links live sockets to revoked credentials. A socket continued echoing messages after its user's session rows were deleted. New upgrades are rejected; already-established upstream access continues.

Define the intended revocation guarantee and either close associated sockets on session/token/account revocation or enforce a bounded reauthorization interval. Track upgraded sockets during shutdown as well: the shutdown implementation calls `server.close()` and has a ten-second forced exit, but does not explicitly drain upgraded sockets. An active-WebSocket shutdown was not executed; the idle HTTP shutdown passed.

### A10 · Medium — Expired rows and logs have no retention lifecycle

**Evidence:** [SessionStore.js:28](../src/helpers/SessionStore.js#L28), [SessionStore.js:80](../src/helpers/SessionStore.js#L80), [session migration](../db/migrations/20260313201917_sessions.js), [make_logger_daily.js:32](../src/services/logger/make_logger_daily.js#L32).

Expired sessions are excluded from reads but not periodically deleted. There is no repository-provided scheduled cleanup for expired/used token rows, auth-event retention or old daily logs. Anonymous auth sessions now have a 24-hour lifetime, but expiry does not reclaim their rows. Authenticated HTTP sessions also update expiry/last-seen on every request.

Provide bounded batch cleanup with appropriate expiry indexes and documented retention, distinguish security-event retention from disposable session/token data, and throttle session touches. Add monitoring for table size, write load and log volume. No storage exhaustion or production growth rate was measured.

### A11 · Medium — Email change holds a transaction across network delivery

**Evidence:** [email_change.js:127](../src/routes/email_change.js#L127), [complete_email_change_confirm.js:17](../src/actions/complete_email_change_confirm.js#L17).

The email-change transaction deletes/inserts identities and calls a completion helper that awaits email delivery before commit. A slow or failing provider prolongs locks or rolls back an otherwise valid identity change. The helper also initiates a redirect before the transaction callback has returned.

Commit the identity change and token consumption first. Send notification afterward, preferably through a transactional outbox with retries. Test provider timeout and failure while an unrelated request accesses the database.

### A12 · Medium — Direct examples keep spoofable forwarded-IP defaults

**Evidence:** [parse_trust_proxy.js:9](../src/helpers/parse/parse_trust_proxy.js#L9), [direct compose example:8](../docs/examples/authwall-direct/docker-compose.yaml#L8), [docker-compose.yaml](../docker-compose.yaml).

The default trusts one proxy hop, while the direct example publishes Authwall itself and does not set `AUTHWALL_TRUST_PROXY=false`. A directly connected client can supply the forwarded address used for per-IP throttles and audit attribution. The security documentation correctly warns about this; the runnable examples do not implement its instruction.

Set direct recipes to trust no proxy. For proxy recipes, set an explicit trust boundary matching reachable hops and test spoofed forwarded headers. This finding concerns a documented deployment configuration, not deployments that already restrict reachability and configure trust correctly.

### A13 · Medium — Expensive authenticated operations lack abuse limits

**Evidence:** [password.js:312](../src/routes/password.js#L312), [profile.js:37](../src/routes/profile.js#L37), [profile.js:120](../src/routes/profile.js#L120).

Both password-changing paths can repeatedly run bcrypt without a dedicated failure limiter. The profile route can decode/resize a 5 MB upload without a route-level concurrency or request limiter. File-size limits do not bound decoded image work; Sharp does have its own default pixel limit, so this is not an assertion of unlimited decoding.

Throttle password failures by account and client, bound concurrent image processing, and choose an application-appropriate explicit pixel limit. Test enforcement on both profile and change-password routes. No resource-exhaustion load test was performed.

### A14 · Medium — First-password support is missing from the SPA

**Evidence:** [spa.html:1923](../design/public_html/spa.html#L1923), [password.js:329](../src/routes/password.js#L329), [set_first_password.test.js](../tests/api/stories/set_first_password.test.js).

The server permits a verified OAuth user with no password to set one without a current password. The SPA unconditionally requires `current_password` before sending the request. The backend story passes, but the corresponding browser workflow is blocked.

Expose an explicit `has_password`/action capability in status and render a first-password form accordingly. Add an end-to-end test beginning with an OAuth account without a password.

### A15 · Medium — Network failures leave SPA actions unresolved

**Evidence:** [spa.html:1193](../design/public_html/spa.html#L1193), [spa.html:1855](../design/public_html/spa.html#L1855), [spa.html:1886](../design/public_html/spa.html#L1886).

Common handlers set a button to loading, await fetch/status parsing, then clear loading only on success. A rejected fetch or invalid JSON skips recovery. Shared helpers also generally do not validate HTTP success before interpreting the response.

Use a common action wrapper with `try/catch/finally`, explicit response-status validation, a visible error and a retry path. Test offline requests, upstream 500 responses and a failing `/auth/status`. This was established by control-flow inspection rather than an interactive outage test.

### A16 · Medium — Migration tooling does not follow runtime database selection

**Evidence:** [package.json:22](../package.json#L22), [knexfile.js:14](../knexfile.js#L14), [bin/run_knex.js:4](../bin/run_knex.js#L4), [Dockerfile](../Dockerfile).

The npm migration and rollback scripts hard-code `--env=sqlite`; that Knex configuration points to `data/db.sqlite3`, independent of the runtime's resolved `AUTHWALL_DB`. The apparent alternative helper requires the nonexistent `db/get_database_env` and fails even for `--help`. The image excludes `bin/` although the CLI docs describe commands inside the container.

Wire one supported migration command to the same resolved configuration as startup, print the selected non-secret target, and package/document the commands actually supported. Test custom SQLite paths plus MySQL/PostgreSQL selection. No migration or rollback was run against existing project data.

### A17 · Medium — Coverage reporting can hide failures and includes tests

**Evidence:** [package.json:29](../package.json#L29), [package.json:37](../package.json#L37).

The coverage script separates unit tests, API tests and report generation with semicolons. Its final exit code can be the successful report's even if a suite failed. The exclusions omit `**/*.test.js`, so colocated unit-test bodies are measured as application code.

Using the same captured run, repository settings yielded 94.19% statements / 87.46% branches; excluding test files yielded 92.74% / 85.45%. Neither is a measure of all source because config and migrations are excluded and unexecuted entrypoints may be absent.

Preserve test failure exit codes, exclude all test files, explicitly define the coverage source set, and add appropriate thresholds. Verify the command returns nonzero for an intentionally failing fixture.

### A18 · Medium — Sentry span redaction is incomplete

**Evidence:** [sentry.js:69](../src/services/sentry.js#L69).

The transaction hook calls the sanitizer, but that sanitizer only visits `request` and `breadcrumbs`. It does not visit `event.spans[].description` or URL fields in span data. A synthetic transaction containing a token in `spans[].data['url.full']` and `description` was returned with the marker intact.

Sanitize the SDK's actual transaction/span URL fields, or disable/drop fields that cannot be reliably filtered. Capture a representative outgoing HTTP span and verify the serialized payload before enabling tracing. The sanitizer gap was executed; live Sentry transmission of a credential was not demonstrated.

### A19 · Medium — Runtime image validation is missing from CI gates

**Evidence:** [master.yml](../.github/workflows/master.yml), [production.yml](../.github/workflows/production.yml), [trivy.yml:22](../.github/workflows/trivy.yml#L22), [bin/deploy](../bin/deploy).

CI tests source in a Playwright environment. The production image is built during deploy, and the Trivy job scans the checkout as a root filesystem with exit code zero. It does not establish the vulnerability state of the final Node/Alpine image. npm audit covers the dependency advisory database, not the runtime operating-system packages.

Build the actual runtime image in PR CI, smoke-test it as its configured user with a writable data mount, and scan that image. Use a deliberate severity/exception policy for the scan gate. The local build and startup succeeded; this finding is a missing regression and supply-chain gate, not a current build failure.

## Lower-priority findings

### A20 · Low — Keyboard navigation gaps

[spa.html:491](../design/public_html/spa.html#L491), [spa.html:595](../design/public_html/spa.html#L595), and numerous profile/footer controls use clickable `span` elements without link/button semantics or keyboard focus. Most non-sign-in workflows use click handlers rather than actual forms.

Use semantic links/buttons, real forms and labelled error regions. Validate keyboard-only completion of reset, magic-link, profile and sign-out flows, including focus after view changes. No full accessibility conformance or contrast audit was performed.

### A21 · Low — Browser harness depends on local state

[playwright.config.js:89](../playwright.config.js#L89) reuses an existing server outside CI and defaults to a shared `/tmp/authwall-e2e.sqlite3` file. This can test an unrelated local process or share accounts across runs. The local cache also lacked the headless-shell executable expected by default.

Use unique per-run database/port/output paths and an explicit owned server. Document browser installation and keep package/image versions synchronized. The temporary audit configuration disabled reuse, selected an isolated database and used installed full Chromium; all 54 browser cases then had passing results.

### A23 · Low — Reproducibility and dependency ownership gaps

[Dockerfile](../Dockerfile) uses a moving `node:24-alpine` base; CI uses `lts/*` while the runtime is Node 24, and actions are referenced by mutable version tags. Master/release workflows do not declare an explicit least-privilege `permissions` block. [create_app.js:32](../src/create_app.js#L32) imports `proxy-addr` directly even though it is only installed transitively.

Pin deliberate runtime/test versions and image digests, pin actions to reviewed commit SHAs, set explicit permissions and declare direct imports as direct dependencies. This is a maintenance/supply-chain concern; no malicious dependency or compromised workflow was found.

## Reproduction ledger

These probes were created outside the repository, used the existing API harness with fresh SQLite data, and asserted the observed defective behavior.

| Probe | Observation |
| --- | --- |
| Username-only sign-up + email allowlist + verification off | Protected upstream returned an identity-bearing response. |
| OAuth disconnect + pending email + no password | Last OAuth credential removed; only pending email remained. |
| Secure/domain cookie round-trip | Stored session returned no secure/sameSite/domain/originalMaxAge metadata; follow-up response did not issue a replacement cookie. |
| Two pending reset tokens | Both reset the password sequentially. |
| Reset token issued before email change | Still reset the account after the address changed. |
| Two simultaneous requests with one reset token | Two successful password-reset events. |
| Rejected WebSocket with synthetic query token | Raw marker appeared in upgrade log. |
| Established WebSocket followed by session-row deletion | Socket still exchanged messages. |
| Verified email with stale WebSocket session snapshot | Upgrade returned 401, then 101 after an ordinary HTTP request healed the snapshot. |

Additional checks established the broken migration helper, unchanged synthetic Sentry span fields and coverage inflation. No proof-of-concept was run against a remote deployment.

A minimal recipe for the token race is to create a test user, issue one reset link, obtain CSRF/cookies for two independent clients, POST the same token concurrently with two different new passwords, then count successful reset events. The acceptance condition after a fix is exactly one success.
