# Authwall project audit

Date: 2026-07-27
Scope: repository at `/app`, version `1.14.0`, commit `aa9a4dc` (branch `master`)
Method: full source read + empirical reproduction against the project's own API test harness

## TLDR

Authwall's security *design* is good — server-side revocable sessions, per-session CSRF tokens,
timing-safe comparison, hashed one-time tokens, OAuth state + PKCE, `x-auth-*` stripping on both HTTP
and WebSocket paths. The *implementation* has four confirmed defects that break either the
authorization boundary or a headline feature, plus a dependency tree that CI cannot fail on.

Verdict: **not ready to be trusted as an authentication boundary without Phase 1 remediation.**

- 🔴 `/auth/sidecar` returns `200 + X-Auth-User` for users the proxy path redirects to email
  verification — an authorization bypass in both documented sidecar topologies. *(Reproduced)*
- 🔴 **GitHub sign-in permanently breaks on the second login.** GitHub returns a numeric `id`; the
  identity lookup binds it unnormalized, matches nothing on SQLite, and the fallback sign-up hits a
  unique constraint. *(Reproduced — new, not in prior audits)*
- 🔴 Live magic-link tokens and Google OAuth codes sit in cleartext in `data/logs/*.log` **right
  now**. *(Verified against real log files)*
- 🔴 A filesystem error on the default daily logger crashes the whole proxy. *(Reproduced)*
- 🔴 14 known vulnerable production dependencies (6 high) — 13 fixable non-breaking. Trivy runs with
  `exit-code: 0`, so CI never fails on them.
- 🟠 OAuth-only users **cannot set an initial password** — `bcrypt.compare(x, null)` throws and they
  get `An error occurred [req_…]`. *(Reproduced — new)*
- 🟠 `AUTHWALL_WEBSOCKETS=0` and `AUTHWALL_PERSONAL_ACCESS_TOKENS=0` **enable** those features. So
  does any unrecognized value. *(Reproduced)*
- 🟠 Avatar temp files leak on every CSRF rejection and every undecodable upload. *(Reproduced)*

Most findings from `audit-2026-07-10.md` are still open: the only commits since then touched
Docker, CI, and docs. This audit re-verifies them against current code and adds five new ones (H2,
M1, M4, M5, and the boolean-parsing generalization in M3).

## High severity

### H1. `/auth/sidecar` bypasses required email verification

**Description.** `sidecar_get` resolves a session or PAT to a user and immediately returns `200` with
`X-Auth-User`. It never calls `email_verification_required`. Every other authenticated path does:
the HTTP proxy at `src/create_app.js:374`, PAT auth at `src/create_app.js:419-423`, and browser
WebSocket auth at `src/create_app.js:580-582`.

**Impact.** In the two deployment topologies the project documents as first-class —
`docs/examples/authwall-sidecar-nginx/` (nginx `auth_request`) and
`docs/examples/authwall-sidecar-caddy/` (Caddy `forward_auth`) — a signed-in user with an unverified
email reaches the protected application even with `AUTHWALL_CONFIRM_EMAIL_REQUIRED=true`. This is a
direct authorization bypass, and `docs/security.md` never mentions that sidecar mode checks less
than the proxy path.

**Severity:** High — authorization bypass in a supported topology.

**Location:** `src/routes/status.js:169-185`.

**Verification (reproduced).** With `config.confirm_email.required = true`, sign up with
email + password and do not verify:

```
authenticated            : true
email verified_at        : null
GET /some/protected/path -> 302 location="/auth/email-verify?return=%2Fsome%2Fprotected%2Fpath"
GET /auth/sidecar        -> 200 x-auth-user="awuser_nsgbhf1dpvgxnk73a2qkw7ag"
```

**Expected:** `/auth/sidecar` returns `403` (or `401`) for a user the proxy path would hold at
verification.
**Actual:** `200` plus the identity header the reverse proxy copies onto the upstream request.

**Remediation.** In `sidecar_get`, after resolving the user, apply the same gate the proxy uses:

```js
if (!req.auth?.personal_access_token_uid && email_verification_required(req)) {
    res.status(403).send();
    return;
}
```

Add an API test asserting sidecar and proxy agree for an unverified user. Longer term, extract the
single "is this request authorized?" decision so proxy, sidecar, PAT, and WS paths cannot drift
again — the drift is the root cause, not the missing line.

### H2. Repeat GitHub sign-in fails permanently (unnormalized numeric subject) — NEW

**Description.** `callback_get` looks up the provider identity with the raw `user_info.sub`:

```js
const ident = await db('user_identities').where({
    type: oauth_provider.user_identity_type,
    value_normalized: user_info.sub,          // ← raw
}).first();
```

but every write stores `String(user_info.sub)` (`src/helpers/make/make_oauth_flow.js:99, 127, 199,
229`). `oauth_provider_github.fetch_user_info` sets `sub: user_info.id`, and the real GitHub API
returns `id` as a **JSON number** (`"id": 583231`). SQLite does not apply TEXT affinity to a bound
integer parameter, so the lookup against the TEXT column never matches:

```
stored typeof(v) : text
where v = 583231 (literal) : [ { v: '583231' } ]
where v = ?      (bound 583231) : []          ← no match
where v = ?      (bound '583231') : [ { v: '583231' } ]
```

The miss sends the returning user down the sign-up branch, which inserts
`String(sub)` — colliding with `unique(['type','value_normalized'])`.

**Impact.** A GitHub user can sign in exactly once. Every subsequent attempt fails with an opaque
`An error occurred [req_…]` and they are locked out of that identity forever. On MySQL the same
comparison silently coerces the column to a number, which makes the index unusable (full scan) and
matches on numeric prefixes.

**Severity:** High — total loss of a headline sign-in flow, plus a cross-backend correctness hazard.

**Location:** `src/helpers/make/make_oauth_flow.js:76-79`; `src/oauth_providers/oauth_provider_github.js:66`.

**Why the suite misses it.** Every GitHub fixture uses a **string** id — `tests/mock_github.js:15`
uses `id: 'github-user-123'` and `tests/api/stories/github_no_email.test.js:6` defaults to
`id = 'github-sub-123'`. The mocks encode a payload GitHub never sends.

**Verification (reproduced).**

```
PROBE A — numeric id 583231 (what GitHub actually returns)
  first  sign-in -> authenticated=true  user_uid=awuser_m2i084g2iazreflerpnwhm9a
  identities stored: [ '583231 (string)' ]
  second sign-in -> authenticated=false user_uid=undefined
                    error="An error occurred [req_lk7kwrj7vucq57641i5tbb2g]"

PROBE B — string id 'github-user-123' (what the mocks use)
  first  sign-in -> authenticated=true  user_uid=awuser_z31y4vnpzi3mat4p5y01i3st
  second sign-in -> authenticated=true  user_uid=awuser_z31y4vnpzi3mat4p5y01i3st   ← passes
```

**Expected:** the second sign-in resolves to the same user.
**Actual:** unique-constraint violation surfaced as a generic error.

**Remediation.**
1. Normalize once at the provider boundary — have each `fetch_user_info` return `sub: String(...)`,
   and validate it is a non-empty string before use (an unvalidated `sub` of `null` would become the
   identity `'null'` and collide across users).
2. Use the normalized value for the lookup as well as the insert.
3. Change the fixtures to numbers: `tests/mock_github.js` and the `github_no_email.test.js` default.
   Add a regression test that signs in twice with a numeric id.

### H3. Secret-bearing request URLs are written to logs in cleartext

**Description.** The request logger records the full URL including the query string:

```js
logger.write(`[req_begin] ${req.method} ${JSON.stringify(req.url)} …`);
```

Magic-link tokens, email-verify tokens, email-change tokens, and OAuth authorization codes all
travel as query parameters.

**Impact.** Anyone with log read access — an operator, a log shipper, a backup, a mounted volume —
holds working single-use sign-in credentials. A magic-link token in the log is a complete
authentication bypass for that account until it expires or is used.

**Severity:** High — credential disclosure to a lower-trust store.

**Location:** `src/create_app.js:66`; sinks `src/services/logger/make_logger_daily.js`,
`make_logger_stdout.js`.

**Verification.** Real entries present in this working tree today:

```
[req_begin] GET "/auth/magic-link/confirm?token=cf0bbd31074e5df6c4f27b7cd433fb409f94fa858c27f446243854a49689714a"
[req_begin] GET "/auth/google/callback?state=login_otk27xkeoy70fs8x&iss=…&code=4%2F0Aci98E_3tEd_b5i3QTj4l3QXxTHL1yQQRlGrdwdf3eL1_o5g7BIfu0Hesp97pEL3vb4E_g&…"
```

Reproduce: `grep -rhoE '\[req_begin\] GET "[^"]*token=[^"]*"' data/logs/`.

**Expected:** sensitive query parameters redacted before the line is written.
**Actual:** verbatim tokens and OAuth codes on disk.

**Remediation.** Redact in the logger, not at each call site. `src/services/sentry.js` already has
the right predicate (`is_sensitive_query_param` — `token`, `secret`, `password`, `code`, `state`);
lift it into a shared helper and apply it to `req.url` in the `[req_begin]` line, the
`[error_handler]` details, and the `[proxy_error]` line. Note that the existing `data/logs/*.log`
files must be treated as compromised and rotated.

### H4. A logger filesystem error terminates the process

**Description.** `make_logger_daily` creates a write stream and never attaches an `'error'`
listener:

```js
stream = fs.createWriteStream(file, {flags: 'a'});
stream.write(`[${new Date().toJSON()}]${s}\n`);
```

An unhandled `'error'` event on an `EventEmitter` is thrown as an uncaught exception.

**Impact.** Disk full (`ENOSPC`), a permissions change on the volume, or a removed mount takes down
the auth proxy — and with it every application behind it. `daily` is the default logger
(`config.logger` falls through to `make_logger_daily` in `src/index.js:70-75`); the Docker image
sets `AUTHWALL_LOGGER=stdout`, so this hits non-Docker and custom deployments hardest.

**Severity:** High — availability of the entire trust boundary depends on log writes succeeding.

**Location:** `src/services/logger/make_logger_daily.js:29-33`.

**Verification (reproduced).**

```
$ node -e "const fs=require('fs');const s=fs.createWriteStream('/proc/1/nonexistent-dir/app.log',{flags:'a'});s.write('hello\n');setTimeout(()=>console.log('alive'),300)"
Error: ENOENT: no such file or directory, open '/proc/1/nonexistent-dir/app.log'
Emitted 'error' event on WriteStream instance at:
    at emitErrorNT (node:internal/streams/destroy:170:8)
Node.js v24.14.1
```

The process dies; `alive` never prints.

**Expected:** a log write failure degrades logging, not availability.
**Actual:** uncaught exception, process exit.

**Remediation.** Attach `stream.on('error', …)` that reports once to stderr and falls back to stdout
for the remainder of the day-file. Also handle the rotation edge: `stream?.end()` on day change is
fire-and-forget, and `stream.write()`'s backpressure return value is ignored, so a slow disk buffers
without bound.

### H5. Production dependency tree carries 14 known vulnerabilities, and CI cannot fail on them

**Description.** `npm audit --omit=dev` reports 6 high and 8 moderate. Several sit directly in the
request path of an auth proxy:

| Package | Severity | Fix |
|---|---|---|
| `axios` | high | `npm audit fix` |
| `brace-expansion` | high | `npm audit fix` |
| `form-data` | high | `npm audit fix` |

13 of 14 are fixable without a breaking change.

**Impact.** Known-exploitable code in the proxy, the multipart parser, and the HTTP client of a
security boundary. `multer`'s two advisories are both DoS; `sharp`'s are inherited libvips CVEs
reachable from the avatar upload path (which, per M2, already accepts arbitrary bytes).

**Severity:** High — cumulative, and structurally invisible.

**Location:** `package.json`, `package-lock.json`; `.github/workflows/trivy.yml:24`.

**Remediation.**
1. `npm audit fix` — clears 13.
2. Bump `sharp` to `^0.35.3` separately and run the avatar tests (the resize/webp API is unchanged

3. Add `npm audit --omit=dev --audit-level=high` as a CI step, and set `exit-code: 1` on Trivy.
   Without this, the fix regresses in a month.

### H6. Microsoft and Facebook emails are treated as verified without proof

**Description.** `authorize_oauth_verified_emails` and the identity writer both trust
`user_info.verified_emails`. Google gates on `email_verified`; GitHub gates on the per-address
`verified` flag. Microsoft and Facebook do not gate at all:

```js
// oauth_provider_microsoft.js:64
verified_emails: [user_info.email].filter(Boolean),
// oauth_provider_facebook.js:59
verified_emails: [user_info.email].filter(Boolean),
```

Those addresses are then inserted with `verified_at: now` and are what the allow/deny rules are
evaluated against.

**Impact.** With `AUTHWALL_ALLOWED_DOMAINS=corp.example.com`, an attacker who can get an unverified
`corp.example.com` address onto a Microsoft or Facebook account passes the access rules and lands
inside. `docs/security.md` states the rules are "checked against the provider's verified emails" —
which is true for Google and GitHub and false for these two.

**Severity:** High when access rules are in use; Medium otherwise.

**Location:** `src/oauth_providers/oauth_provider_microsoft.js:64`,
`src/oauth_providers/oauth_provider_facebook.js:59`.

**Remediation.** Either require an explicit verification signal (Microsoft: prefer the `xms_edov`
claim on the id_token where the tenant emits it) or stop marking these identities `verified_at` and
route them through the normal email-verification flow. Whichever you choose, correct the claim in
`docs/security.md` — right now the doc is stronger than the code.

## Medium severity

### M1. OAuth-only users cannot set an initial password — NEW

**Description.** Both password-change entry points compare against a possibly-`null` hash:

```js
const ok = await bcrypt.compare(current_password, user.password_hash);
```

For a user created through OAuth, `users_create` leaves `password_hash` as `null`, and
`bcrypt.compare(x, null)` **throws** `data and hash arguments required` — not a `UserFriendlyError`,
so `error_handler` replaces it with `An error occurred [req_…]`.

The guard above it says *"Cannot set or **set** or change password without a verified email or
username"*, which implies setting an initial password is supported. It is not: `current_password` is
mandatory, and there is no value that satisfies a `null` hash.

**Impact.** A user who signed up with Google/GitHub and later wants a password (e.g. to stop
depending on the provider) cannot get one, and the failure message tells them nothing. Each attempt
also raises a non-`UserFriendlyError` into Sentry as a real exception — recurring noise that masks
genuine faults.

**Severity:** Medium — broken advertised capability + opaque failure + error-reporting noise.

**Location:** `src/routes/password.js:338`; `src/routes/profile.js:88` (same defect, second path).

**Why the suite misses it.** `tests/api/stories/github_no_email.test.js` has a test named *"can set a
password after connecting Google with a verified email"* — but it posts `current_password: ''`,
which trips the `Missing fields` guard first, and then only asserts the error is **not** the
identity error. It never sets a password. The name promises coverage the body does not deliver.

**Verification (reproduced).** GitHub sign-in with a verified email, then set a password:

```
providers            : [ 'oauth_github:verified', 'email:verified' ]
password_hash        : null
error shown to user  : "An error occurred [req_vpnom1n6zmfio2sjuh9lfnr7]"
```

**Expected:** a passwordless user can set an initial password without supplying `current_password`.
**Actual:** generic error; no password is ever set.

**Remediation.** Branch on `user.password_hash === null`:

```js
if (user.password_hash === null) {
    // initial password: nothing to verify against
}
else if (!await bcrypt.compare(current_password, user.password_hash)) {
    throw new UserFriendlyError('Current password is incorrect');
}
```

Require `current_password` only when a hash exists, and have `GET /auth/status` expose whether the
user has a password so the SPA can hide the field. Fix the misleading test to actually set and then
sign in with the new password.

### M2. Avatar temp files leak on CSRF rejection and undecodable uploads

**Description.** Multer must run before `csrf_middleware` (it populates `req.body`, which the CSRF
check reads — the ordering is deliberate and correctly commented). But the temp file is only removed
inside the handler, after `sharp` succeeds:

```js
await sharp(req.file.path).resize(256, 256, {fit: 'cover'}).webp({quality: 90}).toFile(avatar_path);
await fs_rm(req.file.path);
```

Two paths skip the `fs_rm`: a CSRF failure (handler never runs) and a `sharp` throw. The
`fileFilter` only checks the **client-declared** `file.mimetype`, so any 5 MB blob labelled
`image/png` reaches `sharp` and takes the second path.

**Impact.** Unbounded growth of `data/temp-uploads` from unauthenticated-ish requests — an
authenticated user, or anyone who can trigger a CSRF failure, appends 5 MB per request with no
cleanup anywhere in the codebase. Eventually fills the volume, which (see H4) then crashes the
process.

**Severity:** Medium — disk exhaustion reachable by any signed-in user.

**Location:** `src/routes/profile.js:22-40, 76-81`.

**Verification (reproduced).**

```
CSRF-rejected upload : temp files 2 -> 3
undecodable upload   : temp files 3 -> 4
  error shown to user = "An error occurred [req_uxdz1jgiwyys3z6z0bb4pn7q]"
```

Two orphaned files were already present in `data/temp-uploads/` before the probe ran.

**Expected:** every request path removes its temp file.
**Actual:** two common paths leak it; nothing ever sweeps the directory.

**Remediation.** Wrap the handler body in `try/finally` and `fs_rm(req.file.path)` in the `finally`;
add an error-handling middleware after the multer stack that removes `req.file` on any failure.
Validate real image bytes (`sharp().metadata()`) rather than the declared mimetype, and surface a
`UserFriendlyError('Invalid image')` instead of the generic error.

### M3. `0` and unrecognized values silently *enable* boolean flags

**Description.** `parse_bool_flag` maps only six spellings and passes anything else through, where
the `bool` coercion treats every non-empty string as true:

```js
return {yes: 1, no: 0, true: 1, false: 0, on: 1, off: 0}[value] ?? value;
```

**Impact.** `0` is the single most likely "off" value an operator will reach for — and this codebase
*trains* them to: `AUTHWALL_RATE_LIMITING` is special-cased so that `0` disables it, and
`docs/config.md:164` documents exactly that. Applying the same habit elsewhere turns the feature
**on**. `AUTHWALL_PERSONAL_ACCESS_TOKENS=0` exposes the entire bearer-token authentication surface an
operator believed was disabled; `AUTHWALL_WEBSOCKETS=0` opens the WebSocket proxy path.

There is no validation, so typos fail open too — `disabled`, `FALSE`, `False`, `nope` all enable.
Note `make_config` *does* hard-fail on an unknown `AUTHWALL_*` **name**, which makes the silent
acceptance of an unknown **value** inconsistent with the file's own conventions.

**Severity:** Medium — misconfiguration silently widens the attack surface.

**Location:** `config/make_config.js:401-404`; call sites at lines 121, 145, 149.

**Verification (reproduced).**

```
AUTHWALL_PERSONAL_ACCESS_TOKENS="0" -> enabled=true    AUTHWALL_WEBSOCKETS="0"        -> enabled=true
AUTHWALL_WEBSOCKETS="disabled"      -> enabled=true    AUTHWALL_WEBSOCKETS="FALSE"    -> enabled=true
AUTHWALL_WEBSOCKETS="False"         -> enabled=true    AUTHWALL_WEBSOCKETS="nope"     -> enabled=true
```

(`false`, `no`, `off`, and empty all correctly disable.)

**Expected:** `0` disables; an unrecognized value is a startup error.
**Actual:** `0` and every unrecognized value enable.

**Remediation.** Accept `0`/`1` alongside the existing spellings, case-insensitively, and throw on
anything else:

```js
function parse_bool_flag(value) {
    const map = {yes:1, no:0, true:1, false:0, on:1, off:0, 1:1, 0:0, '':0};
    const out = map[String(value).trim().toLowerCase()];
    if (out === undefined) {
        throw new Error(`Invalid boolean value: ${JSON.stringify(value)}`);
    }
    return out;
}
```

Then fold `AUTHWALL_RATE_LIMITING` onto the same helper so one rule covers every flag, and update
`docs/config.md` to list `0`/`1`.

### M4. Microsoft display names become the literal string `"undefined undefined"` — NEW

**Description.**

```js
name: `${user_info.givenname} ${user_info.familyname}`.trim() || null,
```

Microsoft's OIDC userinfo endpoint returns the standard OIDC claims `given_name` and `family_name`
(underscored). With the underscore-less names read here, both are `undefined`, and template
interpolation stringifies them: the result is `"undefined undefined"` — which is **truthy**, so the
`|| null` fallback never fires and the string is stored as the user's `display_name`.

**Impact.** Every Microsoft sign-up gets `display_name = "undefined undefined"`, rendered in the
profile UI, the sessions list, and every outbound email greeting. The `|| null` fallback is
unreachable for *any* claim-name mismatch, so this is fragile independent of which spelling is
correct today.

**Severity:** Medium — user-visible data corruption on every account from one provider.

**Location:** `src/oauth_providers/oauth_provider_microsoft.js:63`.

**Why the suite misses it.** `tests/mock_microsoft.js:20-21` was written to match the code
(`givenname` / `familyname`), so the test asserts the implementation against itself. A mock that
mirrors the code cannot detect a claim-name error.

**Verification.** `node -e "const gn=undefined,fn=undefined; console.log(JSON.stringify(\`${gn} ${fn}\`.trim() || null))"`
→ `"undefined undefined"`.

**Remediation.** Read both spellings and filter before joining, so a missing claim yields `null`:

```js
const parts = [user_info.given_name ?? user_info.givenname, user_info.family_name ?? user_info.familyname];
const name = parts.filter(Boolean).join(' ').trim() || user_info.name || null;
```

Update `tests/mock_microsoft.js` to the underscored OIDC claims and add a case with the claims
absent, asserting `display_name === null`.

### M5. Email-change confirm holds a DB transaction across email delivery and responds inside it — NEW

**Description.** `email_change_confirm_get` calls `complete_email_change_confirm` from inside the
transaction callback, and that function performs a network `send_email` and then `res.redirect`:

```js
await db.transaction(async function () {
    await db('email_change_tokens')…update({used_at: now});
    await db('user_identities').where({id: ident.id}).del();
    await db('user_identities').insert({…});
    await complete_email_change_confirm(req, res, user_id, old_email, new_email);   // ← sends email + responds
});
```

**Impact.** Three distinct problems:
1. **Pool starvation** — a DB connection is pinned for the duration of an external mail-API call. A
   slow or hanging provider ties up connections; with knex's default pool of 10, a handful of
   concurrent confirms can stall unrelated requests across the whole proxy.
2. **Response before commit** — the redirect is written while the transaction is open. If the commit
   then fails, the user has been told the change succeeded when it did not.
3. **Mailer failure reverts a completed change** — `send_email` (not `send_email_nothrow`) throws on
   provider error, rolling back an email change the user legitimately confirmed.

**Severity:** Medium — reliability and correctness under load or provider degradation.

**Location:** `src/routes/email_change.js:126-146`; `src/actions/complete_email_change_confirm.js`.

**Verification.** Read the nesting at `email_change.js:126`; compare with every other flow —
`complete_password_change`, `complete_sign_in`, `complete_sign_up` all commit first and send
afterwards. This is the only place the pattern is inverted.

**Expected:** transaction commits, then the response is sent, then notification email is attempted.
**Actual:** email and response happen inside the transaction.

**Remediation.** Move `complete_email_change_confirm` after the transaction block, and switch its
`send_email` to `send_email_nothrow` to match the notification semantics used elsewhere (this is a
courtesy "your email changed" notice — it should not be able to undo the change).

Two smaller issues in the same handler, worth folding into the fix:
- The new identity is written as `value: email_change.email_normalized`, discarding the address the
  user actually typed. For Gmail this turns `First.Last@gmail.com` into `firstlast@gmail.com` in the
  UI. Store the original alongside the normalized form, as every other identity writer does.
- The handler does not re-check that the target address is still unregistered. If someone claims it
  between request and confirm, the insert violates the unique constraint and surfaces as
  `An error occurred`. Re-check and raise a `UserFriendlyError`.

### M6. OAuth connect initiation is CSRF-able (forced account linking)

**Description.** `GET /auth/google?connect=1` is an unauthenticated GET with no CSRF token and no
sign-in requirement. It writes `oauth_state` and `oauth_code_verifier` into whatever session the
browser carries and redirects to the provider. The session check happens only later, in the
callback.

**Impact.** Classic forced-linking: an attacker who can make a victim's browser issue that GET while
the victim is signed in to Authwall *and* to the attacker's provider account gets the attacker's
provider identity linked to the victim's Authwall account. The attacker can then sign in as the
victim through that provider. It also lets any third-party page overwrite a victim's in-flight OAuth
state, breaking a legitimate login.

**Severity:** Medium — requires a chained provider session, but the outcome is full account takeover.

**Location:** `src/helpers/make/make_oauth_flow.js:32, 39-52`. Note the disconnect route is correctly
protected (`POST` + `auth_middleware` + `csrf_middleware`); only connect is exposed.

**Remediation.** Require an authenticated session for `?connect=1` at initiation, not just at
callback, and carry a one-time CSRF-bound value in the `state` (the state already encodes intent via
`oauth_state_from_intent`; bind it to `req.session.csrf_token` as well and verify on return). The SPA
already renders connect as a plain `<a href>` (`design/public_html/spa.html:1552`), so this needs a
matching frontend change to a POST-and-redirect.

### M7. Personal access tokens survive password reset and "revoke all sessions"

**Description.** `complete_password_reset_confirm` deletes `sessions` rows; `sessions_revoke_all_post`
deletes other sessions. Neither touches `personal_access_tokens`. `complete_password_change` also
leaves them.

**Impact.** The recovery story is incomplete. A user who resets their password because they believe
they were compromised keeps every attacker-created PAT alive — and PATs authenticate proxied
upstream requests and WebSocket upgrades indefinitely (`expires_at` is nullable = never expires).
"Sign out everywhere" does not mean everywhere.

**Severity:** Medium — defeats the primary account-recovery action.

**Location:** `src/actions/complete_password_reset_confirm.js:21-22`;
`src/routes/sessions.js:56-63`; `src/actions/complete_password_change.js:24-30`.

**Remediation.** Revoke PATs on password reset (unambiguously a compromise-recovery action). For
"revoke all sessions", either revoke them too or label the button accurately — silently leaving them
is the one option that misleads. Record a `personal_access_token_revoked` auth event with
`reason: 'password_reset'` so the audit log explains the mass revocation.

### M8. One-time token consumption is not atomic

**Description.** Every one-time credential follows read-then-write:

```js
const magic_link = await db('magic_links').whereNull('used_at').where('token_hash', …).first();
if (!magic_link) { throw … }
await db('magic_links').where({id: magic_link.id}).update({used_at: now, …});
```

Two concurrent requests with the same token both pass the `whereNull` check before either updates.
The same shape appears in email-verify confirm and password-reset confirm. Guess counters have the
matching race: `email_verify_confirm_post` and `magic_link_confirm_post` read `attempts`, then write
`attempts + 1`, so N parallel requests consume one increment.

**Impact.** A single-use magic link can establish two sessions. More usefully to an attacker, the
non-atomic counter means `max_attempts` (5) is not a real ceiling — parallel guessing gets
substantially more attempts per token than configured, weakening the 6-digit code materially.

**Severity:** Medium — requires concurrency, but directly weakens a documented control.

**Location:** `src/routes/magic_link.js:88-95, 155-160`; `src/routes/email_verify.js:72-88, 127-136`;
`src/routes/password.js:287-303`.

**Remediation.** Make consumption a conditional update and branch on the affected row count:

```js
const claimed = await db('magic_links').where({id, used_at: null}).update({used_at: now, updated_at: now});
if (!claimed) { throw new UserFriendlyError('Invalid or expired magic link'); }
```

For counters use an atomic `increment('attempts', 1)` and re-read, or do the check inside a
transaction with `forUpdate()`. There is no concurrency test anywhere in the suite — add one.

### M9. Sibling password-reset tokens survive a completed reset

**Description.** `password_reset_confirm_post` marks only the token it consumed as used.
`complete_password_reset_confirm` never clears the others. `complete_password_change` *does*
(`password.js` → `db('password_reset_tokens').where({user_id}).whereNull('used_at').del()`), so the
two recovery paths disagree.

**Impact.** A user who clicked "forgot password" three times has three live tokens. Using one leaves
the other two valid for their full 10-minute window — so an attacker who intercepted an earlier
email (shoulder-surf, shared inbox, forwarded message) can reset the password again *after* the
legitimate reset, and the user's own successful reset gives them no protection.

**Severity:** Medium — an inconsistency that undermines the reset flow's guarantee.

**Location:** `src/actions/complete_password_reset_confirm.js`; contrast
`src/actions/complete_password_change.js:30`.

**Verification.** There is a test for the *change* path — `"Old password-reset link is invalid after
profile password change"` — and none for the reset path, which is the one that is broken.

**Remediation.** In `complete_password_reset_confirm`, inside the existing transaction, delete (or
mark used) all other unused tokens for that `user_id`. Add the mirror-image test.

### M10. Sentry URL redaction fails open for relative URLs

**Description.**

```js
function sanitize_url(url) {
    try { const out = new URL(url); … }
    catch (error) { return url; }     // ← unredacted
}
```

Express populates `event.request.url` from `req.url`, which is a **relative** path
(`/auth/magic-link/confirm?token=…`). `new URL('/auth/…')` throws without a base, so the catch
returns the string untouched.

**Impact.** The exact secrets H3 leaks to local logs also reach Sentry — a third-party service —
whenever an error occurs on a token-bearing request. `docs/security.md` states query parameters that
look like secrets "are replaced with `[Filtered]`", which is not what happens on the common path.
Breadcrumbs are not sanitized at all.

**Severity:** Medium — credential disclosure to an external processor; higher if the DSN is shared.

**Location:** `src/services/sentry.js:91-108`.

**Verification.** `node -e "new URL('/auth/x?token=abc')"` → `TypeError: Invalid URL`. The unit test
at `src/services/sentry.test.js` only exercises absolute URLs, so the failing branch is untested.

**Remediation.** Parse with a base: `new URL(url, 'http://localhost')`, then re-emit
`pathname + search` when the input was relative. Add `beforeBreadcrumb` running the same
sanitizer. Extend the test with a relative URL — it is a two-line change that would have caught this.

### M11. `bin/run_knex.js` cannot run

**Description.** It requires a module that does not exist:

```js
const get_database_env = require('../db/get_database_env');
```

`db/` contains only `index.js`, `utf8mb4_bin.js`, and `migrations/`.

**Impact.** Any documented operator workflow routed through this script fails immediately. Nothing
else in the repo references it — including the `migrate` npm scripts, which call `knex` directly with
a hardcoded `--env=sqlite`. That hardcoding is the more consequential half: `npm run migrate` against
a MySQL or Postgres deployment silently migrates the local SQLite file instead of the real database.

**Severity:** Medium — broken tooling that can be mistaken for a successful migration.

**Location:** `bin/run_knex.js:4`; `package.json:20-22`.

**Verification.**

```
$ node bin/run_knex.js migrate:status
Error: Cannot find module '../db/get_database_env'
```

**Remediation.** Either implement `db/get_database_env.js` (deriving the knex env from `AUTHWALL_DB`
exactly as `config/make_config.js:512-528` already does — extract that logic rather than duplicating
it) and point the `migrate*` npm scripts at `bin/run_knex.js`, or delete the script and make the
scripts resolve the env from `AUTHWALL_DB`. Leaving `--env=sqlite` hardcoded is the one option that
stays actively misleading.

### M12. `normalize_email` accepts strings that are not email addresses

**Description.**

```js
const at = s.lastIndexOf('@');
if (at === -1) { return s; }      // ← no '@' is still "valid"
```

Callers treat a truthy return as "valid email". `config/make_config.js` applies a real regex
(`normalize_access_email`), but no runtime route does.

**Impact.** `POST /auth/sign-up` with `email=foo` passes the `email && !email_normalized` guard and
creates a `type: 'email'` identity whose value is `foo`. The account then enters the email-verify
flow and Authwall attempts to deliver to `foo`. Downstream, `authorize_email` computes
`email_normalized.split('@')[1]` → `undefined`, so domain deny-rules cannot evaluate such an
identity at all. The same gap affects magic-link request, email add, and email change.

**Severity:** Medium — corrupt identity data and an access-rule evaluation hole.

**Location:** `src/helpers/normalize/normalize_email.js:9-11`; callers in `password.js:141`,
`magic_link.js:41`, `email_add.js:27`, `email_change.js:37`.

**Remediation.** Return `null` when there is no `@`, or when either side is empty — and reuse the
shape check `make_config` already applies so config-time and runtime validation agree. Note that
tightening this changes sign-up behaviour, so add tests for the currently-accepted malformed inputs
first.

### M13. Expired security records are never cleaned up

**Description.** No process removes expired sessions, used or expired magic links, password-reset
tokens, email-verify tokens, or email-change tokens. The only `setInterval` in the codebase is the
in-memory rate-limiter eviction. `bin/` has no maintenance command.

**Impact.** Unbounded growth of tables holding security-relevant data, and an indefinitely retained
record of every address that ever requested a magic link (`magic_links.email` stores the raw
address with no FK and no user link) — a data-minimization problem as well as a capacity one. This
development database already holds 250 sessions and 15 magic links from casual use.

**Severity:** Medium — operational debt with a privacy dimension.

**Location:** schema in `db/migrations/`; no cleanup implementation anywhere.

**Remediation.** Add `bin/prune` deleting rows past `expires_at` (plus a retention window for
`auth_events`), document it in `docs/cli.md` alongside `bin/activity-summary`, and either call it on
an interval at startup or ship a cron example in `docs/deployment.md`.

### M14. Sensitive account actions lack step-up authentication

**Description.** With a live session and a valid CSRF token, a caller can change the account email
(`POST /auth/email-change/request`), remove the account (`POST /auth/account/remove`), create a
never-expiring PAT, or disconnect providers — none of which re-check the current password.

**Impact.** Any session hijack converts directly into permanent account takeover: change the email,
confirm from the new inbox, done. The password-change path *does* require `current_password`,
so the protection exists but is applied inconsistently — email change is the more valuable target.

**Severity:** Medium.

**Location:** `src/routes/email_change.js:24-26`; `src/routes/account.js:15`;
`src/routes/personal_access_tokens.js:25-28`; `src/helpers/make/make_oauth_flow.js:34`.

**Remediation.** Require `current_password` (when the user has one) or a fresh re-authentication
timestamp in the session for email change, account removal, and PAT creation. `account_remove_post`'s
`confirmation === 'DELETE'` check is a typo guard, not an authentication control.

## Low severity and hardening gaps

- **L1. State-changing confirmations execute on GET.** `GET /auth/email-verify/confirm`,
  `/auth/magic-link/confirm`, and `/auth/email-change/confirm` mutate state and, for magic links,
  establish a session. Mail scanners and link prefetchers consume these tokens before the user
  clicks. Land on a confirmation page that POSTs.
- **L2. Return URLs trust every subdomain, and ignore port on that branch.**
  `redirect.js:47-49` accepts any `*.<public_url_hostname>`; the subdomain branch also skips the port
  check the same-host branch performs. Documented as intentional in `docs/security.md`, but one
  compromised or user-controlled subdomain becomes an open redirect on the login flow. Consider an
  explicit allow-list.
- **L3. `trust proxy: true` is unconditional.** Directly exposed, any client sets `X-Forwarded-For`
  and controls rate-limit keys, `auth_events.ip`, and last-used IPs. Well documented in
  `docs/security.md` with a hardening checklist item — the residual gap is that nothing *enforces*
  it. Consider an explicit trusted-proxy config value.
- **L4. Rate limiting is per-process and in-memory.** Documented. Worth noting the limiter fires
  `next(new UserFriendlyError(…))`, producing a `302` redirect rather than `429` — API clients
  cannot distinguish throttling from a failed login. The bearer limiter does return `429` correctly.
- **L5. WS and HTTP bearer limits key on different identities.** HTTP uses `req.ip` (proxy-aware);
  the WS upgrade path uses `req.socket.remoteAddress` (`create_app.js:473`). Behind a proxy, every
  WS attempt shares one key — the shared `bearer_miss_limiter` then throttles all upgrades together
  while HTTP throttles per client.
- **L6. `AUTHWALL_SET_HEADERS` can override `X-Auth-User`.** `proxyReq` applies operator headers
  after setting the identity (`create_app.js:245-255`), so a configured `X-Auth-User` silently wins.
  Reject that name at config parse time.
- **L7. Authwall's own session cookie is forwarded upstream** unless explicitly unset. Consider
  stripping `connect.sid` from the proxied `Cookie` header by default.
- **L8. Sign-up enumerates existing accounts.** `Email already exists` / `Username already exists`
  vs. the deliberately generic sign-in and password-reset responses. Inconsistent with the care
  taken elsewhere (the `dummy_hash` timing defense at `password.js:100-107` is exactly right).
- **L9. Root secret gets only a length check.** `validate_secret` requires ≥32 characters;
  `'a'.repeat(32)` passes. HKDF derivation limits the blast radius, but a warning on low-entropy
  input is cheap.
- **L10. `parse_authwall_seed` is 20% covered and fragile.** The compact format splits on `:`, so any
  password containing a colon is silently truncated; malformed JSON throws an unhandled
  `SyntaxError` during config load, failing startup with a parser message rather than a useful one.
- **L11. SPA renders some values via `innerHTML` without escaping.** `avatar_url` and provider
  `p.value` at `spa.html:1486, 1588` interpolate unescaped, while the PAT and session renderers
  correctly use `escape_html`. All such values are the viewer's own, so this is self-XSS rather than
  stored-XSS — but the inconsistency is a latent hazard the moment any of it renders cross-user.
- **L12. Public-path matching is raw prefix matching.** `path_matches` compares
  `path.startsWith('/lib/')` with no normalization, so `/lib/../secret` is checked as a public path.
  Express normalizes most traversal before this point; normalize explicitly rather than relying on it.
- **L13. MySQL 5.7 is in the CI matrix.** EOL since October 2023. Testing against it costs a job per
  run and implies support the project may not want to promise.
- **L14. CI workflows lack explicit `permissions:` blocks.** `master.yml` and `production.yml`
  inherit the repo default token scope; `docs.yml` and `trivy.yml` correctly scope theirs.
- **L15. Playwright cannot run locally.** All 54 cases fail with "Executable doesn't exist" — CI is
  unaffected (prebaked image), but a contributor cannot run `npm test` end-to-end. Add a documented
  `npx playwright install` step or a preflight check with a clear message.

## Cross-cutting observation: the tests validate the code against itself

Three of the five new findings (H2, M1, M4) share one root cause, and it is worth naming separately
because no per-finding fix addresses it.

Coverage is 94% and 508 tests pass, yet all three defects sit on fully-covered lines. The reason:

- `tests/mock_github.js` sends `id` as a string; GitHub sends a number.
- `tests/mock_microsoft.js` sends `givenname`/`familyname`; the OIDC spec (and Microsoft) send
  `given_name`/`family_name`.
- `github_no_email.test.js`'s *"can set a password"* test asserts only which error came back.

Each mock was written to match the implementation rather than the provider, so the suite confirms
the code agrees with itself. Coverage cannot detect this — the lines execute either way.

**Remediation.** Capture one real (redacted) response per provider from live credentials, commit
them as fixtures, and build the mocks from those. Add a note to `docs/oauth-providers.md` recording
where each fixture came from and when, so the next person can tell a deliberate shape from a guess.

### Larger refactoring — worth scheduling, not worth rushing

These are the structural items behind several findings. Each is a multi-day change and none should
block the phases above.

- **One authorization decision, four call sites.** H1 exists because proxy, sidecar, PAT, and WS
  paths each re-derive "is this request authorized?". Extract a single `authorize_request(req)`
  returning a typed decision and have all four consume it. This prevents the next H1 rather than
  fixing this one. *Do after Phase 1 — the immediate fix should not wait for the refactor.*
- **Real provider fixtures.** See the cross-cutting section. Capture one redacted live response per
  provider and rebuild the mocks from it. This is the highest-leverage testing change available and
  directly prevents the H2/M4 class. *Best done alongside Phase 2, while the provider code is
  already open.*
- **Transaction discipline.** M5 is the acute case, but the pattern — external I/O and response
  writes interleaved with DB work — recurs across `src/actions/`. Establish the convention
  (commit → respond → notify), then audit the action files against it.
- **Rate limiting that survives a restart and spans processes.** L3/L4/L5 all stem from in-memory
  per-process counters keyed on a spoofable IP. A shared store and an explicit trusted-proxy config
  would close all three together.
