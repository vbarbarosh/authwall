Reviewed the trust placed in upstream services, operators, database users, logs and build tooling. The checkout contained 676 tracked files. The sandbox initially blocked local listeners. The test counts above come from the completed loopback-enabled runs. The PostgreSQL and both MySQL runs emitted Knex “Transaction query already complete” diagnostics from `SessionStore.set` despite their passing assertions. The harness rolls back a transaction per case. A teardown ordering problem is an **unreproduced observation**: the traces and harness were inspected, but the originating test was not isolated and no production session loss was observed. [Harness](../mocha.api.js) and [session store](../src/helpers/SessionStore.js).

The review did not access a deployed service, production data, real provider accounts, real mailboxes, Sentry ingestion, a published image, registry credentials or repository protection settings. Test results do not measure production availability, concurrent traffic at fleet scale, backup permissions or downstream cache behavior. No percentage of source coverage is claimed for this run.

## Verdict

**The three high findings from November 19 have fixes and passing regressions for their reported cases.** The most immediate deployment work is to protect database access and startup credentials. Within the application, preserve the distinction between an address reported by a provider and one it verified. The standard Facebook allow-list fixture still holds the user at email verification.

| Area | Security decision |
|---|---|
| Account admission | Keep the protections for header forwarding, email addition and provider-backed access. Correct the provenance of stored provider addresses (AW-170). |
| Recovery | Treat AW-125 and AW-135 as priorities for deployments that allow unconfirmed addresses or resend verification links. Both affect the user's ability to retain control of their account. |
| Storage and operations | Check SQLite file and directory modes, separate the protected app from the identity database, and keep rejected configuration values out of startup logs (AW-169, AW-171, AW-173). |
| Sidecars | A sidecar decision is specific to a credential and a path. Prevent storage of that response (AW-172). The gateway handling upgraded connections owns their ongoing authorization (AW-132). |
| Supply chain | The application production lockfile passed npm audit. The built image includes additional packages that need updates or removal (AW-174). |
| Availability | The earlier shared upstream socket bottleneck is fixed. The replacement pool has no active-socket ceiling. Size concurrency limits at the edge and upstream against their actual capacity (AW-122). |

## Findings

### AW-169 — Fresh SQLite files inherit the process umask (medium)

A local account that can traverse the data directory may be able to copy password hashes, identities and authentication history. This matters on shared hosts and bind mounts. A private ancestor directory or an owner-only service umask limits the exposure.

**Evidence.** Ran `bin/migrate` twice against new, empty SQLite paths in a private audit directory. Both runs applied 22 migrations. With umask `0022` the database mode was `0644`. With `0077` it was `0600`. The app selects a filename and leaves file creation to SQLite. By contrast, it explicitly requests `0600` when creating the signing key. No other user's files or data were read. [knexfile.js:18](../knexfile.js) and [make_config.js:373](../config/make_config.js).

**Correction.** Create new SQLite databases owner-only before first open. Document the directory, journal, backup and existing-file permissions required for installations that intentionally share a group. Acceptance should cover startup and the migration CLI under a permissive umask, as well as approved shared-volume configurations.

### AW-170 — Stored provider addresses lose their verification status (medium)

Authwall uses a provider identity's saved addresses as evidence for an account that has no verified local address. Facebook explicitly returns its address as pending. The callback puts pending and verified addresses in the same JSON list. A later reader of that list cannot establish which kind it received. This is a confirmed data integrity issue. An admission bypass was not demonstrated.

**Evidence.** Ran the existing mocked Facebook registration for a new user and inspected the two identity records before the user opened the verification mail. Result: `provider snapshot count=1; mailbox proof=false`. The callback constructs the array at line 128, writes it on registration at line 326 and refreshes it at line 300. The access-rule helper consumes that array at line 48. The separate allow-list story still returns 403 before mailbox confirmation and 200 afterwards. [Facebook adapter](../src/oauth_providers/oauth_provider_facebook.js), [OAuth flow](../src/helpers/make/make_oauth_flow.js), [admission decision](../src/helpers/access_refusal_from_identities.js) and [Facebook story](../tests/api/stories/facebook_address_pending_until_confirmed.test.js).

**Correction.** Persist only provider-verified addresses as admission evidence. Keep pending addresses separately where the UI needs them. Clear or rebuild existing ambiguous Facebook snapshots from trustworthy evidence. Cover registration, linking, repeat sign-in and legacy rows. Verify that the independent mailbox gate still works.

### AW-171 — The sample stack puts the upstream on the credential database network (medium)

The root Compose stack gives the application database account a literal password and puts the upstream, Authwall and MySQL on the same default network. A compromised upstream in a deployment copied from this stack would have a network path and a published credential for the identity database. The database port has no host mapping. Exposure depends on code execution or network access inside the stack.

**Evidence.** Parsed the tracked Compose document with the project's YAML parser. The three services have no separate networks, the literal application password equals the one in Authwall's database URL, and MySQL has no published port. The explicit database URL in the service environment also takes precedence over that variable in the referenced env file. The older S22 observation covered the override. [docker-compose.yaml:11](../docker-compose.yaml) and [September 2 audit](audit-2026-09-02.md).

**Correction.** Put MySQL on a private network shared only with Authwall. Supply unique application and administrative credentials at deployment. On a previously initialized volume, rotate the database accounts as well as changing the configuration. Acceptance is a working sign-in through the upstream and a deployment configuration that gives the upstream neither database network membership nor database credentials.

### AW-172 — Sidecar decisions have no response-cache policy (low)

An auth subrequest returns a user-specific identity header or an anonymous decision for the requested path. A shared cache configured to reuse responses by endpoint could reuse a previous decision. Neither sidecar example configures an authorization cache. Cross-user reuse was not observed.

**Evidence.** In a signed-in API fixture, a normal sidecar check returned `200`, with the identity header present, `Cache-Control` absent and `Vary` absent. The same client's status response returned `Cache-Control: no-store`. The status handler sets it at line 27. The sidecar handler starts at line 210 and returns success with the identity at line 265. [status.js](../src/routes/status.js) and [sidecar tests](../tests/api/security/sidecar.test.js).

**Correction.** Set `Cache-Control: no-store` at the beginning of the sidecar handler and document bypassing shared caches on the authorization subrequest. Verify the directive on authenticated, public, optional, unauthorized and forbidden decisions.

### AW-173 — Syntax errors can copy an upstream credential into startup logs (medium)

Operators can use `AUTHWALL_SET_HEADERS` for a private header shared with an upstream. Two parser errors quote the whole rejected entry. A separator typo can therefore persist the configured credential in startup stderr and any log collector that receives it.

**Evidence.** Started separate Node processes loading `./config` with an inert marker. The valid entry exited 0 and emitted no marker. The colon-separated entry and the entry missing its name both exited 1 and contained the marker in stderr. The two error messages serialize the input at lines 16 and 23. This is distinct from AW-127, whose JSON seed diagnostic was repaired. [parse_set_headers.js](../src/helpers/parse/parse_set_headers.js) and [startup summary](../src/helpers/render/render_config_summary.js).

**Correction.** Report the setting, entry number and expected syntax. Omit raw entry text and wrap validator errors that may echo names or values. Add a subprocess regression asserting a synthetic secret is absent from both output streams. If a real startup log already contains a credential, restrict access and rotate that credential.

### AW-174 — The built runtime image includes vulnerable copies outside the app lockfile (medium)

Trivy 0.76.2 scanned image ID `4c79f629837d96b1a0171672a2ce1ca38bb6b518d7c8e54f0b42aa7727ecfa1a`. It reported six high matches, all in the **global npm installation** bundled with the Node base image. The entry point runs `node src/index.js` directly. Package presence is confirmed. Use of the six affected code paths by incoming Authwall requests is unverified.


|---|---|---|

**Evidence.** Exported the image built by `bin/build`, then ran `trivy image --scanners vuln --format json --input <image.tar>`. The report lists installed paths and fixed versions. An offline inspection of the image confirmed the npm package directory. The project CI runs a separate image scan filtered to critical and high with exit code zero. **Correction.** Update the base packages and remove the package manager from the final image if runtime operations do not require it. Run the four image checks again. Scan the exact image digest intended for publication and record the disposition of outstanding advisories as part of the release.

## What is good

- **Requests to the protected app.** HTTP and WebSocket forwarding now apply the header policy before handing the request to the proxy library. Built-in forwarding strips Authwall's session cookie, derives the user header from authenticated state, and runs access checks for the configured path. The API suite covers public, optional and private requests, including the earlier header regression. [Proxy](../src/create_app.js) and [header-policy regressions](../tests/api/stories/expect_keeps_every_header_rule.test.js).
- **Account holders.** Session identifiers and CSRF tokens rotate at sign-in. Sensitive management routes require a browser session. Password changes and resets transactionally revoke the relevant credentials. One-time confirmation claims use a database uniqueness constraint. These controls have regression coverage across routes and credential types, subject to the engine-specific skips above. [Session replacement](../src/helpers/replace_session.js), [management middleware](../src/helpers/middleware/auth_middleware.js), [password routes](../src/routes/password.js) and [confirmation claims](../src/helpers/claim_confirmation.js).
- **Provider and mailbox boundaries.** The six adapters feed a shared authorization-code flow with session-bound state and an S256 challenge. A provider link depends on the provider identity and the current owner. The test suite distinguishes a reported address from mailbox proof in the user-facing flow. Preserve that distinction in persistent data as well. [OAuth flow](../src/helpers/make/make_oauth_flow.js), [provider adapters](../src/oauth_providers/) and [mailbox verification stories](../tests/api/stories/facebook_address_pending_until_confirmed.test.js).
- **Operators and maintainers.** A partially configured provider now fails startup. A malformed JSON seed gets an input-free diagnostic. The signing key is created exclusively with owner-only permissions. The Dockerfile copies a bounded set of runtime files and runs as a non-root user. The application source is writable by that same user (AW-53). [Configuration](../config/make_config.js), [seed parsing](../src/helpers/parse/parse_authwall_seed.js), [image](../Dockerfile) and [build context](../.dockerignore).

## Recommended order of work

1. **Protect existing installations.** Check the effective sign-up policy on upgraded installations, rotate exposed header or sample database credentials where applicable, restrict access to SQLite files, and isolate the identity database from upstream services. Owners can verify these changes through effective configuration, filesystem metadata and network membership. Covers AW-133, AW-169, AW-171 and AW-173.
2. **Preserve proof of account ownership.** Start with sibling verification links and the release of active login identities (AW-135, AW-125), then correct provider snapshot provenance (AW-170). Exercise both new and existing identity rows before rolling out the change.
3. **Refresh and rescan the final image.** Triage AW-174 against the exact artifact to be shipped. Verify that the six high npm-bundle matches and the fixable Alpine advisories are removed or explicitly dispositioned. Keep the image self-check in the release path.
4. **Set edge policy explicitly.** Add no-store to every sidecar decision (AW-172). Decide where socket revocation, forwarded-header normalization and connection limits are enforced (AW-132, AW-152, AW-122). Recheck those guarantees in the deployment topology that users actually run.
5. **Close the remaining recovery and test gaps.** Prioritize passwordless step-up, last-sign-in-method checks, disposable database ownership and MySQL rollback coverage (AW-123, M-02, AW-129, AW-168).
