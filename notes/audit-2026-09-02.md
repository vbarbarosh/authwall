Date: 2026-09-02
Scope: repository at `/app`, version `1.14.0`, commit `a1bf8d6` (branch `master`)

Repository changes made: None. All probes ran in a disposable copy under the session scratchpad.

**Verdict: the trust boundary has three new ways through it, and none of the July findings were worked.**

The only change since the 2026-07-28 audit is a dependency bump. That bump happens to close the one Critical from that report: the URL parser in `@vbarbarosh/node-helpers` 3.78 is total, so `GET //[` no longer kills the process. Nothing in this repository pins that behaviour, and every other July finding is still open, including six Highs.

This audit went one layer deeper than July and found three High-severity defects that earlier reports either missed or dropped as "deployment-dependent". All three were reproduced end to end. An anonymous client can read protected upstream content through any prefix rule in `public_paths`. A magic link signs its recipient into whichever account currently holds their address, even an attacker's unverified one. And the profile page renders identity values into HTML unescaped, which a magic-link login turns into stored XSS on the protected origin.

Operationally, the API suite cannot run on this checkout at all: it points at the developer's own database, which a stashed feature branch migrated past `master`.

Open by severity: **0 Critical** (July's one is fixed), **9 High** (3 new, 6 carried), **12 Medium new** (+21 carried), **31 Low new** (+28 carried), **1 July finding fixed** (N31, by the dependency bump).

Counts cover findings in this report and the still-open findings of 2026-07-27 and 2026-07-28. Earlier audits' items that those two reports dropped are re-listed under prior findings.

## Top findings
- **High** **Any `/*` public rule is a full bypass.** `GET /lib/../admin/secret.txt` passes the `/lib/*` check and is forwarded verbatim; a normalizing upstream serves `/admin/secret.txt` to an anonymous client. *Reproduced against a real static server.* (S1)
- **High** **Magic links log the victim into a squatted account.** Sign up with someone else's address, never verify it; when they request a magic link, it signs them into your account, and your password still works. *Reproduced twice, independently.* (S2)
- **High** **Stored XSS on the auth origin.** The profile view injects usernames and e-mail values into `innerHTML`; sign-up accepts `<img onerror=…>` as a username; a magic-link URL with `?return=/auth/profile` logs any visitor into that account. (S3)
- **Medium** **Every anonymous `/auth/*` hit writes a 30-day session row**, including the health endpoint the docs say to probe. Nothing prunes them. *Reproduced: 15 requests, 15 rows.* (S4)
- **Medium** **Twenty bad WebSocket tokens lock out every WebSocket client for 15 minutes** in the documented reverse-proxy topology, while the HTTP path lets the same attacker escape with a forged `X-Forwarded-For`. *Reproduced.* (S5)
- **Medium** **Password-reset mail goes to unverified addresses**, and the e-mail add endpoint has no cooldown, so any address can be flooded with attacker-authored text. (S6, S7)
- **Medium** **Secrets still reach Sentry**: the Facebook app secret via a GET query captured by HTTP breadcrumbs, and password-reset tokens via the unredacted `Referer` header on error events. (S9, S10)
- **Medium** **`npm test` is broken on this checkout** because the suite uses `data/db.sqlite3`, which the stashed admin-panel work migrated ahead of `master`. (S14)
- **Fixed** **July's Critical crash is gone**, closed by the helper-library bump rather than by a change here, and with no regression test. (prior findings)

## High severity

### S1. Dot segments walk past any `public_paths` prefix rule

*High · Reproduced*

**Where.** `src/create_app.js:461-469` (`path_matches`), `:362` (`sign_in_required`), `:218-282` (proxy forwards `req.url` as received). Docs recommend prefix rules at `docs/config.md:348-355`.

**What happens.** Express does not normalise dot segments, so `req.path` for `GET /lib/../admin/secret.txt` is exactly that string. `'/lib/../admin/secret.txt'.startsWith('/lib/')` is true, the request is classed public, no session is required, no `X-Auth-User` is set, and `http-proxy-middleware` forwards the raw target. Any upstream that normalises paths (nginx, Apache, Tomcat, Python's `http.server`, most static-file servers and frameworks) resolves it to `/admin/secret.txt` and serves it. Encoded variants (`%2e%2e`, `..%2f`, `;/../`) are forwarded untouched as well, so the set of vulnerable upstreams is wider than dot-segment normalisation alone. The shipped default `public_paths` are exact matches, so a stock deployment is safe until the operator adds the first `/*` entry, which is the first thing the documentation tells them to do for assets.

**Evidence.** Raw-socket requests against the real server (`node .`) with `AUTHWALL_PUBLIC_PATHS=/lib/*` and an echo upstream, then against `python3 -m http.server` serving `lib/app.js` and `admin/secret.txt`: 

```
GET /lib/../admin           → 200, upstream received "/lib/../admin"
GET /lib/%2e%2e/admin       → 200, upstream received "/lib/%2e%2e/admin"
GET /lib/..%2fadmin         → 200, upstream received "/lib/..%2fadmin"
GET /lib/;/../admin         → 200, upstream received "/lib/;/../admin"

GET /admin/secret.txt        → 302 /auth/sign-in?return=%2Fadmin%2Fsecret.txt
GET /lib/../admin/secret.txt → 200 "TOP SECRET ADMIN PAGE"
```

 The earlier July 5 and July 10 audits raised this as deployment-dependent; no test or normalisation was added and the July 27/28 reports dropped it.

**Fix.** Canonicalise before matching, and refuse what cannot be canonicalised. Decode percent-encoding once, reject any remaining `%2f`/`%5c`, resolve `.` and `..` with `path.posix.normalize`, reject if the result still contains `..` or a backslash, collapse duplicate slashes, and match on the result. Forward the canonical path to the upstream too, so the two never disagree. Add negative tests for each variant above against a prefix rule; the same helper should feed the sidecar once N5 is fixed.

### S2. A magic link signs the victim into whoever pre-registered their address

*High · Reproduced*

**Where.** `src/routes/magic_link.js:94-98` and `:158-162` (identity lookup with no `verified_at` filter, then `complete_sign_in`); `src/routes/password.js:151-156` (sign-up stores any address unverified); nothing expires unverified identities (prior M13).

**What happens.** Registration is open by default. An attacker signs up with `attacker` / their own password and the victim's e-mail address, and never verifies it. When the victim later chooses "send me a link" for their own address, the link is delivered to them, they click it, and the confirm handler finds the attacker's identity row, marks nothing verified, and signs the victim into the attacker's account. The attacker's username and password remain on that account, so everything the victim does inside the protected app from then on is visible to, and controllable by, the attacker. With `confirm_email.required` on, the victim is instead asked to verify, the verification mail goes to them, and they complete the attacker's account for them. Combined with the still-open H6, a signed-in Microsoft or Facebook user can squat an address as *verified* without ever receiving mail at it, which removes the one signal (the unverified badge) the victim might notice.

**Evidence.** Reproduced by the routes reviewer and again independently by the lead with a fresh spec: 

```
attacker_uid:            awuser_r8974ygfvsmbqjt2kvc8l1zy
victim_now_signed_in_as: awuser_r8974ygfvsmbqjt2kvc8l1zy
same_account:            true
providers:               [["email","victim@authwall.test",verified=false],["username","attacker",verified=true]]
```

 The routes reviewer then signed in as `attacker` with the attacker's password and received `authenticated:true` for the same `user_uid`. The same lookup shape governs password reset (S6).

**Fix.** E-mail-based sign-in must only match identities with `verified_at IS NOT NULL`. If the address is pending on another account, either refuse with a neutral message or create a fresh account for the link's recipient and leave the squatter's row to expire. Expire unverified identities after the verification window (M13), and record an auth event when a magic link collides with a pending identity. Add a story test for exactly this sequence.

### S3. Stored XSS through identity values on the profile page, deliverable in one click

*High · Verified in code*

**Where.** `design/public_html/spa.html:1588` (`${p.value || ''}` into `innerHTML`; an `escape_html` helper exists at `:1349` and is used for token rows but not here); `src/helpers/normalize/normalize_username.js:3` (trim only) and `normalize_email.js:9-11` (no shape check); `src/routes/magic_link.js:70-118` (`GET /auth/magic-link/confirm?token=` signs in whoever visits, then honours `?return=` via `redirect.js`).

**What happens.** An attacker registers a username such as `<img src=x onerror=…>` with their own e-mail, requests a magic link, and sends the victim `/auth/magic-link/confirm?token=T&return=/auth/profile`. The victim's browser is signed into the attacker's account (a login-CSRF the GET confirm route permits by design) and lands on the profile view, which injects the username unescaped. The script now runs on the Authwall origin, which in `direct` mode is the protected application's origin, with no CSP (N16). It can sign the victim out and render a credential-phishing sign-in at the genuine URL, or read the upstream app's origin-scoped storage. Provider-supplied values (GitHub login, Discord name) flow through the same sink, and `avatar_url` at `:1486` is an unescaped attribute.

**Evidence.** 

```
normalize_username('<img src=x onerror=alert(1)>')       → '<img src=x onerror=alert(1)>'
normalize_email('<img src=x onerror=alert(1)>@x.test')   → '<img src=x onerror=alert(1)>@x.test'
spa.html:1588  <div class="connection-value">${p.value || ''}</div>
```

 Sign-up (`password.js:145-148`) only rejects empty values. The magic-link-as-login-CSRF half was exercised by the S2 reproduction; the DOM injection was verified by reading, not executed in a browser.

**Fix.** Escape at every sink: `escape_html(p.value)` at `:1588`, the `avatar_url` attribute at `:1486`, the initials at `:1488`, and the session rows at `:1688-1708` (N17). Validate at the source too: apply the e-mail shape check that `make_config.js:538` already uses to sign-up, magic-link and e-mail-add, and a username charset. Make magic-link confirmation a POST landing page so a link cannot log a third party in. Ship the N16 headers as defence in depth.

## Medium severity

### S4. Every anonymous `/auth/*` request writes a 30-day session row, including health probes

*Medium · Reproduced*

**Where.** `src/create_app.js:109-118` (sets `csrf_token`, `ip`, `ua` on every `/auth` request), `:92-108` (`saveUninitialized:false` is defeated because the session is modified), `SessionStore.js:45-63`; `docs/deployment.md:128-136` tells operators to probe `/auth/health`.

**What happens.** A cookieless request to `/auth/health`, `/auth/status`, or any static asset under `/auth/` creates a `sessions` row with `user_id=null`, a 512-byte `ua`, and an expiry 30 days out. A liveness probe every 10 seconds is 260,000 rows a month. Nothing prunes expired sessions (prior M13). An unauthenticated attacker can do the same with `curl` in a loop, and on SQLite there is no length check on `ua` (N22), so each row can carry the full 16 kB header budget. This is unauthenticated storage exhaustion against the one table every request reads.

**Evidence.** 

```
before: 0 rows
5 × GET /auth/health, 5 × GET /auth/status, 5 × GET /auth/spa.html  (no cookies)
after:  15 rows   e.g. {user_id:null, ip:"127.0.0.1", ua:"axios/1.18.1", expires_at:+30d, custom:{csrf_token:…}}
```

**Fix.** Do not touch the session for health and static routes: mount `/auth/health` and the static handler before the session middleware, or scope the CSRF-token middleware to the SPA page and status routes. Give anonymous sessions a short lifetime (an hour), and add the prune job (M13) with an index on `expires_at` (L17). Truncate `ua` and `ip` to their column widths (N22).

### S5. WebSocket bearer failures are keyed on the proxy's address: one client locks out all, while HTTP lets the same client escape

*Medium · Reproduced*

**Where.** `src/create_app.js:474` (`req.socket.remoteAddress` for upgrades) versus `:402` (`req.ip`, which honours `X-Forwarded-For` because of `trust proxy: true` at `:54`); one shared `bearer_miss_limiter` (`:121-123`). `docs/security.md:137-155` instructs operators to deploy behind a reverse proxy.

**What happens.** In the documented topology every upgrade arrives from the reverse proxy's address. Twenty invalid bearer tokens from any client, no account needed, put that single key over the limit and every WebSocket bearer client is refused with `bearer_rate_limited` for 15 minutes; repeat once a quarter hour for a permanent outage of WebSocket API access. The HTTP path uses the forwarded address instead, so the attacker escapes their own lockout by rotating `X-Forwarded-For` when the proxy appends rather than overwrites, or when Authwall is exposed directly.

**Evidence.** 

```
ws  valid token, before:          opened=true
20 × ws  Authorization: Bearer awp_bad…  (same socket address)
ws  valid token, after:           opened=false status=401 reason=bearer_rate_limited
http valid token, same address:   429 "Too many failed authentication attempts…"
http valid token + X-Forwarded-For: 198.51.100.7   →  200 authenticated=true
```

**Fix.** Resolve the client address once, the same way, for both paths: a configurable `trust proxy` hop count or CIDR list (default `1` in `proxy` mode, `false` in `direct`), and derive the upgrade key from the same resolver. Add a startup check that refuses `trust proxy: true` semantics without an explicit setting. Key the bearer counter on the token prefix as well as the address so one client cannot exhaust a shared key.

### S6. Password reset and every notification are delivered to unverified addresses, and a reset does not evict a squatter

*Medium · Reproduced*

**Where.** `src/routes/password.js:230` (identity lookup without a verified filter), `src/helpers/models/get_user_email_and_name.js:6,12` (same, and reads a non-existent `is_verified` column), `src/helpers/send_email.js:7` (comment promises verified-only delivery), `src/actions/complete_password_reset_confirm.js:21` (deletes sessions only).

**What happens.** Following the S2 squat, the victim's anonymous reset request mails a live reset link to the unverified address; after the reset the attacker's username identity and any personal access token they created remain valid (prior M7). Independently, signing into a squatted account produces "new sign-in" and "password changed" notifications to an address that never opted in, which is an unbounded harassment channel to any mailbox.

**Evidence.** Reproduced by the routes reviewer: the `password_reset` mail was delivered to the unverified address; after the reset, the pre-existing PAT still returned `authenticated:true` and was proxied with 200.

**Fix.** Reset only for verified identities. On a successful reset, revoke personal access tokens and strip identities that were not verified. Route all `user`-based mail through a verified-only lookup and delete the dead `is_verified` reference. Correct `docs/emails.md:17` to say which messages go to unverified addresses by design.

### S7. `POST /auth/email/add` has no cooldown or limiter: unlimited attacker-authored mail to any address

*Medium · Reproduced*

**Where.** `src/routes/email_add.js:72` calls `create_email_verify_token` without the 60-second check that `email_verify.js:45-55` applies; `email_remove.js:45` deletes instantly; `email_change.js` has a per-target cooldown but no IP limiter.

**What happens.** An add/remove loop from any username account sends a confirmation mail per iteration to an arbitrary address. With N18 the body opens with the attacker's display name, up to the 100 kB body limit, newlines included.

**Evidence.** 

```
5 × (add target@example.test, remove) → 5 confirm_email mails in 79 ms, no error
```

**Fix.** Reuse the `email_verify_tokens` cooldown keyed by `email_normalized` inside `email_add_post`, add the per-IP limiter used by sign-up to `/auth/email/add` and `/auth/email-change/request`, and cap and sanitise `display_name` (L4/N18).

### S8. Removing the last e-mail under `confirm_email.required` locks the user out with no in-app recovery

*Medium · Reproduced*

**Where.** `src/routes/email_remove.js:34` (counts identities, not usable ones), `src/helpers/middleware/auth_middleware.js:4-8` (`/auth/email/add` is not in the allowed set while verification is pending).

**What happens.** A username-plus-e-mail user removes their e-mail. On the next sign-in every protected path redirects to `/auth/email-verify`; `POST /auth/email/add` answers "Email verification required"; `POST /auth/email-verify/request` answers "No unverified email found". The current session keeps working until sign-out because of the N3 snapshot, which hides the problem until it is too late.

**Fix.** Refuse removal when `confirm_email.required` is on and no other verified e-mail remains; add `/auth/email/add` to `EMAIL_VERIFICATION_ALLOWED_PATHS`; make the "last usable method" guard count verified e-mails and a password, not rows (prior L3).

### S9. The Facebook app secret travels in a GET query that Sentry's HTTP breadcrumbs record

*Medium · Verified in code*

**Where.** `src/oauth_providers/oauth_provider_facebook.js:36-42` (`http_get_json(urlmod(…, {client_secret, code, code_verifier}))`); `@sentry/core` `add-outgoing-request-breadcrumb.js:20` stores `parsedUrl.search`; `src/services/sentry.js:18-23` registers only `beforeSend`, and `sanitize_sentry_event` (`:62-78`) never touches breadcrumbs.

**What happens.** Any error captured later in the same request, including the token exchange itself failing with a 400 (the breadcrumb is recorded on the response event before axios throws), ships the long-lived app secret plus the one-time `code` and `code_verifier` to Sentry. The other five providers post credentials in the body, so this is Facebook only, but it is the provider's master credential.

**Fix.** Exchange via `POST` form body (Graph accepts `POST /oauth/access_token`). Register `beforeBreadcrumb` and run `urlxxx` over `data.url` and `data['http.query']` for `category === 'http'`; add `client_secret` to the sensitive-key predicate (it already matches `secret`, but test it).

### S10. Sentry error events ship the `Referer` header unredacted, a second sink for N2

*Medium · Reproduced*

**Where.** `src/services/sentry.js:80-88` drops only `authorization`, `cookie`, `set-cookie` and `x-csrf-token`; the request-data integration attaches all other headers.

**What happens.** The reset page renders the SPA with the token in the address bar. Any 5xx caught by `setupExpressErrorHandler` on a request issued from that page carries `Referer: …/auth/password-reset/confirm?token=…` into Sentry, where it is a working credential for anyone with project access.

**Evidence.** 

```
sanitize_sentry_event({request:{headers:{referer:'…/confirm?token=SECRETTOKEN123'}}})  →  referer returned verbatim
```

**Fix.** `headers.referer = urlxxx(headers.referer)` (and `referrer`) in `sanitize_sentry_event`, run `event.breadcrumbs[].data.url` through `urlxxx`, and add a unit test with a token-bearing referer. Do the log sink (N2) in the same commit; splitting them is what produced this finding.

### S11. Mailer HTTP calls have no timeout; on SQLite a stalled provider stalls the whole proxy

*Medium · Verified in code*

**Where.** `src/http/http_post_json.js:10` (axios with no `timeout`; default is 0, meaning none); used by all three mailers; `src/routes/email_change.js:123-146` awaits the send inside `db.transaction`; `knexfile.js` SQLite pool is one connection.

**What happens.** A provider that accepts the TCP connection and never answers holds the e-mail-change transaction, and with it the only SQLite connection, indefinitely. Every other database call in the process queues behind it, so sign-in, session lookup and the proxy's own session touch all hang. On MySQL/Postgres the pool caps at ten, so ten such requests do the same. There is no retry either.

**Fix.** `timeout: 10000` in `http_post_json`, and move mail sending out of the transaction (prior M5): commit first, send after, and record a failed send as an auth event rather than rolling back.

### S14. `npm test` cannot run on this checkout: the suite uses the developer's live database

*Medium · Reproduced*

**Where.** `mocha.api.js:17,35` (loads `.env`, builds `knex(config.knexvars)`); `config/make_config.js:515-531` (`get_knexvars` accepts only `mysql://` and `postgres://`, so SQLite is always `data/db.sqlite3`); `stash@{0}` contains `db/migrations/20260808120000_auth_events__normalize_ip.js`.

**What happens.** The stashed admin-panel work (dated 2026-08-27 in its own notes) migrated `data/db.sqlite3` with a migration that `master` does not have. Knex now refuses to list migrations, `bootstrap_database` throws in the root `beforeAll`, and all 386 API tests are skipped. There is no environment variable that points the suite at another SQLite file, so the only remedies are deleting the developer's database or un-stashing the feature. This is prior N10 turning from a hygiene note into a hard failure, and it is the kind of thing a CI-only view never sees.

**Evidence.** 

```
$ npm run test:api
1) "before all" hook: beforeAll in "{root}":
   Error: The migration directory is corrupt, the following files are missing: 20260808120000_auth_events__normalize_ip.js
0 passing (20ms)
```

**Fix.** Give the SQLite backend a file setting (`AUTHWALL_DB=sqlite:///path`, or a dedicated `AUTHWALL_SQLITE_FILE`), have `mocha.api.js` default it to a per-run temporary file, and stop loading `.env` in the harness. Until then, a `pretest` check that the migration list matches the database gives a one-line error instead of a corrupt-suite one.

## Low severity and hardening gaps

Grouped by area. Each item was verified in code; those marked reproduced were exercised.

### Configuration and startup
- S16 — **Two more silent misconfigurations.** `AUTHWALL_COOKIE_SAMESITE=Strict` (capitalised as MDN and every browser doc writes it) becomes `lax`; `AUTHWALL_PERSONAL_ACCESS_TOKENS=disabled` enables tokens. *Reproduced.* Same rule as N4/N13: invalid input is a startup error, and enum matching should be case-insensitive.
- S15 — **`X-Powered-By: Express` is sent on every response.** Observed on the raw probes. `app.disable('x-powered-by')` in `create_app.js`.
- S41 — **`public_url` is never validated as a URL.** `AUTHWALL_PUBLIC_URL=example.com` is accepted (`make_config.js:44`), which sets `cookie.secure=false` and makes `new URL(config.public_url)` throw inside the WebSocket origin check (`create_app.js:708`), turning every browser upgrade into a 500. *Config half reproduced.*
- S42 — **`PORT` is not parsed.** `PORT=abc` is passed through as a string to `listen` (`make_config.js:156`). Harmless today because Node throws, but it is the same class as N4.

### Sessions, tokens and accounts
- S26 — **The current-password check has no throttle** (`password.js:49`): twenty wrong guesses returned twenty "Current password is incorrect" from one session. *Reproduced.* A hijacked session can brute-force the real password. `/auth/profile` also runs `sharp` on 5 MB uploads with no `limitInputPixels` and no limiter. Add a failure counter keyed by `user_id` to both.
- S27 — **A reset token issued to the old address survives an e-mail change** (`password.js:236-242` binds tokens to `user_id` only). *Reproduced.* Delete unused reset tokens inside the change transaction.
- S28 — **Anyone can invalidate a victim's magic-link code** by re-requesting for the same address; `magic_link.js:136-142` checks only the newest row. *Reproduced.* Match any unused, unexpired row, or bind the code to its token.
- S29 — **Account removal leaves PII behind**: `magic_links` rows carry the raw address with no user link, and `auth_events` keep `identity_value`, `ip`, `ua` after `user_id` is nulled (`account.js:31-38`). *Reproduced.*
- S30 — **`src/routes/dev.js:17-21` dumps live session IDs, users and token hashes with no guard.** It is unmounted (`create_app.js:141`), but only by a comment. Delete it or gate on a non-production environment plus authentication.
- S17 — **The same provider can be linked to one account repeatedly**; connect checks only the exact `sub` (`make_oauth_flow.js:77-94`) and disconnect removes whichever row comes first (`:262`). *Reproduced:* GitHub 1001 then 1002, one disconnect leaves 1002, invisible in the SPA. Refuse a second identity of the same type, or replace explicitly.
- S18 — **OAuth connect bypasses the verification hold** every other management route enforces (`make_oauth_flow.js:90` checks only `user_id`). Policy inconsistency, not an escape.
- S19 — **Google is asked for an offline refresh token that is never used** (`oauth_provider_google.js:29`, `access_type: 'offline'`). Drop it.
- S35 — **Account-existence oracles for signed-in users**: "Email already registered" at `email_add.js:55` and `email_change.js:51`; pre-auth, "Magic link already sent" at `magic_link.js:50` reveals a request in the last minute. Respond uniformly and record the reason in `auth_events`.

### Logging, Sentry and services
- S20 — **Daily log files are created world-readable** (`make_logger_daily.js:48`, mode 0644; 0664 observed under `data/logs/`) while `secret.key` is 0600. These files have held live tokens (L1). Use `mode: 0o600` and fix existing files.
- S21 — **The logger passes CR/LF through** (`make_logger.js:93-117`): a message with `\n` emits a second, unprefixed line. No current sink interpolates raw client input, so this is defence in depth. Escape line breaks in `format_line`.
- S25 — **`bluebird` is a production dependency for one `Promise.delay`** (`bootstrap_database.js:1,23`) and shadows the global `Promise` in that file. Use `timers/promises`.
- S24 — **`bin/bcrypt` takes the password on `argv`** (`bin/bcrypt:11`, shown that way in `docs/cli.md:44`), visible in `ps` and shell history. Read from a prompt or stdin. Loading `config/` from `bin/bcrypt` and `bin/activity-summary` also creates `data/` and writes `data/secret.key` as a side effect.

### Docker and CI
- S22 — **`docker-compose.yaml` silently overrides `.env`**: its `environment:` block (`:8-12`) hardcodes the public URL, upstream URL and database, and Compose gives `environment` precedence over `env_file`, so the values `.env.example` tells operators to set are ignored. It also binds `3000:3000` on all interfaces and sets the MySQL root password to `root`. Use `${VAR:-default}` interpolation.

Verified sound: no `pull_request_target`; deploy is gated on the four test jobs; registry credentials only reach the masked login action.
- S38 — **Branch and version drift.** `production` carries `release v1.14.1` (2026-07-18) that was never merged back; `master`, 24 commits ahead, still reports 1.14.0 from `/auth/health` and `package.json`. The next `bin/release` on `production` will bump from 1.14.1 while `master`'s history says otherwise. Merge release commits back, or read the version from the tag at build time.
- S39 — **Work in progress lives only in a stash.** `stash@{0}` holds 17 files of admin-panel work (a migration, a new helper, tests, a design note) with no branch. A stash is easy to drop and invisible to reviewers; it is also what broke the test database (S14). Move it to a branch.

### Frontend
- S31 — **A failed `/auth/status` leaves a blank page forever** (`spa.html:1193-1198`, no `try/catch`; preloader removed only on success at `:2217-2222`). A 502 from a fronting proxy shows nothing. Catch, dismiss the preloader in `finally`, show a banner.
- S32 — **The previous user's data survives sign-out in the same document**: sign-out is handled client-side without a reload (`:2140-2143`, `:1291-1295`) and `popstate` re-renders without refetching (`:1179-1184`), so Back after sign-out on a shared computer shows the old profile, session IPs and token prefixes. Use `location.assign` on sign-out and clear rendered data when unauthenticated.
- S33 — **The demo bar is on by default on the documented quick-start hosts**: `spa.html:1136` enables it for `localhost` and `127.0.0.1`, which is where `getting-started.md:30` and `recipes.md:14` send new users. Extends L11. Gate on `?demo=1` only, and never in the shipped file.
- S34 — **Password-manager and keyboard defects**: the change-password inputs (`:803-811`) have no `autocomplete`, so managers may fill the current password into "new"; sign-up, reset-confirm, magic-request and verify-code screens are `<div class="form">`, not `<form>`, so Enter does nothing; the split OTP inputs lack `autocomplete="one-time-code"`. Every secondary navigation control is a `<span onclick>` (16 of them), unreachable by keyboard; extends L12.
- S36 — **`navigate_after` fetches the return target, then navigates to it** (`:1255-1264` with `redirect: 'follow'`, then `:1291-1298`): the upstream return URL is requested twice with cookies, and a side-effecting GET runs twice. Use `redirect: 'manual'` and read `Location`.
- S40 — **The N31 fix is unpinned.** The crash was closed by a library contract (`urlparts` is total in 3.78). Add the four malformed-input cases (`//[`, `http://[::1`, `/%`, a bare `?`) to `urlxxx.test.js` and one API test that `GET //[` returns a response, so a future helper release cannot silently reopen it.

### Findings

### F1. One timed-out test poisons every later test

*Medium · Reproduced*

**Where.** `mocha.api.js:42-58` opens a transaction per test and rolls it back only when the test body settles; a mocha timeout does not settle it. The SQLite pool is one connection, so the next test blocks on acquire.

**What happens.** A probe with one 300 ms timeout made every subsequent test in the run fail, including a pure-filesystem test, and without `--exit` the process hung in `afterAll` on `db.destroy()`. On MySQL/Postgres the same happens after ten leaks. The first real failure is buried under hundreds of consequential ones.

**Fix.** Race the test body against its timeout inside the wrapper and always roll back in `finally`; set a short `acquireConnectionTimeout` so the real failure surfaces; print the first failing test prominently.

### F2. Anonymous-rejection tests cover 6 of 19 protected routes; CSRF tests cover 6 of 20 mutating routes

*Medium · Reproduced*

**Where.** Mutation of `auth_middleware.js:18` above. CSRF assertions exist only in `csrf.test.js`, `profile_post.test.js:75` and `status_get.test.js:21`. The OAuth connect guard (`make_oauth_flow.js:90-92`) has zero coverage hits.

**Fix.** One table-driven spec over the output of `express_routes` asserting "Authentication required" and "Invalid CSRF Token" for every `POST /auth/*` behind those middlewares. New routes are then covered by construction.

### F3. `npm run test:e2e` seeds a published credential into the developer's database

*Medium · Verified in code*

**Where.** `playwright.config.js:96` sets `AUTHWALL_SEED=foo:foo`; `tests/playwright/start_server.js:25` boots `src/index.js`, which runs `bootstrap_users()` against whichever database `.env` selects.

**What happens.** A local end-to-end run creates a `foo`/`foo` user in the developer's working database, or in the MySQL/Postgres instance named in `.env`. Same root cause as N10 and S14.

**Fix.** Dedicated test database, and a per-run random seed password.

#### Missing negative tests (verified absent by grep and coverage)
- Return URL: only `https://evil.com` and `/\evil.com` are tested; no sibling domain, no protocol-relative `//evil`, no scheme mismatch, no absolute same-host or subdomain accept. `redirect.js:38-47` has zero hits and no unit test.
- Cross-user session revoke; revoked or expired session over WebSocket; magic-link *code* re-use after success.
- Oversize bodies (JSON 100 kB, multer 5 MB; the upload `fileFilter` has zero hits); CR/LF in `AUTHWALL_SET_HEADERS` (no handling, no test).
- A bearer token reaching `/auth/sidecar` with an unverified owner (`status.js:172`, `:191` branch arms never taken).
- Every variant in S1, and the sequence in S2.

#### Lower-severity harness items
- F5 — **`npm run test:coverage` never fails**: `package.json:27` chains with `;` and ends in `c8 report`, so the exit code is 0 even when tests fail. Use `&&` or `c8 --check-coverage`.
- F6 — **The CI `echo` service container is dead weight** (prior L15): every job exports `AUTHWALL_UPSTREAM_URL=http://echo:8080`, and both harnesses overwrite it with an in-process server.
- F7 — **Config restore drops the MySQL collation prototype**: `structuredClone` in `mocha.api.js:34,86` loses the `Object.create({collate})` trick from `knexfile.js:98`. Harmless today because knex is built once before any restore.

## Cross-cutting observations

### Nothing from July was worked, and the one Critical closed by accident

Thirteen commits landed between the July 27 and July 28 audits. Zero landed between July 28 and today apart from a dependency bump. That bump fixed N31, which is good, but the repository does not know it: no test covers the malformed-target case, so the fix lives in a library's documented behaviour rather than here. The rest of the register, including six Highs, is exactly as it was. A finding register that is not being drained is a liability in itself, because each audit re-verifies the same items and the cost of doing so grows.

### The trust boundary is checked on the wrong representation

S1, S5 and the still-open N5 are one defect in three places: an authorization decision made on a string that is not the string the other side will act on. The public-path check matches the raw request path while the upstream normalises it; the WebSocket limiter keys on the socket address while the HTTP limiter keys on a forwarded header; the sidecar sees no path at all. July recommended a single `authorize_request(req)`; this audit adds that the function's first job is to compute a canonical path and a canonical client address, and that every consumer (proxy, sidecar, upgrade, limiter, audit log) must use those and nothing else.

### "Unverified" is a state the code stores but does not honour

S2, S6, S8, H6 and prior L3 all reduce to the same query shape: `where({type: 'email', value_normalized})` with no `verified_at` condition. The schema records verification; the lookups that decide who signs in, who receives a reset link, and whether an account still has a usable credential ignore it. One shared `find_verified_email_identity()` helper, and a rule that unverified rows expire, closes the whole cluster.

### Validation happens at config time and nowhere else

`make_config.js:538` has a correct e-mail shape check; no route uses it. Usernames are trimmed and stored. Display names are stored up to the body limit. The consequence is S3 and N18, and it will be the next XSS or injection too. A single boundary helper (shape, length to column width, no control characters) applied to every `req.body` field before it reaches storage is a smaller change than fixing each sink after the fact, and the sinks still need escaping regardless.

### Two Highs in this report were in earlier audits and were dropped

Path traversal was raised on July 5 and July 10 as "deployment-dependent". The spoofable client IP was raised on July 2, 5 and 10, demoted to Low on July 27, and absent on July 28. Neither was fixed; both simply fell off the register as the reports were rewritten. Each audit should carry the previous register forward verbatim until an item is closed with evidence, and "depends on the upstream" should read as "reproduce it against the most common upstream" rather than as a reason to lower severity.

### The test suite is coupled to the developer's machine

S14 is what N10 looks like when it finally bites. The suite loads `.env`, uses the developer's SQLite file, and cannot be pointed elsewhere. It passed 386 tests in a clean copy and zero in the checkout. Anything that makes "run the tests" depend on state outside the repository will eventually produce a green CI and a red laptop, or the reverse.

## Method

The lead read the request path end to end (`create_app.js`, the config layer, session store, auth and CSRF middleware, status and health routes, entrypoint, bootstrap, and the helper library's URL parser) and ran the reproductions for S1, S2, S4, S5, S14, N1–N4, N8, N13, N31 and the config-value matrix. Five parallel reviewers each took one area (OAuth; account routes and actions; services, database, CI and Docker; SPA and documentation; test suite and harness), re-verified every July finding in that area against the current lines, and reported new findings with evidence. Findings from reviewers that decide severity (S2, S3) were re-checked by the lead before inclusion.

All test runs and probes used a disposable copy of the repository under the session scratchpad with `node_modules` symlinked, so the checkout at `/app`, its `data/` directory and its `.env` were never touched. Probe specs were removed afterwards. Old log contents under `data/logs/` were counted for token-bearing lines but no values were printed or copied.

Not covered: a browser execution of S3, MySQL and Postgres backends (no server available; M8's exploitability there is by reasoning), the Docker build, and the bind-mount permission behaviour in the getting-started docs.
